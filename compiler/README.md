# The bmb compiler

M1 (ADR-0016) minimal end-to-end path: parsing → name, type, ownership, spec and effect checking → proof gate (Z3) → LLVM IR → executable.
The semantics and the encoding are in ADR-0017 and ADR-0018.

```
cargo run -- check a.bmb b.bmb   # prints diagnostics as JSONL. Exit code 1 if there is an error
cargo run -- verify a.bmb        # check + proof. Includes a status line per definition. --emit-smt DIR saves the queries (the canonical symbol text the solver received, the names of the symbols are in the `.legend` next to it, ADR-0063). Compared with the port: the rows, diagnostics and exit code, and the scripts with every query asked after an answer, with and without the proof cache (not yet the incremental cache of `--cache DIR` without `--emit-smt`)
cargo run -- build a.bmb -o app  # produces an executable only when every obligation is proved
cargo run -- emit-llvm a.bmb -o a.ll  # IR. Unproved obligations remain as runtime checks (trap)
cargo run -- emit-llvm --all-checks a.bmb -o a.ll  # IR without proof. Every obligation remains as a runtime check (contracts are not trusted, so mutants that cannot be proved also run honestly)
cargo run -- codes               # list of diagnostic codes (JSONL)
cargo run -- fix a.bmb           # applies mechanical fixes (replacement) and rechecks, repeatedly. By default it only reports (JSONL), --write fixes in place, --print prints the fixed text
cargo run -- verify --cache .bmb-cache a.bmb  # proof cache: a proved obligation with the same solver input is not solved again. Unchanged definitions also skip encoding and IR generation
cargo run -- verify --def u::f --def u::g a.bmb  # proves only the named definitions (the whole program is checked). The status lines are byte-identical to a full proof, the exit code follows only those definitions. An unknown name gives exit code 2 (the overlapping reads of two edits are re-proved at merge, ADR-0065 decision 4)
cargo run -- stability a.bmb     # proves with Z3 seeds 0..5 (--seeds N for 0..N) and reports definitions whose verdict changes with the seed. Compared with the port
cargo run -- uses a.bmb          # for each definition that is not proved, finds and reports a minimal #[uses(..)] list. With --write it edits the file. --cache DIR is the same cache as verify
cargo run -- lint a.bmb          # contract tuning lint: impossible pre, pre not used by the proof, post not used by callers, weak specs where a mutation survives (warnings W09xx). --cache DIR is the same cache as verify. --select W0901,W0905 runs only those checks. Compared with the port for `--select` of W0901, W0902, W0905 and W0918 (the satisfiability checks and the re-verification without a precondition; the port has not the other checks, nor `--cache DIR` with W0902 or W0905, which goes through the incremental cache)
cargo run -- mutate --def u::f a.bmb  # all W0904 mutations (no cap, no proving) as programs: per row the normal form of the changed unit (for the BSB generator)
cargo run -- examples --count 3 u::f -- a.bmb  # examples and counterexamples of a contract: from `requires` and `ensures` alone, without the body, the allowed inputs and outputs, rejected results and excluded inputs as JSONL (see "Examples of a contract" below). Compared with the port
cargo run -- weaken old/ new/    # spec weakening detection: compares the contracts of two editions (files or workspaces) by SMT implication, per definition same, refined, weakened etc. with a counterexample, a weakening is W0908. Exit code 1 if there is a weakening or an undecided one
cargo run -- weaken --readers r.jsonl old/ new/  # the reader's comparison: each line gives a definition and the #[uses] of a proof that reads its contract, and the forward verdict is made with only that disclosed set (and the spec fns the two contracts call: the reader's default context, ADR-0095 A1) (ADR-0065 §3)
cargo run -- reads a.bmb         # one row per definition with its proof key (the proof's read set: its own text, callee contracts, unfolded spec fns, declarations, types)
cargo run -- doctor              # checks the pinned Z3 and LLVM versions (scripts/toolchain.env)
../scripts/setup.sh              # installs the pinned versions (in a new cloud session the start hook runs it automatically)
../scripts/check.sh              # verification gate: fmt, checks of things that go stale (scripts/fresh.sh: generated documents, surface fingerprint, fast health), clippy, build, then the test executables and the script checks concurrently (scripts/gate_jobs.py), and at the end a check of the files the run left behind. Only one runs at a time (scripts/with_gate_lock.sh). Judge by the exit code
cargo run -- map all a.bmb        # standard map L0 to L2 (JSONL, ADR-0020; types, `impl` functions and `types` edges are in ADR-0026 §6)
cargo run -- query slice u::f -- a.bmb  # read queries: units surface edges slice find contracts status impact duplicates effects tests
cargo run -- query status m1 m2::f -- ws  # scope arguments: units, status, duplicates, effects, effect E and tests take paths (unit, definition, type) and answer only for what is under them. edges DEF out 64 calls follows only edges of that kind (see "Query scope" below)
cargo run -- query --cache .bmb-cache status -- ws  # map and query also take --cache DIR (it affects only L1, surface and status, which prove; the output is the same bytes)
cargo run -- import ws a.bmb     # one normal-form file per unit in the workspace ws/src/
cargo run -- apply ws ops.json   # write transaction (unit/put/remove/remove_unit/rename/expect, see "Identity" below). A structural or type error rejects the whole transaction. `put` writes every item of a unit (ADR-0074): a function, type (including attributes), trait or trait impl replaces the whole item at the same address (`unit::f`, `unit::T`, `unit::Trait`, `<unit::T as unit::Trait>`), and the functions of `impl T { .. }` are merged function by function into T's block. `use` is the checker's E0214. `remove` takes those five addresses and `unit::T::f` (`unit::T` together with its inherent `impl` block, and the block too if it is the block's last function). Trait methods, trait impl functions and units are rejected with a message saying what to use instead
cargo run -- mcp ws              # MCP server (stdio): query map verify build tx_begin/put/commit etc.
cargo run -- mcp --write-tool ws # adds `write` (unit, definition, removal, commit and proof in one call) to the above. The frozen task sets are used with it off
cargo run -- mcp --compact ws    # compact agent projection (ADR-0068, `src/view.rs`): the surface is the bodiless normal form after `// path: status`, L0, L2 and slice are text, a successful proof is `{"verified":N}`, no hashes, positions or costs. Off by default (frozen measurement condition)
cargo run -- mcp --tool-docs ws  # explains the tools by the tool descriptions alone: for `query` what each query returns, `write` as the only write path (arguments are explained only in the schema), no design references (ADR or backlog numbers). Replaces the tools section of the prompt (ADR-0072). Off by default (frozen measurement condition)
cargo run -- mcp --bounded ws    # the results of `query` and `map` as a window with a budget of 32,768 bytes (ADR-0127): when cut, a `truncated` row comes last, and the two tools take `offset` and `limit`. Off by default (frozen measurement condition)
cargo run -- mcp --bounded-16k ws  # the same window with a budget of 16,384 bytes (which budget becomes the default is not decided yet)
cargo run -- mcp --item-docs ws  # the descriptions of `tx_put`, `tx_remove` and `write` state the five items and their addresses (ADR-0074 §6). The behaviour does not depend on the flag, and without the flag the tool list bytes of the frozen sets stay as they are (`frozen_tool_lists_keep_their_bytes` in `tests/mcp.rs`)
cargo run -- mcp --stats ws      # per response, one line of the frontend cache counts (`parsed`, `reused`, `checks`, `indexes`) to standard error (`tests/mcp_cache.rs`). The response bytes stay as they are
cargo run -- mcp --file-tools ws # file diff editing surface (ADR-0073): `read_file` (the source text of a unit file) and `edit_file` (apply a unified diff, commit and prove in one call). Off by default (frozen measurement condition)
cargo run -- mcp --ast-tools ws  # JSON AST editing surface (ADR-0073): `read_ast` (the syntax tree at a JSON Pointer position) and `edit_ast` (apply a JSON Patch, commit and prove in one call), diagnostic positions are the tree pointer `at`. Off by default (frozen measurement condition)
cargo run -- ast ws              # the syntax tree as one JSON document (what the JSON AST surface sees, unit names are the keys, no positions)
cargo run -- dump tokens a.bmb   # the lexer's tokens as JSONL (file, byte range, kind, the normal-form `text` of a literal, integer `value`, float `bits`, byte string `value`: stage-by-stage comparison with another implementation)
cargo run -- dump parse a.bmb    # the parser's program in normal form before checking (also programs the checker rejects, `bmb fmt` is after checking)
cargo run -- dump types a.bmb    # what the checker's body check computed (compared with the port): `types` (the resolved program, locals per definition, type per expression, type arguments, call edges, effects, recursion), `moves` (the places where an owned value is given up)
cargo run -- dump texts a.bmb    # the qualified texts the incremental key reads (compared with the port): per definition the qualified normal form and the exterior that callers read, then per item the qualified hash
cargo run -- dump lowered a.bmb  # the tables code generation reads (compared with the port, `Tables::lowered`: text is bytes, `char` is `u32`): function signatures, data types, heads of trait `impl`s, locals, type per expression, type arguments, places that are text, then for each type that appears in the tables the type with its references stripped and the fields and variants of its instance
cargo run -- dump layout a.bmb   # code generation's type layout (compared with the port, when the check passes): for each type that appears in the tables the register type, memory type, size and alignment, the predicates that hold and its kind as an element, then whether it holds a `Vec`, whether it has heap values, the entry point, `---`, the LLVM type definitions
cargo run -- dump smt-decls a.bmb  # what the proof encoder derives before it reads a body (compared with the port, when the check passes, with no solver, `verify::dump_decls`): the instances of generic spec fns the program reaches and the types they mention (`prepare`), then for each function of the encoder's tables (a `Vec` and text are an array and a length, a `Box` is its value) the sorts of its parameters and of its result, the SMT functions of a spec fn and the declarations of its type parameters, then the datatype declarations in their order, which parameters and results are text, and each definition's default proof context
cargo run -- dump smt a.bmb        # what the proof encoder builds of each definition (compared with the port, when the check passes, with no solver and nothing canonicalised, `verify::dump_smt`): the declarations of the spec fns, then for each definition and instance a `def` row (kind, unit, substitution, `#[uses]`, proof context, the spec fns of its contract, what it reveals, which parameters and result hold an array, the field positions of struct parameters), for a spec fn that is not generic an `axiom` row (its definition as the queries take it, the parts for ground instances, the struct facts of the text), for a proof fn a `proof_params` row (the declarations and facts of its parameters on entry), for a recursive spec fn a `termination` row, for an executable or proof function with a body an `exec` row (the declarations, the obligations that hold by their own text, whether the end of the body is unreachable, the path condition there, the entry values, the texts known valid, the validity functions defined, and the reach points with their path conditions: the end of the body and the exit of each loop, as the vacuity check records them), and after a `termination` or `exec` row one `obl` row per obligation (code, position, message, `shared` and `assumptions`: the number of assumptions it shares with the row before it, from the start, and the rest; goal, struct facts, the value a counterexample adds, and `sub`: the query of a sub-proof `assert .. by`, or why its assertion has no translation). `encoded` is false for an `#[external_body]` function alone, which has no obligations
cargo run -- dump smt-queries a.bmb  # the queries of each definition as the solver would receive them first (compared with the port, when the check passes, with no solver, `verify::dump_queries`): per definition a `queries` row with its `script` and `legend`, the bytes `verify --emit-smt` writes to `DEF.smt2` and `DEF.smt2.legend` when no retry runs (per obligation the query with bit operations abstracted, the probe and the full query, or the query of a sub-proof; what follows an answer is not there: the ground-instance retries, the bounded search, the trusted pass of a program with escapes, of which this is the first pass), then per definition a `reach` row with every form each reach point of the vacuity check may be asked in (probe, bit-vector form, recursive form, full query). The proof pass itself writes them, with a switch that starts no solver. The dump of a large program is large: every query repeats its base
cargo run -- dump runtime        # code generation's constant IR texts with their names as JSONL (`scripts/codegen_text.py` makes the port's `selfhost/codegen_text.bmb` from this)
cargo run -- dump lower a.bmb    # the checker's stages before the body check (stage-by-stage comparison with the port): `std` (the program with the named library units added), `lower` (after lowering function values and constants, the generated names and the values of the constants), `decls` (the declarations the checker collected, as JSONL). The diagnostics up to that point, `---`, the text of that stage
BMB_SOUND_ITERS=60 cargo test --release --test soundness  # soundness fuzzing: compares proofs, counterexamples and builds against an independent interpreter
BMB_SOUND_ITERS=40 cargo test --release --test soundness_owned  # owned data fuzzing: moves, replacements and reference match on linked lists, Box and Vec fields; compares proofs, counterexamples, builds and valgrind frees against the interpreter
BMB_SOUND_ITERS=200 cargo test --release --test soundness_widths  # integer width and bit operation fuzzing: the ten integer types, mixed widths, bit operations and shifts (literal and variable amounts inside and outside the width), bit methods and conversions; compares proofs, counterexamples and the output and traps of the two builds against an interpreter with Rust semantics
BMB_FMT_FUZZ_ITERS=2000 cargo test --release --test fmt_fuzz  # normal form and hash fuzzing: normal form and hash are invariant under layout, comments and file splitting, fmt is idempotent, status lines and IR are identical before and after fmt (only the first BMB_FMT_FUZZ_PROVE are proved). Renaming one name (definition, unit, type, field, variant, parameter, local, label) leaves every `id` unchanged, and editing a literal changes the `id` of that definition (the number of names per file is BMB_FMT_FUZZ_RENAMES)
BMB_MCP_FUZZ_SESSIONS=500 cargo test --release --test mcp_fuzz  # MCP session fuzzing: under arbitrary orders of tool calls, the response format, the transaction model, only a commit changes the workspace, and after a commit the check passes and the files are in normal form
cargo test                       # regression corpus (tests/check, tests/verify) and tests of the gate and auxiliary facts
BMB_BLESS=1 cargo test           # updates the expected diagnostics (.jsonl)
```

When standard output is closed (`bmb hash ws | head -1`), every command ends with exit code 141 without a panic (the same as a process ended by SIGPIPE, `tests/cli.rs`).


## Surface rules fixed during implementation

These make the subset of ADR-0016 concrete. All of them come from "make choices mandatory" (ADR-0013) and one normal form (principle 8).

| Rule | Content |
| --- | --- |
| Unit of organization | Only `#[summary("..")] mod name { .. }` comes at the top level. The summary is mandatory. Another unit is called by its full path (`unit::f`). There is no `pub`. `use a::b::f;` (a single name) is accepted with E0214, and `bmb fix` rewrites the uses to full paths and deletes the line (glob, group and alias forms get only the E0214 hint) |
| Definition summary | `#[summary("..")]` before a function, `struct`, `enum`, `trait` or `const` (optional, one string). A `///` line is its input form, and the normal form moves it into the attribute. The hash and the proof do not read it, and it goes out as the `summary` key of map L1 (ADR-0117) |
| Functions | The return type is mandatory (including `-> ()`). An executable function must have `#[effects(..)]`: `pure` (no effect) or a set of the effects `alloc` (heap allocation: `Vec::new`, `Vec::with_capacity`, `push`, `clone`, `Box::new`; aborts when memory runs out) and `io` (output); the normal form is in name order (`#[effects(alloc, io)]`, ADR-0030). The declaration must contain the effects the body needs (its own operations and the declared effects of its executable callees): if one is missing it is E0606 (the fix is the attribute with all needed effects written), and if a `pure` function calls an `io` function it is E0603 at that call. A declaration wider than needed is allowed (the declaration is the interface). Writing `pure` together with another effect or writing one effect twice is E0607 (fixed to the normal form), an unknown effect is E0602. A function of a trait impl cannot have an effect that the trait method does not declare (E0316). `main` contains `io` (E0701). `panic` and `nondet` are brought in together with their sources (escape hatch 2E, input builtins). The property test that compares E0606, E0603, `effects_required` and `query effect` against a reference implementation on random call graphs is `tests/effects_props.rs` (ADR-0030 §8). A `spec fn` has no effect attribute. A `proof fn` writes neither a return type nor an effect attribute (E0256, see the proof function item below) |
| Clause order | The order `requires`, `ensures`, `decreases` is fixed |
| Input aliases | Habitual forms whose meaning is uniquely determined are accepted without an error and read as the same syntax tree as the canonical form (ADR-0095 "the meaning of input aliases"): a repeated clause keyword `invariant a, invariant b,` (W0912), clauses before the loop body `while c { invariant a, decreases d, .. }` (W0913), compound assignment `t op= e` as `t = t op e` (W0914: E0103 if the place calls a function), and `T::try_from(x).unwrap()` as `x as T` (W0915). `bmb fmt` writes the canonical form, `bmb lint` reports it, and `bmb fix` fixes it by splicing the source text. The hash, the map and the proof are those of the canonical form (`input_aliases_are_the_canonical_program` in `tests/fix_cmd.rs`) |
| Contracts | Each clause of `requires` and `ensures` is a `bool` spec expression. A clause that contains a quantifier is written as a call to a named predicate (`spec fn .. -> bool`) (E0501, ADR-0095 A2). A predicate whose body is `true` is rejected |
| Result name | To use the result in `ensures`, name it with `-> (r: T)` |
| References | `&[T]` and `&mut [T]` only on parameters. As an argument, pass `&arr` or `&mut arr`, or pass on a received reference parameter as it is. A `&mut` argument cannot overlap another argument of the same call. However, it is allowed when a scalar argument passed by value only reads that array (`f(&mut a, a.len())`, ADR-0024) |
| Names | A local name cannot shadow a visible name (a parameter, an outer local, the result name) (E0303). The same name in scopes that do not overlap (sibling blocks, two `for i`, different `match` arms) is accepted if it has the same type (one type per name in one function, ADR-0095 A3) |
| Literals | No suffixes (`5i64`, `0xffu32`) (E0104, with a fix that only deletes the suffix). The type is determined by the context. Decimal and `0x`, `0o`, `0b`, with the `_` separator (ADR-0048 §3). A digit outside the radix (`0b102`) or a prefix without digits (`0x`) is E0108. The normal form keeps the radix that was written (the syntax tree has `Radix`) and writes the digits of that radix in lowercase, without separators and leading zeros (`0xFF_00` → `0xff00`, `0b0000_0101` → `0b101`, `1_000` → `1000`). A separator is only layout, like whitespace, so one normal form (ADR-0019) is kept. Array lengths and repeat counts (`[T; N]`, `[v; N]`) are counts, so they are written in decimal |
| Floating point | Only `f64` (ADR-0061). A literal has digits on both sides of the point (`1.0`, `6.02e23`, E0109), and an `f64` in the place of an integer literal is E0401 with the fix `1.0`. Comparison is IEEE (no `Eq` or `Ord`, E0428), from integers only `f64::from(x)` (a 64-bit source has the obligation `\|x\| <= 2^53`), and from `f64` to an integer, `%` and `to_bits` are rejections with a hint. In proofs the operations are uninterpreted symbols, and IEEE applies only inside `by (bit_vector)`. For details see the "Floating point" item below |
| Control | There are `return`, `break`, `continue` and labels, `loop`, range `for`, `?` and `match`. The last expression of a block is its value. `decreases` is mandatory on every `while` and `loop` (automatic for `for`), and `decreases` is mandatory on recursive functions (including mutual recursion) |
| Spec only | `forall`, `exists`, `==>`, `old(..)` and `#[trigger]` only in spec contexts. `exists|x: T| e` has the same rules as `forall`: integer bound variables (E0402), `#[trigger]` mandatory (E0511, E0512), the encoding is SMT `exists` (the range facts with `and`), and the trigger lint W0906 is the same (ADR-0079). `old` only on `&mut` parameters, in `ensures`, loop invariants, `assert` and `proof` blocks (the value at function entry) |
| Ghost contexts | The body of a `proof fn` and a `proof { .. }` block in executable code (in statement position, including loop bodies, no value). What may come there: calls to a `proof fn` (as statements), `assert`, `if` and `match` (case splits), and `let` of a spec expression. Calls to executable functions, assignment, `let mut`, `&mut`, loops and nested `proof` blocks are E0257, and calling a `proof fn` outside a ghost context (executable code, specs) is E0258 (in executable code, with a fix that wraps it as `proof { f(..); }`). A `let` in the block is visible only inside that block. In the normal form a `proof` block is a statement at the place where it was written (the order is meaningful: the fact holds from there on) |
| Nesting limit | Syntactic nesting (parentheses, unary operators, blocks, `if`, `else if`, `while`, `==>`, chains of binary operators and postfix operators, types, units) goes up to 256 levels. Beyond that it is E0107. Array and object nesting in JSON input (transactions, MCP) also goes up to 256. The CLI and the MCP server run on a thread with a large stack (`STACK_BYTES`) |
| Comments | Only `//`. They do not go into the map. Structured rationale (ADR-0006) comes after M1 |

- Data type surface (ADR-0026, 2B in progress): the parser and the normal form read and write `struct`, `enum`, `impl T`, `Option<T>`, `Result<T, E>`, the receiver `self: &T`, struct construction, field reads, `*p` and `match`. Inside a unit the normal form is subunits → types (in name order, each type's `impl` right after it, the functions in it in name order) → functions; a `match` has one line per arm, and a condition that contains a struct construction is wrapped in parentheses. A struct construction is read only when `name :` follows `T {`, so it is not confused with the block of `while k < n { .. }`. The checker accepts type declarations, names, signatures, `impl` functions and `T::f` calls (recursive types E0421, the builtin names `Option`, `Result`, `Some`, `None`, `Ok`, `Err` are reserved E0309, one `impl` in the same unit as the type E0308, if the first parameter is that type its name is `self` E0310, type arguments and empty types E0420, unknown types E0305). It also checks values, fields and `match` (struct construction E0422, unknown fields and variants E0306, E0307, exhaustiveness and declaration order E0426, payload count E0427, `==` on data types in executable code E0425). Rust habits for data types are E0220 to E0233, and the mechanical ones have a `replacement` (`if let` and `_ =>` become a whole `match` in declaration order). Proof (ADR-0027): a struct is decomposed into its fields, an enum (including `Option` and `Result`) is an SMT datatype per instance, and `match` is discriminant path conditions (an enum value in executable code, that is, a parameter, a call result or a value after a loop, has for each variant the range facts of that variant's payload leaves, conditional on being that variant: the same as the facts a `match` arm gives. Without them a `spec fn` that takes the payload slice of an `Option<Vec<u8>>` result was not unfolded because of the range guard on the length), and a slice of structs is an array per leaf. Counterexamples are in Rust notation (`Point { x: 1, y: 2 }`, `Some(-1)`). Spec `==` is Rust's `==`: field by field for structs, only the elements within the length for arrays (a fixed length of 16 or less is unfolded element by element, otherwise a range quantifier), and for an enum with an array payload the same variant and the same payload. Specs can use array literals and repeats (including the empty array) and recursive calls inside `forall` (a measure obligation per bound variable). There is no construct the prover does not accept (E0814 retired). Code generation: structs and enums live in memory as named LLVM struct types (an enum is a tag `i64` and a payload area, with a view type per variant) and travel as pointers. They are copied where Rust copies (arguments, fields of a construction expression, payloads, `let`, `=`, `match` bindings) (`memmove`, the size is a constant expression of the LLVM layout), and a data result is returned through memory given by the caller (`ret.out`). `&T` and `&mut T` are the address of that place. Arrays of data types: `[T; N]` in locals, fields, payloads, results and slices. The element is a scalar, a struct or enum (including array fields), or a fixed array (nested `[[T; M]; N]`), and only `Vec` is not allowed (E0402, proposed in ADR-0047). A place is a path of variables, fields and elements, like `g[i][j] = v` and `b.rows[i].cells[j] = v`. They are also used as value parameters and results (a parameter is copied by the callee, a result goes to `ret.out`). The result of a scalar array is the same. The proof is an array per leaf like a slice of structs, the length is `N`, a literal is a `store` per element, and a repeat is a constant array per leaf. A fixed array inside an element is a leaf array one level deeper (`(Array Int (Array Int T))`) and its length is a constant (`elem_leaves`, `elem_template`). Code generation is `[N x %T]` in memory; a literal computes all elements and copies them aside before filling (`a = [a[1], a[0]]`), a repeat is a fill loop, and `let` and `=` copy the whole array. The fields of a construction expression are written in declaration order: another order is E0434 with the expression rewritten in declaration order (ADR-0080), and the normal form does not sort (the evaluation order is the written order).
- Integer conversions (ADR-0028, surface ADR-0095 A4): `x as T` (`T` is an integer type, the precedence is the same as Rust, after unary operators and before `*`) leaves the value as it is, and if the range of the target does not contain the range of the source (`i64`→`u64` is `x >= 0`, `i32`→`i16` is `-32768 <= x <= 32767` etc., `check::conv_obligation`) it gives the prover the range obligation E0815. If it does contain it (`u64`↔`usize`, `u8`→anything, `i16`→`i32`) there is no obligation. `T::try_from(x).ok()` is `Option<T>` and has no obligation (`Some` if in range). Code generation emits no instruction for a proved conversion, and for an unproved conversion it leaves a target range check (one comparison, `Gen::in_range_of`) and a trap. `T::try_from(x).unwrap()` is an input alias read as the same syntax tree (W0915, `fmt` and `fix` turn it into `x as T`). Habits: `as` with a target that is not an integer or `f64` is E0205 (`x as f64` is replaced with `f64::from(x)`), a bare `T::try_from(x)`, a method other than `.unwrap()`/`.ok()`, or a non-integer source is E0412 (`bool` is replaced with `if b { 1 } else { 0 }`), `T::from`, `.into()` and `.try_into()` are E0212, `.expect(..)` is E0213, and a conversion inside a spec is E0513 (specs mix integer types, ADR-0022). The builtin `print_u64` prints a `u64` unsigned.
- `const` items (ADR-0052, `src/consts.rs`): `const NAME: T = e;` (the type is mandatory, a value type: integers, `bool`, `char` and arrays, structs and enums of them (including `Option` and `Result`). Containing `Vec`, `String`, `Box` or a reference is E0437). - Early return (ADR-0049 §1, §3, §4): `return e` and `return` are expressions of type `!` (`TypeKind::Never`) that come in statement and expression position (`None => return d,`). `!` fits any expected type (`expect_ty`), an `if` or `match` with one arm of type `!` has the type of the other arms, and a block without a tail that ends with a statement that does not finish has `!`. A `return` inside a spec is E0503. An `if` or `match` in statement position ends at its closing `}` (Rust: `if c { return; } *x = 1;` is two statements). Proof: the postcondition is an obligation under the path condition of the return point (`Enc::post_check`, the same function as at the function end) and that path ends (`Enc::dead`). A join (`branch`, the right side of `&&` and `||`) leaves out the side that ended and continues with the condition and facts of the remaining side, and when a loop body ends there are no invariant preservation and decrease obligations. Move check: every owned local and parameter (including field paths) that a `return` passes is dropped at that exit (`MoveInfo::exits`), a join leaves out the ended path (`Mv::join`), and the later statements of the same block are not looked at. Code generation: it returns after dropping the owned temporaries of the enclosing regions and the exit drops (`Gen::emit_return`, shared with the function end), and the code after it is put in an unreachable block (the value is `CVal::Never`). - Loop exits (ADR-0049 §1, §3, §4): `break`, `continue`, `break 'l`, `continue 'l`, the labels `'l: while` and `'l: loop` (the lexer reads `'l` as a label only after `break`/`continue` and before `:` (skipping comments), and `'a` elsewhere is a lifetime, E0208), and `loop [invariant ..,] [decreases ..,] { .. }` (the value is the value of `break e`, and `!` if there is no `break`). A `loop` in a function whose declared effects include `nondet` may omit `decreases` (ADR-0094: a loop that runs until the input ends): it is proved for partial correctness, and that definition and the definitions that call it have `"termination":"unproved"` in their L1 and `status` rows and `nonterminating` in `test_reasons`. All three are expressions of type `!`. Outside a loop E0250, a missing label E0317, a `break` with a value in a `while` E0251, a `loop` without `decreases` E0506, inside a spec E0503. The expected type of the `loop` is the type of every `break` value. Proof (`Enc::loop_core`, shared with `while`): at each `break` point of one iteration it collects the path condition and the state of that iteration (`VLoop`), and the exit is "the condition is false ∨ the path condition of each `break`" (exclusive, since they are paths within one iteration) with an `ite` of the state and value according to those conditions. Code generation: `continue` branches to the head, `break` puts the value in the result place and branches to the end, and the temporaries of the regions inside the loop and the exit drops are done first (`GLoop`, `Gen::jump`).
- Range `for` (ADR-0049 §2): `['l:] for i in lo..hi [invariant ..,] { .. }` and `lo..=hi`. - Integer types (ADR-0048 §1): `i8`, `i16`, `i32`, `i64`, `isize`, `u8`, `u16`, `u32`, `u64`, `usize` (`isize` and `usize` are 64 bits). The checker handles them with the single `TypeKind::Int(IntTy)` (width, signedness and limits are methods of `IntTy`), mixed widths are E0401 (with a conversion hint), an out-of-range literal is E0406 and unsigned negation is E0411 (both with a hint). In the proof they are all `Int` with the range fact of the type and the overflow obligation (E0803, including `T::MIN % -1`), and wrapping is the two's complement map. Code generation uses `i64` in registers (the mathematical value, sign-extended for signed types and zero-extended for unsigned ones) and the type's own width (`i16`, `i32` etc.) in memory (arrays, `Vec`, fields), extending on read (`elem_kind`, `load_mem`). `+`, `-` and `*` of types narrower than 64 bits are exact in 64 bits, so they are computed as they are (`nsw`, and only the unsigned multiplication is `nuw`: `(2^32 - 1)^2` of `u32` exceeds `i64::MAX`, so with `nsw` the range check would read a poison value), and if not proved the type range is checked (`Gen::narrow_arith`); integer methods wrap, clamp or check the result to that range (`Gen::narrow_method`). The `Vec` length limit is `isize::MAX` divided by the element size. 128 bits is E0402 (open question 1).
- Bit operations (ADR-0048 §2, §4, §5): `&`, `|`, `^`, `!`, `<<`, `>>`. The precedence is Rust's: comparison < `|` < `^` < `&` < shift < `+` (`a & b == c` is `(a & b) == c`). The parser reads two adjacent tokens `<` `<` or `>` `>` as a shift (the lexer keeps them apart, so `Vec<Vec<i64>>` closes as it is). `&`, `|` and `^` take two of the same integer type (mixed widths are E0401, with a conversion hint) or two `bool`s (both sides are evaluated, the same as Rust), and `!` is logical negation on `bool` and bit inversion on integers (anything else is E0401, with a hint; in a position without an expected type, for example the method receiver `(!(a ^ 9)).rotate_left(1)`, the operand decides). A shift shifts only integers (E0401) and the amount may be any integer type (the same as Rust; an amount made only of literals is `u32`, and an amount with its own type has that type, so `x >> (match b { None => 1, Some(v) => v })` has the type of `v`), and the type of the value is the type of the shifted value. If the shift amount may be outside `0..w` (`w` is the width) there is the overflow obligation E0803 (the panic condition of a Rust debug build; a signed amount is also blocked when negative, and a literal amount within the range has no obligation). `<<` discards the bits outside the width and `>>` is an arithmetic shift on signed types. In specs a bit operation of mixed widths has the width of a type that contains both (E0401 if there is no such type), and if the amount of a spec shift is outside `0..w` the value is unspecified (the obligation belongs to executable code). Proof (mixed encoding): integers stay `Int` and only the bit operation terms go through bitvectors of the operand width (`verify::bv_term`: `(bv2nat (bvand x y))`; for signed types, two's complement by subtracting `2^(w-1)` from the `bv2nat` with the sign bit flipped). Executable code declares a bitvector constant per operand and gives its value (`(= (bv2nat x) a)`, `a + 2^w` for a negative one: `Enc::operand_bv`; it finds models tens of times faster than `int2bv`), and specs use `((_ int2bv w) a)`. Forms that can be written linearly are linear (`verify::linear_bit`): `<<` by a constant amount is a multiplication wrapped to the width, `>>` is floor division (`div`), `a & (2^k - 1)` is `a mod 2^k`, and `!a` is `-a - 1` (`MAX - a` for unsigned). Bitvector terms are given result range facts together, under the operand ranges (`bit_facts`: the range, `&` is at most the operands, `|` is at least them, by sign for signed types, the sign of `^`, the size of `>>`). An obligation is first solved with a query that abstracts the bitvector terms to integer constants (`abstract_bits`: the same term is the same constant, a term that contains a bound variable stays as it is, and if there are quantified definitions, by their ground instances); if it is proved that is the end, otherwise it goes to the exact query (a proof of a weaker query is a proof). The abstract query gets congruence facts for the same operation in different notations (`bit_congruences`): for two terms that become the same tree when the operand constants of executable code (`|'bv@k|` with a given value), the `((_ int2bv w) v)` of specs and numeric literals are read as width and value, it gives "if the values of the differing leaves are equal the two terms are equal". This is true in any model (`bv2nat` is injective at one width, and a value equal to a `bv2nat` is in range), so the abstract query is still weaker than the exact query. Without this, `x ^ k` in code and `x ^ k` in a spec became two constants unknown to each other and were connected only by the exact query (`int2bv`), and a single 32-bit `^` did not finish at rlimit 5,000,000 (`bit_step` of `lib/crc32.bmb` 10,003,176 → 2,481). Test `bit_congruences_relate_notations_and_hold` (the facts are true by Z3 for each sample value), `mix` and `mask_xor` in the corpus `tests/verify/pass/bits`. The cost of proofs that do not need the definition of a 64-bit variable shift went down (the whole definition of `ones` in `tests/run/bits` 757860 → 8988). In `--emit-smt` the abstract query is the first attempt of the obligation and the exact query follows as `; exact query of obligation k` (`scripts/solver_stability.py` solves the abstract query, the probe and the exact query all as stages of one obligation and measures the verdict). That the terms equal Rust's operations and the facts are true is confirmed by `tests/lemmas.rs`, which computes the terms (all pairs for 8 bits; boundaries, values near powers of two and pseudo-random values for wide types). Code generation (§5): on the extended values in registers `and`, `or` and `xor` produce extended values as they are, so there is no check; `!` is `xor -1` on signed types and `xor MAX` on unsigned ones, `>>` is `ashr`/`lshr` (exact in 64 bits), and `<<` of a narrow type is `shl` followed by `trunc` to its own width and extension again. An unproved shift amount is checked with `icmp ult amount, w` and traps (`Gen::shift`, test `an_unproved_shift_traps_exactly_from_the_width`). The W0904 mutations include `&`↔`|`, `^`→`|`, `<<`↔`>>`.
- Bit methods (ADR-0048 §2): on integer types `rotate_left`, `rotate_right`, `wrapping_shl`, `wrapping_shr` (the amount is `u32` and is taken modulo the width, no obligation), `count_ones`, `count_zeros`, `leading_zeros`, `trailing_zeros`, `leading_ones`, `trailing_ones` (`u32`), `swap_bytes`, `reverse_bits`, `checked_shl`, `checked_shr` (`Some` of the wrapping shift only when the amount is within the width), and on unsigned types `is_power_of_two` (`count_ones == 1`, a signed receiver is E0404). They have Rust's signatures: argument count E0405, an amount that is not `u32` E0401, a non-integer receiver E0404 (all with a hint). In specs the operand of a bit operation or bit method is its two's complement image at the width of that type (ADR-0090: for a value that left the type through spec arithmetic, the bitvector form and the linear form also read the same value; `verify::image` wraps with `wrap_int` only the operands that can syntactically be outside the type). Proof (`verify::bit_method`): a constant amount is a linear form (a wrapping shift is the form of `<<` and `>>`, a rotation is the sum of two pieces), and anything else is a term that wraps one named bitvector function (`bmb_rotl32`, `bmb_ctpop64`, `bmb_brev16` etc.; `*_ones` is the `clz` or `ctz` of the complement; `subproof::helper_def`; only the definitions the query uses go in) in `bv2nat`, and executable code assumes the result facts (the type range; a count is in `0..=w`, and is extreme only at 0, or for `*_ones` only when all bits are 1). Because they are named functions, the same method in code and in a spec is connected by the congruence facts of the abstract query. That the terms equal Rust's methods and the facts are true is `bit_method_terms_are_rusts_methods` in `tests/lemmas.rs`. Code generation (`Gen::bit_method`): on the value truncated to its own width, LLVM `fshl`/`fshr` (the amount modulo the width), `ctpop`, `ctlz`/`cttz` (the width at 0; for `*_ones` after `xor -1`), `bswap`, `bitreverse`, then extension again. A wrapping shift masks the amount with `w - 1` and uses the same instruction as `<<` and `>>` (`Gen::shift_inst`). `bit_methods_compute_rusts_results` in `tests/codegen.rs` confirms that the values equal rustc's for every integer type (boundary and pattern values, and amounts inside and outside the width). Bytes: `x.to_be_bytes()` and `x.to_le_bytes()` are `[u8; w / 8]`, and `T::from_be_bytes(b)` and `T::from_le_bytes(b)` are `T` from that array (Rust's signatures, an array of a different length is E0401). The proof is a linear form (`verify::byte_term`: byte `k` is `(mod (div a 2^s) 256)`, so even for an operand outside the type it is a byte of the image; `verify::from_bytes_term`: the sum of the images of the bytes placed at their positions, read as a value of the type; `byte_terms_are_rusts_bytes` in `tests/lemmas.rs`). Code generation stores each byte by a logical shift and truncation and, when reading, uses zero extension, shifts and `or` (a narrow signed type is sign-extended from `w` bits), and `bit_methods_compute_rusts_results` compares with rustc. A proof that connects bytes and bitvector-form methods (for example `from_le_bytes(x.to_be_bytes()) == x.swap_bytes()`) is not decided, because the two forms differ.
- `assert(e) by (bit_vector);` sub-proof (ADR-0048 §4, `src/subproof.rs`): proves `e` in a separate query (`QF_BV`), and from then on the outer proof assumes it (E0818: the counterexample is the values of the free variables, with a hint on how to fix it). It is the same anywhere in executable code, `proof` blocks and `proof fn` bodies, and inside a spec it is E0503. The query sees only the free variables of `e`, and each ranges over all values of its type (no path facts, the Verus rule: write a needed fact as `p ==> q`). The translation takes the term the encoder made from `e` (a fresh symbol per free variable) and moves each integer subterm to a two's complement bitvector of a width that contains its interval, so it is exactly the same as the fact the outer query assumes (`bit_vector_translations_are_exact`). The outer proof assumes `(=> (and ranges of the free variables .. ranges of the unfolded arguments ..) e)`. A spec fn that the assertion calls is unfolded if it is in `#[uses]`, is not recursive or generic, and handles only integers and `bool` (an argument is named once with `define-fun`, and an argument that may be outside the type is an assumption of the sub-proof and a premise of the outer fact). Division: unsigned `/` and `%` with a non-constant divisor are translated to SMT-LIB's Euclidean `div` and `mod`, signed ones to the truncating `bmb_tdiv` and `bmb_trem` (`bvsdiv`, `bvsrem`), and when both operands are non-negative they are `bvudiv` and `bvurem` of that width (`division_translations_are_exact`). A non-constant divisor being non-zero is the assumption `b != 0` of the sub-proof and a premise of the outer fact. A variable divisor is a division circuit for the solver, so 8 bits is cheap (rlimit in the tens of thousands), 16 bits is millions, and from 32 bits on it is not decided within the limit. What cannot be translated (a spec fn that is not disclosed or is recursive) is E0818 with the reason, and an undisclosed spec fn gets a `#[uses]` hint, so `bmb uses` fills it in (`a_bit_vector_sub_proof_gets_the_spec_fns_it_unfolds`). Scalar reads such as an element, a field, a value behind a reference or a method on a non-scalar receiver (`s.len()`) are variables of the sub-proof (`verify::abstract_reads`: the same text is one variable, the counterexample uses that text, and the premise of the outer fact is the type range of the read value). What is not a term (a quantifier, `old`, a data value, a read that calls a `let` of the assertion) is the checker's E0515, and another prover name and Verus's `by { .. }` are E0516 (if it is a name, with a fix that deletes `by (..)`). The normal form is `assert(e) by (bit_vector);`. The proof cache, `--emit-smt` (`; obligation k: E0818 .. (sub-proof)`) and the incremental key are the same as for other obligations. The congruence facts of the abstract query also connect terms of the same shape whose leaf values are written differently (`t[i] ^ (c >> 8)` and `byte(i, 0) ^ (c >> 8)`, up to 64 per shape). Soundness fuzzer `tests/soundness_bitvector.rs`: it computes random assertions over two `u8` and `i8` variables (spec arithmetic, `/` and `%` dividing by a term, bit operations, shifts, `!`, methods, `if`, spec fns whose arguments may be outside the type) with the interpreter at all 65,536 points, and confirms that a proved assertion is true at every point under the guard and that a counterexample is a false point inside the guard. Where it is used: the table lemma `table_lemma` of `lib/crc32.bmb` (rlimit 104,291), `next_power` in `tests/run/bit_methods`.

- `Vec<T>` (ADR-0031, checker only): the element is a scalar or a struct or enum without arrays (E0402; `Vec<Vec<T>>` and move elements are in the item on move elements below). It can be held in struct fields, enum payloads, `Option<Vec<T>>` and `Box<Vec<T>>`. Parameters are `Vec<T>` (move), `&Vec<T>` and `&mut Vec<T>`, and the return is `Vec<T>`. `Vec::new()` and `Vec::with_capacity(n)` (the element type comes from the expected type), `push`, `pop` (`Option<T>`), `len`, `truncate`, `clone`, reading and assigning `v[i]`, and for slice parameters `v.as_slice()` and `v.as_mut_slice()` in argument position. Move check (`src/moves.rs`): a value use (`let`, the right side of an assignment, an argument, a block value) is a move and a use after a move is E0413, and moving out of `*v` is also E0413. At the join point of `if`/`else` and `match`, a value that only one arm moved is dropped at the end of the arm that did not move it (ADR-0081, `MoveInfo::branch_drops`). At the other join points (an `if` without `else`, the right side of `&&`, `||` and `==>`, the loop head and the body end) "maybe moved" is E0414. In the same call, `&mut v` or `v.as_mut_slice()` together with a move or reference of `v` is E0410. This check determines the drop points (owned locals remaining at a block end, assignments that replace an owned value) and hands them to code generation. Proof (ADR-0031 §3): the encoder sees `Vec<T>` as a slice value (a pair of an element array and a length) and `&Vec<T>` and `&mut Vec<T>` as slice references (`Tables::slice_view`). So the index obligations, the length upper bound fact, the re-determination after loops and calls, spec arguments and counterexamples are the slice path as it is. Only what changes the length is new: `push` is `len < LEN_MAX(T)` (a fact, not an obligation, ADR-0124) with `store` and `len + 1`, `pop` is `None` if `len = 0`, `truncate(n)` is `min`, `Vec::new()` is length 0, and `with_capacity(n)` has the obligation `n ≤ LEN_MAX(T)`, E0816. After a call with a `&mut Vec<T>` argument the length is also a fresh constant (only the callee's `ensures` is assumed). Code generation (ADR-0031 §4): a `Vec` is the header `%bmb.vec = {ptr, len, cap}` in memory and travels by address like a struct, and copying the header is the move (a value argument is a copy of the header, a result goes to `ret.out`). An index reads the buffer and the length each time it is used (the check only when not proved), `push` calls `@bmb_vec_grow` if `len == cap` (double the capacity, at least 4, `realloc`), `pop` is an `Option` temporary, `truncate` is `umin`, and `clone` is a new buffer and `memcpy`. If the size exceeds `isize` or the allocation fails it is `abort`. E0816 (the capacity of `with_capacity`) is, like other obligations, `; proved E0816` when proved and otherwise a check and a trap. `push` has no length check (the `abort` of the growth path takes care of it, ADR-0124). Drops: at the block ends determined by `moves.rs` (locals and value parameters that remain owned) and at assignments that replace an owned value, and a temporary `Vec` that was read without being moved is dropped at the end of its region (a statement, a block value, a `match` arm, the right side of `&&` and `||`, a loop condition). A data value that points into a buffer being dropped is copied first. The drop is the per-type drop glue (the `Box` item). The runtime goes into the IR only for programs that use the heap (that hold a `Vec` or `Box`) (libc `malloc`, `free`, `abort`, and `realloc` if there is a `Vec`).
- `Box<T>` (ADR-0047): `T` is a value type (a scalar, a struct or enum, an array, a `Box`. `Box<()>` and references are E0402; `Box<Vec<T>>` is in the `Vec` item). `Box::new(v)` (the box type is the expected type, or the type of `v` if there is none), reads `*b` and `b.f` (a field is projected through `&` and every `Box`), writes `*b = v`, `b.f = v` and `(*b)[i] = v` (only on a `let mut` local or a `&mut Box<T>`, E0408), and arguments `&*b` and `&mut *b`. Not there yet: recursive types (E0421 stays), arrays and `Vec`s of move elements (E0402), moves out of a field or `*b` (E0413). Code generation (§4): a `Box` is a cell (`ptr`) that holds a `malloc`ed address and travels by address like a data value (copying the cell is the move). `*b` and `b.f` read the address and go in (the `*r` of a `&mut Box<T>` parameter is the cell itself). A moving `match` drops the unbound move payloads at the start of the arm and the remaining bindings at the end. An allocation failure is `abort` (`@bmb_box_alloc`). The test `run_corpus_frees_every_allocation_once` builds the run corpus that uses the heap with `-O0` and checks with valgrind (AddressSanitizer if it is absent) that there are no leaks, double frees or uses after free.

- Proof functions (ADR-0062): `proof fn f(..) requires .., ensures .., decreases .., { .. }` is a lemma written by the user. Parameters are values and `&T` (`&mut` is E0257, `Vec` is E0402 as for `spec fn`), no return type is written (the parser sets it to `()`; writing one is E0256 with a fix that removes it), and there is no effects attribute (E0256). The contract clauses are named predicates as for executable functions (E0501), and with recursion (mutual recursion included) `decreases` is required (E0507, the checker's call edges include calls between `proof fn`s). Induction is a recursive call with `decreases` (structural induction is a recursive enum measure, ADR-0047 §3). The checker reads a ghost context as `Mode::Ghost`: `if`·`match`·blocks hold ghost statements, conditions, scrutinees, arguments, `let` values and `assert` are specification (`Mode::Spec`, `old` allowed), and calls are split by the kind of callee (`Checker::call`). The move check treats a `proof` block as code that only reads (`Mv::ghost`: it moves nothing). Proof (`verify.rs`, `Enc::ghost`): the body of a `proof fn` is symbolically executed like an executable function and its `ensures` are issued as obligations (`post_check`, E0802). Ghost expressions are translated with `spec`, so there are no overflow or index obligations and arithmetic is over mathematical integers (ADR-0017). `if`·`match` split with `branch`·`match_arms`, and a fact proved on one side remains under that condition (`ghost_expr`). A call is the same `Enc::call` as an executable function call: it proves `requires` (E0801), proves the measure decrease when in the same recursive component (E0809), and assumes `ensures`. Arguments of ghost arithmetic can be outside the parameter type, so it is an obligation that the arguments satisfy the facts of the type (the range of integer leaves, the length range, the range of integer array elements: `Enc::type_facts`) (E0819, omitted when the path condition already has the same fact). The `proof fn` itself assumes exactly those facts about its parameters (the range of an enum payload goes only one level deep and so is left out: an induction that descends into a payload cannot prove the payload of that payload. Write it in `requires` if needed). A `proof` block in executable code does the same translation in the state at that point, the facts proved remain in the path condition after the block, and the block's `let`s end with the block (`Enc::proof_block`). Loop havoc does not look at `proof` blocks (there are no assignments). Code generation erases `proof fn` (only executable functions are lowered) and `proof` blocks (`Stmt::Proof` has no instructions): the program without the ghost code and its IR are byte-for-byte the same (`ghost_code_leaves_no_trace_in_the_ir` of `tests/codegen.rs`). Map: `def_kind: "proof fn"` in L0·L1 (L1 `effects` is `"proof"`), the `proof_calls` edge of L2 (called from a `proof` block or another lemma, itself for induction), `spec fn` names in a `proof fn` body are `contract` edges, `impact` sees a change to a lemma's contract through the `calls` of the calling side, and `tests` does not count lemmas. Incremental key: a lemma enters the caller's hash (by its contract) like an executable callee (contract firewall: changing the body re-encodes only that lemma, `lemma_edits_follow_the_contract_firewall` of `tests/incremental.rs`). Where it is used: `tests/run/max_list` (the recursive contract of BVB `vc-vv0039` as a quantifier contract, no overflow of the sum thanks to a lemma inside the loop), `tests/run/numlist` (the digit-count limit with `pow10` and induction instead of a case-by-case predicate), `lib/utf8.bmb` (the concatenation specification `parses` and two lemmas). What remains: `proof fn` inside `impl`·trait (the parser does not accept it), `assert forall .. by { }` (confirmed when ADR-0062 was accepted: a new ADR when demand appears), lemma proposals from `bmb fix`.
- Induction lemma drafts (ADR-0062 §5, ADR-0135, `src/induct.rs`): `bmb fix --induction` proves a program that has no more mechanical fixes and passes the check, and for each unproved executable function tries writing in drafts one after another. It expands the postconditions through the non-recursive predicate definitions of the unit (depth 4, excluding the inside of quantifiers), and for each application `Q(args)` it reaches, for each recursive predicate `R` of the same unit (parameter types equal to those of `Q`, result `bool`, `decreases` a single unsigned parameter `p`), the draft is `proof fn R_gives_Q(params) requires R(params), ensures Q(params), decreases p, { if p > 0 && R(.. p - 1 ..) { R_gives_Q(.. p - 1 ..); } }` and, before the function's result (only when it is a variable), `proof { R_gives_Q(args); }` (with the result name replaced by that variable). The order is postconditions, applications reached, recursive predicates of the unit, and only the first draft with which the gate proves the lemma and the function together is applied (the code of an applied row is the diagnostic it answers, E0811; two rows, the lemma and the call). A draft that is not proved is not written, so a draft that is shown holds and closes the proof. `bmb fix` without the flag does not run the prover. The one shape handled is "recursion ⇒ a predicate of the same parameters" (BVB `vc-vv0039`: it restores in 2.3 seconds the lemma and the call removed from `tests/run/max_list.bmb`). "Prefix extension" (joining the intervals of `sum_to`) is not handled. Tests `tests/fix_cmd.rs` `induction_writes_the_lemma_the_gate_proves`, `induction_writes_nothing_the_gate_does_not_prove`.
- Type invariants (ADR-0060): `#[invariant(p)]` on a struct or enum. `p` is a `spec fn` that takes that type (`x: &T`; for a generic type, the type's parameters in the same order, with bounds within those of the type) and returns `bool`, and whose body is not `true` (E0254, the hint gives the right signature). One per type (E0255; join conditions with `&&` into one predicate). The attribute name `invariant` is the keyword of the loop clause, but in attribute position it is a name (parser `attrs`). The checker collects all signatures, then resolves the predicate and puts its full path in `Adt::inv` (`Checker::check_invariants`). The normal form writes the attribute line before the type, the qualified text writes the predicate by its full path, and the identity text writes it by `id` (the same rule as `#[uses]`): the predicate and the type are one recursive component, changing the predicate's body changes the type's `id`, and renaming the predicate leaves it unchanged. The transaction `rename` also fixes the predicate name in the attribute. Proof (`src/verify/invariants.rs`): deep validity `valid_T(x)` is the invariant atom `p(x)` (opaque like any other `spec fn`, its definition comes with `#[uses(p)]`) and the validity of fields, payloads, `Box` contents and elements. For elements it is `(forall ((k Int)) (! (=> (< k len) ..) :pattern ((select a k))))`, and the name of the bound variable is the nesting depth, so the same value is the same text. A type parameter is an uninterpreted predicate `|'T.valid|` (a generic definition is proved once), and a datatype that holds itself (a recursive enum, recursion made of structs only) is a function `|T.'valid|` defined by structural recursion, and each query attaches the ground instances of the applications that query contains, up to two levels (there is no quantified definition, so there is no matching loop, `valid_instances`). A value written with a constructor (`None`, `Some(x)`) is unfolded directly at that variant. Assumptions: the parameters of an executable function (value, `&`, `&mut`) on entry, the result of a call and the new values at its `&mut` argument places, the locals a loop havocs at its head. Obligations E0823: call arguments; the result and the current values of `&mut` parameters at every exit of the function (tail, `return`, `?`: `post_check`); the havocked locals at loop entry and at the end of an iteration (`continue` included, `back_to_head`). A fact already in the path condition is not issued as an obligation, so code that only moves values has no obligations. Inside a function the invariant may be broken for a while (field and element assignments, `std::mem::replace`·`swap`, and a `match` on a `&mut` reference create no obligations). A counterexample shows the value at the boundary together with the inputs (`result = Span { lo: 1, hi: 0 }`, `*s`, `argument`, `s on entry`, `s after the iteration`). `spec fn`, values inside specifications, `proof fn` (its parameters and the arguments of calls to it) and `proof` blocks have neither assumptions nor obligations: ghost code is a specification context (ADR-0060 §2, ADR-0062. For a lemma to use the invariant, write `requires p(x)`). The satisfiability query of W0901 uses the same entry assumptions. There is no runtime cost (code generation is unchanged). Incremental key: the type row includes the attribute, and for each type with an invariant, the hash of the predicate's body and the declaration (the `invariant`·`decl` clauses, ADR-0032). `impact` (type): it adds as `values` the definitions that have that type (or a type that holds it) in their locals, parameters, result or callee signatures (`invariant_edits_reencode_where_values_pass` of `tests/incremental.rs`, audit included). Map: the `signature` of an L1 type includes the attribute (`#[invariant(fits)] struct Stack<T: Copy> { .. }`), and a slice that includes that type also includes the definition of the predicate. Where it is used: `tests/run/ring` (ring buffer: the index `(head + i) % 8` is proved without a contract), `tests/run/sorted_set` (strictly sorted set: `insert`·`remove` keep the order without a contract), `tests/run/generic_stack` (migration: one `fits` clause of a loop invariant and the `len <= 8` of `some` disappeared). An in-place move that would leave the invariant broken between iterations is written as one `copy_within` call instead of a loop (ADR-0083: the invariant is broken only inside that operation and the loop head rule is unchanged). The `insert` of the sorted set moves over `self.items` that way.
- Escape hatches (ADR-0029): `assume(p(..));` (a statement in executable code, the argument is one call of a named predicate, E1003) and `#[external_body]` (an executable function; E1004 on `main`·`spec fn`·`proof fn`). Both need `#[rationale(kind = K, "description")]` immediately before them (E1001 without it; `K` is `nonlinear`·`solver_limit`·`boundary`·`performance`, a format error is E1002, `hash = ".."` is written by the tools). A definition with an escape hatch is a source of the `panic` effect (it keeps its checks, so it can end in a trap). Proof (`verify::verify_trusting`): when there are escape hatches, every definition is first proved without trusted facts (no `assume`, no `ensures` of a callee that is not `proved`), and only the definitions that fail there and can reach an escape hatch (`Tables::may_untrusted`) are proved again with the trusted facts: if proved, the trust level is `assumed`, otherwise it fails. `#[external_body]` has no obligations and is `external`. A definition that became `assumed` is in turn an untrusted callee, and the definitions that relied on it are proved again (until the set stops growing). The status line adds `"trust":"assumed"`·`"external"` when it is not `proved` (`status` stays `verified`). A program without escape hatches gets the same single proof as before. Code generation: a definition that is not `proved` and every definition it calls do not have their checks removed by proved obligations (`Outcome::checked`). Those checks are not missing proofs and do not block `build`. The incremental cache neither stores nor looks up definitions that can reach an escape hatch (because the result depends on the proof state of the callees). Rust·Verus habits: `unsafe` (block, item) E0215, `#[verifier::external_body]`·`#[verifier(external_body)]` E0216 (replacement), `admit()` E0217. Tests: the `escapes` module of `tests/codegen.rs` (trust levels, the `proved` set is the same with every `assume` removed, definitions that keep their checks, a false `assume` traps), `tests/run/escapes.bmb`·`tests/run/collatz.bmb`, `tests/check/err/escapes.bmb`, the soundness fuzzer `tests/soundness_escape.rs` (ADR-0029 §8: `assume`·`#[external_body]` that may be false and calls that assume their precondition, four properties). Rationale hash (§3, `escape::Hashes`): the first 16 digits of the SHA-256 of the definition's qualified normal form (without the rationale) and the text of the `spec fn`s it calls. A rationale whose `hash` differs from this or is missing is unconfirmed (it does not block the build, the recommendation of open question 2). `bmb fix` writes in a missing hash, and only `bmb fix --confirm` fixes a stale hash (confirming is a judgement). Editing only the rationale text changes neither the confirmation state nor the definition hash nor the proof key. Lints W1001 (unconfirmed rationale, the fix is the current hash), W1002 (the definition is proved without that `assume`, the fix is to remove it). Tests `maps_show_trust_and_escapes`·`rationales_go_unconfirmed_with_their_code`·`needless_assumes_are_reported` of the `escapes` module of `tests/codegen.rs`.
- Bytes (ADR-0044): `u8` is an integer under the `u64` rules with range 0..=255. It is `i64` in a register and one byte in memory (arrays, slices, `Vec`, fields), and addition and multiplication are computed in 64 bits and then `<= 255` is an obligation (E0803). Conversion to `u8` has the obligation `0 <= x <= 255` (E0815, code generation is one unsigned comparison), widening from `u8` has no obligation. `b'a'` is `u8`, `b"..."` is `&[u8]` and is written only in a call argument position (E0409). In the proof a byte string is a constant array whose length and elements are all known; in the IR it is a private constant of the function (it sits in that function's IR fragment, which fits the incremental cache). The built-in `print_bytes(s: &[u8])` writes the bytes as they are with `fwrite` (the same buffer as `printf`, so the order does not get mixed). Habits: `"..."` in a `&[u8]` position and `'a'` in a `u8` position are E0401 (the fix changes them to `b"..."`·`b'a'`. The earlier E0234 is retired). The standard library unit `std::bytes` (`lib/std/bytes.bmb`, written in BMB and proved, added by the compiler): `eq`·`starts_with` (the result is specified exactly), `find` (`Some(i)` is a real position), `extend` (down to the appended content), `push_u64`·`push_i64` (length and preservation of the prefix), `parse_u64` (`Some(v)` is the decimal value `dec` of the digits). Other units (T4, `lib/std/`): `std::utf8` (`valid_up_to`·`is_valid`, Unicode Table 3-7, the specification is `parses`, the concatenation of well-formed sequences, the loop is proved with the lemma `parses_extend` and `is_valid` with the determinism of the scan `parse_goes_on`), `std::crc32` (`checksum`·`update`·`update_with`: the result equals the bitwise definition `run`. For each byte it looks up one entry of zlib's 256-entry table `table()`, and that the table step equals the bit steps is the `by (bit_vector)` lemma `table_lemma`), `std::sha256` (`digest`: equals the digest `hashed` that writes the padding, schedule, rounds and constants of FIPS 180-4 as a specification. `ROTR` in the specification and the code is `rotate_right`), `std::base64` (`encode` equals the specification `enc_at`, is in normal form and reads back, `decode` accepts only the normal form and equals `dec_byte`, and `round` is `decode(encode(s)) == Some(s)`). Each unit is proved in full on its own (`libraries_are_proved`), and the programs of `tests/lib_run` call them by `std::` paths (no files are passed).
- Strings (ADR-0050): `String` (owned, a move type), `&str` (argument position), `char` (a Unicode scalar value). The literal `"..."` is `&str` and is written only in call argument and comparison operand positions (elsewhere E0409 with the fix `String::from("..")`), `'a'`·`'\u{1F600}'` are `char` (the escapes are Rust's `\n \r \t \\ \' \" \0 \xHH(up to 7f) \u{..}`, others E0101). The operations have Rust's names and signatures: `String::new()`·`with_capacity(n)`·`from(t)`·`from_utf8(v: Vec<u8>) -> Result<String, Vec<u8>>`, `s.push_str(t)`·`s.push(c)`·`s.clone()`, `len()`·`is_char_boundary(i)`, `as_str()`·`as_bytes()` (argument position, and the byte read `s.as_bytes()[i]`), `&s[a..b]` (`&str` argument position), `char::from_u32(x) -> Option<char>` (in specifications too), `u32::from(c)`, `c.len_utf8()`, the comparisons `==`·`<` and so on (byte-lexicographic order, `String`·`&String`·`&str` mixed, in specifications too), the built-in `print_str(s: &str)` (`io`). `Vec<String>` and `&[String]` are allowed, and `[String; N]` is not, as for `Vec`. Habits: `&s`·`s` in a `&str` position E0218 (towards `s.as_str()`); `t.to_string()`·`to_owned()`·`chars()`·`+`·`s[i]`·`char` arithmetic are E0404·E0401·E0407 with hints; `&mut str` E0402; a `String` parameter in a specification E0402 (towards `&str`). Proof (`verify/text.rs`): text is bytes (`Tables::lowered`, `String` is `Vec<u8>`·`&str` is `&[u8]`·`char` is `u32`), and the checker's `Tables::text` separates the operations whose meaning differs from the bytes (`push` of a `char`, comparison). `&s[a..b]` has the obligation that `a <= b` and both are character boundaries (E0820, Rust's `is_char_boundary`), and its value is `bmb_shift` (its axioms only in the queries that use it). That obligation assumes on its own the local facts of the UTF-8 invariant (`verify::text::utf8_window`): the four bytes before each end, for the text being sliced and for the texts the definition received (the checker's `Tables::text_sigs`: text parameters, call results, `&mut` texts after a call), and the end of a received text, without quantifiers. After an ASCII byte, after a whole character and before a leading byte are proved to be boundaries, and counterexamples are valid UTF-8 (`tests/verify/pass/utf8_facts`, `fail/utf8_facts`). `push(c)` gives the exact UTF-8 bytes for a constant, otherwise the exact length and the ASCII byte, and beyond that only the family of the bytes (leading byte, continuation byte); `push_str` gives a new array and a quantified definition; for both the maximum length is a fact (ADR-0124: beyond it `bmb_str_append` calls `abort`). A comparison is, in code, a new constant for the longest common prefix and the facts that define it, and in a specification a quantified expression. Whether `from_utf8` succeeds is not modelled (a new condition). The UTF-8 invariant is kept by construction (every way of making text is a built-in operation): it is neither an obligation nor a fact, so something like the boundary after an ASCII byte is proved only by checking with `is_char_boundary`. That the terms equal Rust's is `text_terms_are_rusts` of `tests/lemmas.rs`. Code generation (`codegen/text.rs`): `String` is a `Vec<u8>` header, `&str` is (pointer, length), `char` is an `i64` register. The runtime has appending (also of bytes that come from its own buffer: the offset before growing), UTF-8 encoding, the validation of Rust's `from_utf8` (rejecting overlong forms, surrogates and values above `0x10FFFF`), `memcmp` comparison, and a check then trap for unproved boundaries. Executable programs `tests/run/strings`·`escape` (same output as the Rust translations `*_ref.rs`, valgrind clean). Fuzzer `BMB_SOUND_ITERS=60 cargo test --test soundness_text`.
- Subslice arguments (within the second-class references rule ADR-0015): from an array, `Vec` or slice `v` of integer elements, `&v[lo..hi]` is passed as a `&[T]` argument (the same position as the `&s[a..b]` of text). The proof is the obligation that `lo <= hi` and `hi <= v.len()` (E0805, Rust's range panic) with the value `(bmb_shift elements lo)` and the length `hi - lo` (`verify::text::elem_slice`); code generation is, after a bounds check if not proved, (element pointer + `lo`, `hi - lo`) (`codegen::text::elem_slice`). It is read-only, so `&mut v[lo..hi]` is E0409 (hint: `&mut v` and the bounds), non-integer elements are E0409, and a different element type is E0401. Corpus `tests/verify/pass/subslices`·`fail/subslices` (counterexamples), `tests/check/err/subslices`, `print_bytes(&text[lo..hi])` of `tests/tools/fgrep.bmb`, mutation `v-subslice-end-unbounded`.
- System interface (ADR-0091): a closed list of built-ins, the paths and names of the Rust standard library, no FFI. The runtime is IR functions over libc (`codegen/sys.rs`) and only what is called enters the module (the signature types of a built-in also enter the type definitions, drop glue and SMT declarations only when it is called). Part (a): `std::process::exit(code: i32) -> !` (`io`, ends the process: libc `exit` flushes the standard streams and destructors do not run. The proof ends that path and requires no postcondition), `eprint_str(s: &str)` (`io`, standard error. It flushes standard output first, so the two streams interleave in call order), `std::env::args() -> Vec<String>` (`alloc, io, nondet`, the program name comes first. An argument that is not UTF-8 gives a message and exit code 101, like Rust's panic. In the proof only the type facts). `std::io::read_line(buf: &mut String) -> Result<usize, std::io::Error>` (`alloc, io, nondet`, appends the next line up to `\n`, `Ok(0)` at the end; a line that is not UTF-8 is rolled back from the buffer and gives `Err`), `std::io::read_to_end(buf: &mut Vec<u8>) -> Result<usize, std::io::Error>` (all the rest). Both use libc's buffered `stdin` and so can be mixed, and a closed standard input (`EBADF`) is an empty input, as in Rust. Part (b) files: `std::fs::read(path: &str) -> Result<Vec<u8>, std::io::Error>`, `std::fs::read_to_string(path: &str) -> Result<String, std::io::Error>` (`Err` if not UTF-8, code 0), these two are `alloc, io, nondet`; `std::fs::write(path: &str, data: &[u8]) -> Result<(), std::io::Error>` (`alloc, io`: creates or truncates and writes everything, mode 0o666 and umask). A NUL byte in the path gives `file name contained an unexpected NUL byte` (code 0), as in Rust. Reads and writes retry on `EINTR`. The `()` wrapped by `Ok(u)` creates no place. Part (c) directories: `std::fs::rename(from, to)`·`remove_file(path)`·`create_dir_all(path)` (Rust's algorithm: create, and on `ENOENT` start from the parent; a directory that already exists is a success) are `Result<(), std::io::Error>` (`alloc, io`), `std::fs::read_dir(path) -> Result<Vec<String>, std::io::Error>` (`alloc, io, nondet`, without `.`·`..` and sorted in byte order, a list of names instead of an iterator (ADR-0091 §2·§6), a name that is not UTF-8 is a UTF-8 error). An atomic write is `write` to a temporary file followed by `rename`. Part (d): `std::env::var(name: &str) -> Option<String>` (`alloc, io, nondet`, `None` if it is absent, not UTF-8, or the name has a NUL: `Option` instead of Rust's `Result`), `std::time::monotonic_ms() -> u64` (`io, nondet`, the milliseconds of `CLOCK_MONOTONIC`, the origin is arbitrary, not used in tool output: ADR-0091 §6). Part (e) processes: `std::process::run(prog: &str, args: &[String], input: &[u8]) -> Result<std::process::Output, std::io::Error>` (`alloc, io, nondet`, looked up in `PATH`; a `poll` loop that reads output and error while writing the input, so they do not block each other; `SIGPIPE` is ignored as in the Rust runtime, so for a child that stops reading early only the writing ends), the built-in struct `std::process::Output { status: i32, stdout: Vec<u8>, stderr: Vec<u8> }` (`status` is the exit code, or 128 + the signal if it ended by a signal). Interactive: `std::process::spawn(prog: &str, args: &[String], stderr: std::process::Stdio) -> Result<std::process::Child, std::io::Error>` (`alloc, io, nondet`, standard input and output are pipes, standard error is this process's with `Stdio::Inherit` and discarded with `Stdio::Null`: Rust's `Stdio::inherit()`·`Stdio::null()`) and the methods of `Child` (the method syntax of ADR-0051, the `impl` functions `std::process::Child::*` of a system type): `c.write_all(data: &[u8]) -> Result<(), std::io::Error>` (writes and flushes), `c.read_line(buf: &mut String) -> Result<usize, std::io::Error>` (one line of the child's output, the same rules as `std::io::read_line`: `Ok(0)` at the end, the buffer unchanged if not UTF-8), `c.id() -> u32`, `c.wait() -> Result<i32, std::io::Error>` (value receiver: closes both pipes, waits and gives the status). `Child` is a move type (no clone, the hint of E0413 on use after move), and if it leaves scope without `wait`, the drop closes both pipes and does not wait (Rust's `Drop`). The fields (`pid` and two `FILE`s) belong to the runtime, so making or reading them by hand is E0436. The pipes are close-on-exec, so a second child does not hold the input of the first child. `SIGPIPE`: every program ignores it from the start (the same as the Rust runtime) and a child starts with the default action (`posix_spawnattr_setsigdefault`, Rust's `Command`). Writing to a closed standard output (`print_*`, the flush of `eprint_str`, the flush at `exit` or at the end of `main`) ends with exit code 141 (stage0's `CLOSED_STDOUT`). Path queries and new files: `std::fs::metadata(path)` (follows links, `stat`)·`std::fs::symlink_metadata(path)` (does not follow, `lstat`) `-> Result<std::fs::Metadata, std::io::Error>`, the built-in struct `std::fs::Metadata { is_dir: bool, is_file: bool, is_symlink: bool, len: u64 }` (fields instead of Rust's methods, the same shape as `io::Error`), `std::fs::write_new(path, data: &[u8]) -> Result<(), std::io::Error>` (`File exists (os error 17)` if it already exists, does not follow a planted link: Rust's `File::create_new(path)?.write_all(data)`). Tests `metadata_and_new_files_are_rusts` (compared with Rust `std::fs`)·`children_inherit_or_drop_stderr_and_a_closed_stdout_ends_with_141`. Tests `a_program_talks_to_z3` of `tests/system.rs` (three queries in turn to the pinned Z3, sending the next after reading the answer)·`children_talk_through_pipes` (echo, end of output, drop, signal 137, `EPIPE` on writing to a finished child, `ENOENT` for a missing program; valgrind 0 leaks). Part (f) stack: a program with recursion (a recursive component of executable definitions) runs `main` on a thread with a 256MiB stack and waits for it (stage0's `STACK_BYTES`, only reserved and used when touched; on the process stack if the thread cannot be created). A program without recursion keeps the former `main` as it is. The built-in struct `std::io::Error { code: i32, message: String }`: `code` is the OS error number (0 for a UTF-8 error), `message` is the same bytes as Rust's `Display` (`strerror` + ` (os error N)`, or `stream did not contain valid UTF-8`). In the proof the buffer becomes any value of its type (length included) and the result is also any value of its type. The effect `nondet` (a value that can differ between runs, its sources are these built-ins) is a reason in `test_reasons` (ADR-0030 §4). Tests `tests/system.rs` (inputs are compared byte for byte with the same Rust program built with rustc). A loop that runs until the input ends cannot use `decreases`: for now, read everything and then walk the bytes, or put a limit on the number of lines.

## Diagnostics

Rules for diagnostic cascades: one defect is reported once, and a diagnostic that would disappear when that defect is fixed is not issued. A defect that would remain after the fix is issued in the same round. A trait impl whose header is rejected (E0235·E0420·E0312·E0311) stays in method lookup and bound judgement (`rejected_impls`), and its functions have their signatures collected and their bodies checked and are also compared with the trait (E0315·E0316) (an overlapping impl E0311 is not compared, and a second impl for the same type has the same function paths, so its bodies are not checked either). The Verus notation `#[verifier::external_body]` (E0216) is read as the BMB notation and checking continues, so the E1001·E0606 of that definition come out in the same round: they are defects that remain after the notation is fixed (`tests/check/err/verus_external_body.bmb`). The wording of the array element rule is the same for types and values (`array_elem_message`).

- One object per line: `code`, `severity` (a code starting with `W` is `warning`, the rest are `error`. Only `bmb lint` and `bmb weaken` issue `W` codes), `message`, `file`, `line`, `col`, `end_line`, `end_col`, an optional `fix` (`message`, and `replacement` if it can be fixed mechanically). E0811 (undecided) has the optional field `obligation`: the original code of the obligation the solver could not decide (`E0802` postcondition, `E0806`·`E0807` invariant entry and preservation, `E0810` assertion and so on). With `bmb verify --bounded-search` (and `bmb mcp --undecided-info`), an obligation that ended undecided is asked once more at 1/10 of the obligation limit, with input bounds (integers `|x| <= 8`, unspecified lengths `<= 4` and the integer elements below them) added to the same encoding (ADR-0108 §1, off by default; when on, a marker is put at the head of the query so the cache is kept separately). That model is also a model of the unbounded query, so on `sat` it issues the counterexample and "found by the search within .." under the obligation's own code (E0802 and so on), and on `unsat`, only when the assumptions without the goal and the bounds are satisfiable together (when there is an input within the bounds that reaches the obligation; that query writes only the definitions the assumptions reach, in the form of the satisfiability check), it puts `"bounded":{"b":8,"l":4}` on E0811 (no counterexample within these bounds, not a proof). In the `--emit-smt` script it remains as `; bounded search of obligation k`. `bmb mcp --undecided-info` also, when a proof fails and the diagnostic recommends `#[uses(..)]`, adds the search of `bmb uses` (4 re-verifications per definition, the workspace unchanged) to the `verify`·`write` responses as a `{"uses_search":ROW}` row (ADR-0108 §2). `bmb probe --def PATH [--loop K] --candidate EXPR..` (in MCP, the `probe` of `--probe-tool`, ADR-0109) proves only that function in a copy with the candidate invariants (at most 16) added to the K-th loop of one function, removes the candidates whose entry (E0806) or preservation (E0807) fails, is undecided or is not checked, and repeats (Houdini), and returns the largest set that is inductive together and whether the function is proved with it. A removed candidate shows only the side that failed in the round in which it was removed (a "holds" in a round where another candidate failed can be vacuous). Files are not changed.
- They are sorted by position and deduplicated. The same input gives the same bytes.
- `CODES` in `src/diag.rs` is the only list of codes. Numbers are not changed or reused.
- `bmb fix` applies every diagnostic that has a `replacement` and checks again, repeating until there is nothing to apply (at most 16 rounds, stopping when the same text comes up again). Within a round it goes in the order (file, start, end, code, text) and applies only those that do not overlap with ones already chosen (two insertions at the same position also overlap). The output is `{"round","file","line","col","code","replacement"}` for each fix applied (positions refer to the text before that round), the remaining diagnostics, and the summary row `{"summary":true,"rounds","applied","changed","remaining","ok","written"}` (`changed` is the files that would change, and whether they were actually written is `written`: `true` only with `--write`). If the program passes the check, the normal form fix W0907 for countable `while` (ADR-0057) is applied under the same rules too. The proof is not run. By default no file is changed, and `--write` writes only the changed files in place. Whitespace is not tidied, so follow with `bmb fmt` if the normal form is needed. If errors remain, the exit code is 1
- E02xx groups the Rust habits separately (type omission, macros, `return`, `as`, `?` and so on). The measurement of the Rust habit error rate (DESIGN.md §4.1) counts this category.

## Proof gate

- For each executable function, symbolic execution produces the proof obligations: overflow, division by zero, `i64::MIN % -1`, index range, call preconditions, postconditions, loop invariants (entry and preservation), `decreases` (loops, recursion, recursive `spec fn`), `assert`.
- A call proves the callee's `requires` and assumes only its `ensures`. The definition of a `spec fn` is unfolded only when it is in the proof context. The context is the union of the default context (ADR-0095 A1; the implementation is rule r2, which does not close over bodies: the `spec fn`s called by the definition's own contract, loop invariants, `assert`s and `proof` code and the `spec fn`s called by the callees' `requires`·`ensures`, without going into their bodies, `verify::default_contexts`, over the names the checker resolved) and the names written in `#[uses(..)]` (another unit's as `unit::name`, only additions, not transitive) (`verify::context_of`). The incremental key and `weaken` use the same context. A `#[uses]` entry that the default context already contains is W0916 (`bmb fix` removes it).
- The definition of an unfolded `spec fn` (ADR-0017 §4, ADR-0064): if it is not recursive, its body calls no other `spec fn` and it binds an array (a slice or `Vec` parameter), a macro of the same meaning; otherwise (and when a `:pattern` of that query contains that symbol), the quantified axiom `∀ args. range ⇒ f = body` (trigger `f(args)`). The macro is `(define-fun f (..) (ite range body (f!ext ..)))` (`Prog::axiom`, `macro_ext`). A symbol defined by a macro is not declared (`needed_decls`), and a definition comes after the macros it uses (`relevant_axioms`). This removes the cost of quantified definitions blocking Z3's model search in queries that have a counterexample (the minimal reproduction with an `(Array Int Float64)` parameter 382,936 → 1,397. The reasons for the narrowing are in the rationale of ADR-0064: nested macros grow terms multiplicatively, a macro in a trigger removes the trigger, and a macro for a scalar predicate harms nonlinear proofs).
- Probe (ADR-0067): a proof obligation that has scalar leaves first solves a query that writes all the leaves as macros, with rlimit `Z3_RLIMIT / 100` (`axioms_in_forms`, `PROBE_SHARE`. The probe of an advisory query has the same value: it is a share of the gate's limit, ADR-0131). On `unsat`·`sat` that answer is used (same meaning), otherwise the full query above is solved with the full limit. This removes the cost of counterexample queries running to the limit on quantified definitions, and leaves hard proofs to the present form (failure corpus rlimit −87%, V4 −6%, V8 −7%). In the script it comes just before the full query as `; probe of obligation k`. When the probe does not decide and there are quantified definitions, a ground instance retry is solved first at the probe's share (ADR-0089: `unsat` is a proof, `sat` when the instances are complete is a counterexample, otherwise on to the full query. Measured: failure corpus −30%, V4 +1.3%, V8 −4.6%, V10 +6.5%). In the script it is `; retry of obligation k with ground instances at the probe's share`, and the proof cache (`bmb proof cache v5`) records in two bits which retries ran, so a proof that comes from the cache emits the same script. The vacuity check (W0905) and the precondition satisfiability check (W0901) also solve a probe first (ADR-0069, `probe_base`: as measured, the verdicts are the same or more are decided and rlimit −17%·−24%). The probes of the two checks also write a non-recursive definition that is not a leaf as a macro when every definition it calls is a macro (ADR-0072, `Forms::SatProbe`: a definition that reaches recursion stays quantified. Measured: undecided 576 → 281·62 → 4, rlimit −39%·−86%, reports unchanged). When the probe does not decide and the query reaches recursive definitions, a query that writes all the definitions reached as one `define-funs-rec` is solved first at the probe's share (ADR-0133, `rec_base`: the body is the function body inside the type range and `!ext` outside, so it has the same meaning as the quantified definition and both `sat`·`unsat` are accepted. This is the case in which Z3's model search ended in `unknown` on quantified recursive definitions. Measured: undecided 216 → 86, rlimit −38%, reports unchanged). The queries of `bmb examples` do not use this form yet.
- Each obligation is solved in a clean solver state. Only `unsat` is success; `sat` is a counterexample; `unknown`, resource exhaustion and a missing solver are failures with their cause.
- Path facts: the facts obtained on one side of an `if` (and on the right of `&&`·`||`) remain as one `(=> c (and ..))` under that condition, and the implications inside it whose connective (`and`·`or`·`=>`) depth is 3 or more (the fact bundle of an inner `if`) are lifted to `(=> (and c g) x)` (`verify::guarded`, `LIFT_DEPTH`). When the bundles nested with each nested `if`, the `ctx-simplify` of Z3's preprocessing did work exponential in the depth (1,821,059 of the 1,843,925 of `utf8::width` → 26,298 for all its obligations). Shallow bundles (the auxiliary facts of division and so on) keep their text.
- A query declares only the `spec fn`s that its text (assumptions, goal, unfolded definitions, ground instances) mentions (`verify::needed_decls`). Adding or changing an unrelated `spec fn` leaves the query text of other definitions byte-for-byte the same. Measurement: over the whole corpus (`tests/**`, the m1·m1b seeds) the `verify` output is byte-for-byte the same as before (both verdicts and `rlimit`), and the `--emit-smt` scripts of the m1b seeds go from 1,987,446 → 746,728 bytes, the `spec fn` declarations from 21,294 → 707 lines.
- Query symbols have canonical names (ADR-0063, `smt::Canon`): the quoted symbols of the text sent to the solver (`|..|`: definitions, locals, callee results, selectors, constructors, datatypes) become `|$k|` in order of first appearance per query (per `(reset)`), and the solver's responses (models, errors, reasons for undecided) come back under the original names. Declarations and unfolded definitions are placed not in name order but in the order of first use in the query, and the locals of merges and loop heads in the order first bound. So the query text and the proof cache key (`cache.rs`, format v5: the key includes the query's memory limit, ADR-0129) of a program in which only the names of definitions and locals were changed are byte-for-byte the same. Counterexamples and diagnostics show names (in the expected output of the failure corpus only the `rlimit` values changed).
- One solver process serves several definitions. For each obligation it sends, after `(reset)`, the whole base including the options again, so the result is the same as with a freshly started process each time. A process more than 60 seconds past its start is started anew at the next definition, so that each definition gets the wall-clock safeguard (300 seconds) in full. The memory limit of a query is `Z3_MEMORY_MB` of `scripts/toolchain.env`: a query that reaches it is undecided (E0811, reason `memory limit reached`) (ADR-0123). Z3 counts memory per process and a process keeps a little for each query it answered (0.45MB after the 2,213 queries of `lib/std`), so undecided because of memory is judged only when that query reached the limit as the first query of a new process (ADR-0129, `smt::Solver::ask`). A process that serves several queries runs at half the limit (`smt::working_memory_mb`), and a query that ends there is asked again, alone, in a new process starting from `(reset)`. The query after one that ended at the limit is asked alone at once (only the cost differs, the answer is the same). So the memory verdict depends neither on what was asked before nor on the process reuse time limit (60 seconds). Even if a probe or a retry ends at a limit, the next query (the full query, the ground instance retry) is asked: a query ended by a limit (`rlimit`, memory) is treated as undecided, like `unknown` (`verify::undecided`). A query asked again alone is the first query of its new process, so when a later command of it ends that process at the limit it is undecided there and not asked a third time. The variables `BMB_Z3_RLIMIT`, `BMB_Z3_MEMORY_MB` and `BMB_Z3_BACKSTOP_MS` may lower the resource limit, the memory limit and the wall-clock safeguard for tests and never raise them: the least they give is 1, as Z3 reads 0 as no limit (`smt::lowered`), and a share of a lowered resource limit is at least 1 for the same reason (`verify::share_of`). The solver connection is ported (`selfhost/solver.bmb`, `selfhost/toolchain.bmb`) and compared with this one by two test programs that send the same scripts through both (`tests/port/smt_answers_ref.rs`, `tests/port/smt_answers.bmb`, the cases `smt-answers*` of `tests/port/README.md`); for them `Solver::ask` is public, `Solver::age` makes a process older in place of waiting for the reuse time limit, and `Solver::close` ends the process and gives its exit status.
- Among maps and queries, only those that carry proof results (L1 rows: `map L1`·`map all`·`surface`, and `status`) run the proof. The rest give the same result without the solver (`tests/no_prove.rs`).
- `surface DEF` proves only the one DEF (`verify::verify_only`). The status of a definition is determined by its own obligations alone (a query is built only from its own source text and the contracts and `#[uses]` of others, and the solver is reset for each obligation), so it is the same bytes as the L1 row of a full proof. The incremental keys too are computed only for what DEF reaches (`incremental::Session::new_for`), and the hashes of the cache file lines are checked only for the lines read (all of them when storing). `tests/mcp_cache.rs` compares with the `map L1` row for each definition with no cache, cold and warm. A failed definition also has the same number of failed obligations (it does not stop at the first failure as `verify_defs` does).
- Diagnostic codes E08xx. The last lines of `bmb verify` are `{"def":..,"status":"verified"|"failed","obligations":n,"failed":k}`.

## Filling in `#[uses]` automatically

`bmb uses [--write] [--cache DIR] <file.bmb|DIR>...` (`src/uses_fill.rs`). It runs only on request, and `check` and `verify` are unchanged.

- For each executable function that is not proved and each `proof fn` (ADR-0062: its proof reads `#[uses]` too, `a_lemma_gets_the_predicates_its_proof_needs`), the candidates = the current `#[uses]` entries ∪ the predicates that the `fix` of that definition's diagnostics reported as "seen by name only". If the candidates do not prove it, it adds the predicates that the newly unfolded bodies mention and tries again (at most 8 steps). Once it is proved, it removes the entries one at a time in sorted order and leaves an entry out if the definition is still proved. The result is a list that cannot be reduced further by removing a single entry (a global minimum is not guaranteed).
- On every attempt it rewrites the attribute text and checks and proves the whole program again. A definition's obligations depend only on its own `#[uses]` (unfolding is not transitive and a callee is seen only through its contract, ADR-0017 §4), so the failed definitions advance one step each, together, in a single verification. The verifications share the incremental cache (`incremental::Session::in_memory` and `rekey`), so a definition whose key has not changed since the previous verification is not encoded again, and the proof cache keeps the unchanged obligations of a changed definition from being solved again. With `--cache DIR` both caches are read from `DIR` and written back at the end (the same files as `verify --cache`). The result does not depend on the cache (`tests/uses_fill.rs`). There are at most 32 verifications per definition. At the end it puts in all the lists it found and verifies once more, and reverts the definitions that are not proved.
- Output (JSONL): for each definition that has a status line, `{"def","uses","status","verifications"}`. `status` is `proved` (proved by changing the list), `unchanged` (already proved) or `not_found` (not proved with any list built from the hints; the file is left as it is). A `proved` line carries the same position keys as a diagnostic (`file`,`line`,`col`,`end_line`,`end_col`) and `fix.replacement` (the text that replaces one attribute or is inserted before `fn`). The last line is `{"summary":true,"defs","proved","unchanged","not_found","verifications","changed","written"}` (`written` is the same as in `bmb fix`). If there is a `not_found`, the exit code is 1.
- Limits: it does not find predicates that the diagnostics do not name (those that appear in no obligation's query). The termination obligation of a `spec fn` does not read `#[uses]`, so if it fails the result is `not_found`.

## Contract-tuning lints

`bmb lint [--cache DIR] [--select CODES] <file.bmb|DIR>...` (DESIGN.md §8.2 "contract tuning", `src/lint.rs`). It runs only on request, and the output of `check` and `verify` is unchanged. The output is warning diagnostics (JSONL, `"severity":"warning"`) and a summary row (below). The exit code is 1 only when the program does not pass the check or the proof gate cannot run (E0812).

| Code | Reports | Method |
| --- | --- | --- |
| W0901 | The function's `requires` clauses cannot hold together. The function cannot be called and every proof about it is vacuous | One satisfiability query in the same encoding as the prover (parameter range facts, definitions unfolded by `#[uses]`, the clauses) (`verify::preconditions_satisfiable`). It reports only on `unsat` and does not report on `unknown`. Like a proof obligation, it solves the probe first (ADR-0069), and if the result is `unknown` because of quantified definitions it asks again with ground instances as the prover does (`unsat` is reported; a `sat` in which every application has an instance counts as satisfied, ADR-0075) |
| W0902 | One `requires` clause is not needed by the function's own proof | It removes that one clause from the syntax tree and proves only that definition again (`verify::verify_defs`). If it is fully proved, it reports. Removing a pre does not break callers, since they only have less to prove. Only functions proved in the baseline verification; W0901 functions and `#[external_body]` functions (the body is not proved) are excluded |
| W0903 | One `ensures` clause is used by no caller's proof | It removes that one clause and proves only the callers again (the `calls` edges of executable bodies, including the function itself if it is recursive). If all of them are fully proved, it reports. Only functions that have callers, all of them proved in the baseline verification |
| W0904 | The specification does not tell apart one change to the body: the mutated function is still proved. The message is `` `before` -> `after` `` | It changes one body node in the syntax tree and proves only that definition again. Mutations: `+`↔`-`, `<`↔`<=`, `>`↔`>=`, `==`↔`!=`, `/`↔`%`, `&&`↔`||`, `*`→`+`, `&`↔`\|`, `^`→`\|`, `<<`↔`>>`, index `a[i]`→`a[i + 1]` and `a[i - 1]` (two mutations), integer literal `c`→`c + 1` (when `c` is at most the `i64` maximum − 1, in the radix it was written in), flipping a `bool` literal, negating an `if` condition. Only executable code is changed (loop `invariant` and `decreases`, `assert`, `old` and `forall` are excluded). - Each clause is judged separately. It does not mean that two clauses reported separately can be removed together.
- Re-verification is expensive, so W0902 and W0903 each do at most 32 of them (`MAX_PRE_TRIALS`, `MAX_POST_TRIALS`). Clauses beyond that are skipped from the end of the order fixed by (path, clause order) and counted in `skipped` in the summary. An in-memory proof cache keeps obligations already proved at the same limit from being solved again (the cache key contains the memory limit: an obligation that the first verification proved at the gate's limit is still solved once more at the advisory limit in re-verification).
- The queries after the first verification (the satisfiability checks of W0901, W0905 and W0918, the re-verifications of W0902, W0903 and W0904) are advisory, so the memory limit of the solver process is `Z3_ADVISORY_MEMORY_MB` of `scripts/toolchain.env` (`smt::advisory`), and the `rlimit` of the full query is `Z3_ADVISORY_RLIMIT` (`smt::query_rlimit`, ADR-0131: `(set-option :rlimit …)` at the head of the query). Both are smaller than the gate's `Z3_MEMORY_MB` and `Z3_RLIMIT`. The probe's share (`Z3_RLIMIT / 100`) and the limit of reach points (1,000,000) are the same values as at the gate. The limit is a property of the asking side (`smt::Advisory`): the queries of `lint` are `Refutations` (every report requires `unsat`), and the queries of `bmb examples` are `Models` (they look for a model) and use the gate's `rlimit` as it is with the advisory memory limit (`tests/lint.rs` `examples_queries_keep_the_gates_rlimit`). The key of the proof cache contains the memory limit and the `rlimit` is inside the query text that is the key, so a proof that the gate put into `--cache DIR` does not answer an advisory query, and the `lint` output is the same with or without a cache (ADR-0129, `tests/lint.rs` `a_cached_gate_proof_does_not_answer_an_advisory_query`, `a_query_at_the_advisory_rlimit_is_undecided_with_and_without_a_cache`). A query that hits a limit is undecided, as at the gate, so a report can go missing but cannot appear: an undecided mutant is not counted as surviving, and an undecided satisfiability check is counted in `pre_undecided` and `reach_undecided`. The first verification runs at the gate's limits (the criterion for a verified function is the same as the gate's).
- At most 64 mutants (`MAX_MUTANTS`) are proved per run. The order takes one at a time from the functions in path order (round robin), and inside a function it is the pre-order traversal of the body. Mutants beyond that are counted in `mutants_skipped` in the summary. `mutants` in the summary is the number of mutants proved, `surviving` is the number of surviving mutants (the number of W0904), and mutant proofs are not counted in `verifications`.
- W0904 is informational. It does not judge whether a mutant is the same as the original body on every input (an equivalent mutant). Example: `x < 0` → `x <= 0` in `if x < 0 { 0 - x } else { x }` is equivalent because both arms are 0 at `x == 0`, and it is still reported. Mutants inside code that is dead under the preconditions are not filtered out either. A function without `ensures` is not mutated, because every mutant would survive.
- `*` is changed only to `+`. `+` is already changed to `-`, so one more mutation on the most common operator would take up the `MAX_MUTANTS` budget. Index mutants mostly die by the bounds proof, and that death is like any other. An index mutation belongs to an element index `a[i]`: a subslice `a[lo..hi]` has none (`(lo..hi) + 1` is not a program), and its bound expressions are mutation sites of their own (`tests/lint.rs` `a_subslice_has_no_index_shift`). `lint_ends_with_a_report_over_the_corpora` checks that `bmb lint` ends with exit code 0 or 1 and JSONL on every file of `tests/verify/pass` and `lib/std`.
- Measurement (`tests/run/search.bmb`): 9 of 48 mutants survived (7 of 33 with the earlier, smaller mutant set). Examples: `n / 10` → `n / 11` and `n % 10` → `n / 10` in `alg::digit_sum`, `(hi - lo) / 2` → `(hi - lo) / 3` in `alg::lower_bound_of`. The last one is a change the specification really does not need to tell apart, because the binary search stays correct. The 6 index mutants (`a[mid]`, `a[i]`, `a[best]`) all died.
- Cost: a restricted re-verification (`verify::verify_defs`) stops at the first failed obligation, because the lint asks only "is it fully proved". With `--cache DIR` the first full verification uses the incremental cache, and the proof cache is read from and written to `DIR/proofs`. Release-build CPU time (solver included, the earlier, smaller mutant set): `search.bmb` 11.7 s → 4.7 s (3.8 s with a warm `--cache`), the m1b seeds 40.3 s → 30.6 s (29.8 s with a warm `--cache`). The cost that remains on m1b is mostly the failing obligations of mutants that die (failures are not cached) and a few quantified queries, among the W0901 satisfiability queries, that run up to the `rlimit`.
- Determinism: fixed seed and `rlimit`; path, clause and mutant order. The same input gives the same bytes.
- Summary row: `{"summary":true,"defs","reports","verifications","skipped","mutants","surviving","mutants_skipped","pre_rlimit","pre_undecided","reach_rlimit","reach_undecided"}` (the three keys `mutants` and so on and the four cost keys were added later).
- Cost of the satisfiability checks (`verify::SatCost`): `pre_*` is the precondition satisfiability check of W0901, `reach_*` is the vacuity check of W0905, and `det_*` is the determinism check of W0918 (`null` if it does not run). `*_rlimit` is the sum of the `rlimit` of all queries that the check sent (probe, full query, ground-instance retry), and `*_undecided` is the number of functions (W0901) or reach points (W0905) that were not decided (including those the solver could not run on). Undecided results are not reported, so this number is the only trace they leave in the output. The two checks solve every function and point before filtering what is to be judged (W0905 only leaves out the reports of unproved functions and W0901 functions), so the cost also counts all of them. A check that did not run is `null`. With a fixed seed and `rlimit` it is deterministic and does not depend on the cache. V11 and V12 of `scripts/health.py` read it.
- Bit-vector queries of the vacuity check (`verify::bv_reach`, `subproof::bit_vector_sat`): if a reach-point query that the probe could not decide uses only range-asserted integers and bitvector and `bool` constants (no definitions, arrays or function symbols), a QF_BV query of the same model, made by the subproof translation, is solved first on the probe's share. A query that mixes linear integer arithmetic and `bv2nat` (the rotations and `^` of the SHA-256 functions) runs model finding up to the limit in integer form but is solved at once as bit vectors. A divisor that can be 0 becomes an assumption of the translation, so in that case only `sat` is accepted (`reach_queries_translate_to_bit_vectors`)
- `--select CODES` (comma-separated, W0901 to W0907, W0909, W0910, W1001 and W1002 of `lint::CODES`): runs only those checks (the `--select` of flake8 and ruff). A selected check reports the same things as in a full run. The first full verification runs only when W0902 to W0905, which judge proved functions, are selected, and the precondition satisfiability check runs only when W0901 or W0902, W0904 or W0905, which leave out the functions it finds unsatisfiable, are selected (`pre_*` appears then too). The count of a check that is not selected is 0. An unknown code gives exit code 2. To look at cost only, use `--select W0901,W0905` (it skips the re-verifications and mutants of W0902 to W0904).
- Limits: W0903 looks only at the callers in the current program (a post meant for use as a public API can be reported too, so it is informational). Functions that failed in the baseline verification, or whose callers failed, are not judged.
- `bmb mutate --def PATH [--def PATH].. <file.bmb>..` (`lint::mutate_sources`): for each of the same mutation sites as W0904 (in the same order) it makes a program with one mutation applied. There is no cap and no proof. A row is `{"def","site","line","col","before","after","unit","text"}` (`text` is the normal form of the changed top-level unit; other units are unchanged) and the last line is `{"summary":true,"mutants"}`. A path that is not an executable function, or a check error, gives exit code 1. The mutant generator of the spec-strength benchmark BSB uses it (in the `bmb-bench` repository (https://github.com/lang-bmb/bmb-bench)).

## Examples of a contract (`bmb examples`)

`bmb examples [--count N] DEF.. -- <file.bmb>..` (`verify::examples`, `src/verify/examples.rs`) makes examples to show to a reviewer who reads the specification, from the `requires` and `ensures` of an executable function alone (it does not read the body; the program is only checked, not proved) (ADR-0078 H-INTENT).

- **Rows (JSONL):** `{"def","kind","input":{parameter: value},"result":value,"after":{parameter: value}}`. `kind` is `allowed` (the input satisfies `requires` and the result satisfies `ensures`), `rejected` (the input satisfies `requires` and the result violates `ensures`) or `excluded` (a value of the parameter types that `requires` refuses; no `result`). `result` is absent if the result is `()`, and `after` is the value afterwards, present only when there is a `&mut` parameter. Values are strings in the same notation as counterexamples (one function, `verify::model_values`, prints the counterexamples of diagnostics, W0918 and the examples): `-5`, `true`, `[1, 2] (len 2)`, `Point { x: 1, y: true }`.
- **Order:** definitions in argument order. For each definition, over N inputs (default 3, 1 to 64), in turn ① an `allowed`, ② one more `allowed` line if another result is also allowed for the same input (evidence that the specification does not fix the result for that input; the question of W0918 asked of one input), ③ a `rejected` for the same input. After that, if there are fewer than N `rejected`, a `rejected` at inputs different from the earlier ones, then at most N `excluded` (when there is a `requires`), and last the summary `{"def","summary":true,"allowed","rejected","excluded","undecided","rlimit","max_len":4}` (row counts, the number of queries not decided, the sum of the `rlimit` of all queries sent).
- **Queries:** the entry state is made by the same functions as for the gate, W0901 and W0918 (`Enc::entry_params`, `Enc::entry_requires`: the range and type invariants of the parameters). A spec fn that the contract calls, and whatever its definition calls, is read by its definition whether or not it is in the function's `#[uses]` (ADR-0134: `#[uses]` is what the proof sees, and the meaning of a contract is the definitions). The verdict comes from the `verify::sat_of` of W0901 and W0918 (probe, the form that writes recursive definitions as recursive functions (ADR-0133), full query, ground-instance retry), with a fixed seed, the gate's `rlimit` and the advisory memory limit (`Advisory::Models` of `smt::advisory`: an example is a model of a `sat`, so it does not use the advisory `rlimit` of `lint`, ADR-0131). The value behind a `&mut` afterwards follows the same rule as at a call site (`Enc::behind_mut_after`: the length of a slice stays). The next input is obtained with clauses that block the values of the earlier inputs. A `rejected` fixes the input and asks `¬ensures`.
- **Small values first:** each query is first asked with the bounds of bounded search added (`verify::bound_terms`, ADR-0108: integers `|x| <= 8`), and if there is no model or it is undecided, it is asked without the bounds. Inside those bounds, the n-th input (from 0) is first asked with every input length at least n, and an `allowed` with a `bool` result is first asked for `true` if n is even and `false` if n is odd (inside the bounds, then outside). A length is always at most 4 (counterexample output shows only up to 4 elements in full; `max_len`). So a contract that is satisfied only at length 5 or more has no rows.
- **When the model gives no value:** if the solver returns an expression for a `bool` value (a result said to equal a quantified predicate), it asks again with that term added as true, and if that does not work, as false. If an integer value is not a literal, that query is undecided.
- **Written-in inputs (ADR-0134):** if the solver cannot decide a query whose input is not bound, it writes in an input and asks again, up to 8 times (`examples::written`): the n-th one takes the lengths 1, 2, 3, 0, 4 in turn, integers come in the fixed order `2, 3, 1, 0, 5, 4, 7, -1, 6, -2, 8, -3`, and a scalar array is one array value (a chain of `store`). The solver only looks for an output at the given input, so quantified formulas over a whole array and recursive predicates are decided. An input outside the types or `requires` is `unsat`, so it moves on to the next one. Over the 90 items of the intent benchmark (in the `bmb-bench` repository (https://github.com/lang-bmb/bmb-bench)), items with no `allowed` row went 12 → 0, and over the 94 functions with contracts in `lib/std`, those that produce rows went 34 → 52.
- **Undecided:** a query that ends in `unknown` or at a limit produces no row and is counted in `undecided` (the enumeration of that kind ends there). A value that is not from a model is not printed. Contracts that have no solution even with written-in inputs fall here (example: nonlinear integer equations).
- **Definitions without examples:** only a `reason` is given in the summary row (no queries). Types whose values are not shown in full (supported: integers, `bool`, structs of those, arrays, slices and `Vec` of those or of those structs, with fixed lengths at most 4; other enums, `Option`, `f64`, text, type parameters and recursive structs are not supported), contracts that go through a spec fn for which no definition can be given, and contracts that use `f64` operations.
- **Determinism:** the same files give the same bytes (no cache is used). Exit code: 0; 1 for a path that is not an executable function or a check error; 2 for a usage error.
- **Tests (`tests/examples.rs`, through the CLI only):** `shown_examples_hold_at_the_gate` confirms by a different route from the generator's queries: it builds a function that binds the values of a row as literals and uses `assert` on the claim (`allowed` is pre and post, `rejected` is pre and `!post`, `excluded` is `!pre`), and checks that `bmb verify` proves it (9 definitions: sortedness, upper-bound and range predicates over slices, structs, `&mut`, a recursive sum under a quantified `requires`). `the_gate_refuses_an_exchanged_claim` (if the claim is exchanged it is not proved), `rows_and_summary_have_the_documented_shape`, `the_output_is_the_same_bytes_every_run`, `a_contract_that_fixes_the_result_has_one_allowed_row_per_input`, `a_weak_contract_shows_two_allowed_results_for_one_input`, `slice_inputs_grow_with_the_row`, `an_undecided_query_shows_nothing_and_is_counted`, `a_definition_without_examples_says_why`, `errors`.

## Detecting specification weakening (`bmb weaken`)

`bmb weaken OLD NEW` (each a file or a workspace, `src/weaken.rs`). It judges by SMT implication whether the contract of a definition was weakened between two editions (`requires` strengthened, `ensures` weakened, `pure` to `io`). The gate-bypass audit (H-GAME) and the refinement verdict of the commutation relation use it. It runs only on request, and `check` and `verify` are unchanged.

- **Targets and pairing:** executable functions and `proof fn` (free functions, `impl T` functions). It pairs by path first, then the rest by `id` (ADR-0059: renames and moves only), and then by the `id` of the program with every `requires`, `ensures` and `#[uses]` deleted (body identity). The contract is part of the `id`, so a rename and a weakening done in one edit change the `id`. That is why the third step catches it (`match`: `path`, `id`, `body`). Pairing by hash is done only when that hash occurs exactly once on each side. Without a pair the row is `added` or `removed`. Functions of a trait `impl` and default bodies are not targets, because the gate proves the refinement of the trait contract (E0817).
- **Verdict:** old contract (R0, E0), new contract (R1, E1). The forward direction is the same as the prover's trait refinement obligation (`Enc::refines`, ADR-0046 §4): each clause of R0 ⇒ R1, each clause of R0 ∧ E1 ⇒ E0 (over the parameters, the result, and the new values behind `&mut` parameters). The backward direction: each clause of R1 ⇒ R0, each clause of R0 ∧ E0 ⇒ E1 (compared on the old domain, `RefineJob::own_domain`). `verdict` is `weakened` (one forward clause is refuted, or `pure` becomes `io`), `undecided` (no refutation and there is a forward clause that could not be decided, G1: do not guess), `same` (all four directions proved, same effects), `refined` (forward proved, one backward clause refuted or `io` becomes `pure`), `compatible` (forward proved, backward not decided), `signature` (the parameters, result or type parameters differ; types are compared by `id`, so a type that was only renamed is the same), `added`, `removed`. A pair whose `id` is the same and whose contracts call the same names (the path-qualified surfaces are the same apart from names and `#[uses]`), and a pair with no contract on either side, are `same` without a query (only the effects are compared). The `id` alone is not enough: an `id` has no names, so two `spec fn` with the same body (`pos`, `gt0`) have one `id`, but a proof that does not unfold that predicate sees them as two symbols (`quarter` in `tests/weaken/readers`; before the fix it was `same`).
- **What the solver sees:** the `spec fn` that the `#[uses]` of each edition unfolds (the same as an ordinary proof), and every `spec fn` reached from the two contracts by following unfolded bodies whose `id` changed between the editions. So a contract that calls a `spec fn` with the same name and a changed body is compared by the two bodies, not by the name (`tests/weaken/spec`). An unchanged `spec fn` is the same function in both editions, and if neither side unfolds it, it is seen by name only. In that case a counterexample interprets that predicate freely, so `opaque` in the row names it (`tests/weaken/opaque`: a `requires` rewritten with a predicate that is not unfolded breaks the proofs of callers that see it by name only, so it is reported as a weakening). Fixed `rlimit`, no time limit, seed 0, a solver reset for each obligation, and the ground-instance retry (DESIGN.md §8.2).
- **As one program:** the two editions are put into one query. The old units go in under a new name (`old_u`), and an old definition, type or trait whose `id` also exists in the new edition is shared with that one (references are rewritten to the new one, the reference traversal of `src/refs.rs`; the same traversal as the transaction `rename`). So an unchanged type is the same sort and an unchanged `spec fn` is the same function. If there are several new items with the same `id` (two structs with the same fields), sharing is only with the one at the same path, and a trait and its `impl` functions are shared only at the same path. A changed `impl` function of a shared type becomes the function `T__f` of the old unit (`Self` is `T`, the receiver is `this`). An old definition to be compared always keeps its own copy (the backward comparison runs on that copy). Whatever references an item that is not shared is not shared. The merged program must pass the check and the `id` of every old item must be unchanged (the sort audit, `audit`). Otherwise the definitions to be compared are `undecided`, with that reason.
- **Output (JSONL):** for each definition, `{"def","old","match","verdict","requires","ensures","effects","lost","gained","undecided","why"}` (in path order; keys that do not apply are `null`). `requires`, `ensures` and `effects` are the relation of the new edition to the old one: `same`, `weaker`, `stronger`, `incomparable`, `undecided` (a relation is written only when both directions are decided). `lost` (what the old contract promised and the new contract does not: a forward refutation) and `gained` (a backward refutation) are `{"clause","counterexample","opaque"}`, and a clause is written with its edition (`new requires pos(x)`, `old ensures is_succ(x, r)`, `effects pure`). A counterexample is the inputs and the result (if the result is `()`, the value of the first `&mut` parameter after the call, `a after`). `undecided` is `{"clause","why"}`. Then, for each weakening, a warning W0908 on that clause of the new edition (for `ensures` the whole new `ensures`, for an effect its name), and last `{"summary":true,"defs","same","refined","compatible","weakened","undecided","signature","added","removed","queries"}`. If there is a weakening or an undecided row the exit code is 1; if an edition does not pass the check, its diagnostics and 1.
- **`proof fn`:** removing an `ensures` clause that follows from `requires` through an unfolded `spec fn` gives the same proposition (`below_more` in `tests/weaken/shapes`). The weakening of a lemma shows up as a strengthened `requires`.
- **Measurement:** the corpus `tests/weaken/` (8 pairs, 32 definitions, `tests/weaken.rs`). The 233 body mutants (`bmb mutate`) of 88 real programs give 1,472 rows (350 solver obligations), all `same` (in the course of this, a defect that did not share two structs with the same `id` and traits was fixed, test `body_mutants_of_real_programs_are_the_same`).
- **Comparison from the reader's side (`bmb weaken --readers FILE OLD NEW`, ADR-0065 §3):** each line of `FILE` is `{"def","uses"}` (a definition and the `#[uses]` of a proof that reads its contract, full paths). It gives one row per line, in that order. The two editions being compared unfold only the `spec fn` that the reader unfolds, instead of their own `#[uses]` (that path in the new edition, the same path in the old edition). The rest is seen by name only. This is because a refinement that holds only through the definition's own `#[uses]` is not a refinement for a caller that does not unfold that predicate (a soundness condition, `tests/weaken/readers`: only the callers whose reader row is not `weakened` are proved in the new edition). Only the forward direction is asked (what the reader needs). So a proved comparison is `compatible` (`same` if the contracts are the same). A row also has `uses` and `revealed` (the unfolded predicates reached from the two contracts by following unfolded bodies: the answer relies on those bodies), and there is no W0908 line. A definition has a single `#[uses]` list, so other readers of the same definition are asked in the `contract_refinements` of the next round. A `spec fn` whose body changed between the two editions and which the reader does not unfold stays a different symbol in the two editions (conservative).
- **Limits:** an old specification that calls a changed `impl` function of a shared type with method syntax (`x.f()`) resolves to the new function, and the sort audit turns it into `undecided`. A type whose generic `impl` has a changed function is not shared (a definition that uses that type in its signature is `undecided`). Old code that uses a renamed field or variant does not fit the shared type, so the check fails and it is `undecided`.

## Identity and names (ADR-0059)

`bmb hash` gives a row `{"def","id","body","iface"}` for each definition (function, `spec fn`, `impl` function, trait default body) and each type declaration. The L1 rows of the map (types and traits included) add `id` after `iface`. All three are the SHA-256 of a nameless normal form (`fmt::Printer::identity`, `src/identity.rs`).

- Another definition is written by its `id` (`#<hex>`), and a trait method or enum variant as `#<id>#k`. Binding names (parameters, result names, locals, labels, type parameters, `forall` and `exists` variables, pattern names) are positions in binding order (`_0`, `_1`, ..), and fields and variants are declaration positions. Attributes, effects, contracts, `decreases` and triggers stay as they are, the targets of `#[uses]` are written by `id`, and unit summaries are not included. Built-ins (`Vec`, `Option`, `std::mem::replace`, the integer types) keep their names. A type argument is written by the position of its segment counted from the end of the path.
- Nominal types: two types with the same structure still dispatch trait calls differently, so the text of a type contains the trait `impl`s of that type, and the text of a trait contains every `impl` (`impl #trait for <type> { #trait#k = #fn, .. }`). A trait, its `impl` functions and the implementing types form one recursive component.
- Recursive components (the strongly connected components of the reference graph, functions, types and traits together): a member is written as `#self.k`. The order starts from the hash of the text with the component erased, then repeatedly hashes again the text in which the other members are written by their previous hashes, until the partition splits no further (colour refinement), and only the remaining ties are settled by path. The component hash is the hash of the member hashes joined in that order, the `id` of a member is `<component>.k`, and a component of one is its own hash. The order of trait methods is settled by the hashes of the method text and of the `impl` functions that define that method, and the remaining ties by name (two methods whose signature, contract and implementations are all the same).
- `body` is the hash of the definition's own text (members of the same component as `#self.k`), and `iface` is that without the body (for a `spec fn` it is `body`). If the `id` of a referenced definition changes, the `id` and `body` of the referrer change too (content addressing). If the body of a `spec fn` that a contract calls changes, `iface` changes too.
- The `changed` of a commit is the definitions whose own text changed (the qualified hash, which writes other definitions by path, `fmt::qualified_hashes`). A body edit reports only that definition. `impact` answers the transitive effect.
- Transaction `rename` (`{"op":"rename","def":"a::f","to":"g"}`, `workspace::rename`): rewrites the declaration of a function, `spec fn`, `impl` function, type or trait and every reference to it (calls by short name and by full path, types, struct literals, variants, patterns, `#[uses]`, bounds, `impl` heads). It is used only on a program that passes the check. After the change the multiset of all `id`s must be unchanged: if the new name captures another reference (as when it shadows the built-in `print_i64` with the same signature), it refuses and names that definition. If it collides with a name in the same unit, the check refuses it (E0302). It also takes units (`workspace::rename_unit`): if `def` is a unit path it rewrites the name of the `mod` and every path written through that unit (the file name follows too), and does the same identity comparison. An existing unit name is refused (`tests/workspace.rs` `rename_of_a_unit_rewrites_every_path_through_it`). It also takes trait methods (`def` is the method path of the trait, `unit::Trait::m`): it rewrites the declaration, the functions of every `impl` of that trait in whatever unit, and path calls and method calls (`refs::Decl::TraitFn`, `TraitImplFn`). If the function path of an `impl` (`<T as Trait>::m`) is given it refuses: changing it separately would disagree with the trait (`rename_of_a_trait_method_reaches_every_impl_and_call`).
- Transaction `move` (`{"op":"move","def":"a::f","to":"b"}`, `workspace::move_def`): moves a function or `spec fn` of a unit to an existing unit `to`. The places where the moved function called functions, types or traits of the old unit by short name become full paths, and the references that pointed at that function (full paths, short names inside the old unit) become the new full path. The identity comparison is the same as for `rename`. Types, traits and `impl` functions are not accepted, and a missing unit or a name that already exists in that unit is refused (`move_of_a_function_keeps_every_identity`). It is in `bmb apply` only and not in MCP.
- Transaction `expect` (`{"op":"expect","def":"a::g","id":"sha256:.."}`): if the `id` of that definition differs in the workspace the transaction started from, the whole commit is refused (optimistic concurrency). Renaming another definition does not change the `id`, so it is not a conflict. A body edit of a callee changes the caller's `id`, so it is a conflict (`tests/workspace.rs`).
- MCP: present only with `bmb mcp --rename-ops`. The tool list of the frozen task set is unchanged (ADR-0021, `frozen_tool_lists_keep_their_bytes`). They are the transaction tools `tx_rename` (`tx`, `def`, `to`) and `tx_expect` (`tx`, `def`, `id`), and the lists `rename` (`[{"def","to"}]`) and `expect` (`[{"def","id"}]`) of `write`. `write` builds one transaction in the order `expect`, `rename`, items (`summary`, `code`, `remove`), and a write that only renames does not need `unit`. The proof after the commit is the same as for other writes. Tests: `tests/mcp.rs` `rename_and_expect_on_request` (declaration and references, `id` unchanged, refusal of a mismatched `expect` and of a colliding name, the transaction path), `tests/mcp_fuzz.rs` (random sessions containing the two operations: valid and invalid names and identities, renaming a definition that was just added).
- Readability: with `id` removed and the hash values masked, the map output is byte for byte the same as the previous compiler's output (85 corpus files).

## Incremental build

`--cache DIR` (`.bmb-cache/` for MCP) keeps per-definition results (`DIR/defs`) next to the proof cache (`DIR/proofs`) (ADR-0032, `src/incremental.rs`). A definition whose key is unchanged gets neither the symbolic-execution encoding nor IR generation. The output (diagnostics, status lines, IR, map) is the same bytes with or without a cache, cold or warm (`tests/incremental.rs`).

- Proof key: the Z3 version, the memory limit, the query head (options, `rlimit`, prelude), the qualified normal form of the definition (`T::f` calls by full path; not the source text: see node positions below), the contract hashes of the executable functions it calls, the body hashes of the `spec fn` it unfolds or that are in the same recursive component, the members of the recursive component, and, for each `spec fn` reached from the definition's text by following callee contracts and `spec fn` texts, its SMT declaration (ADR-0033), and the declarations of the data types that those texts use by name and of their field and payload types. It includes all the edges of the `impact` query (`calls`, `uses`, `names`), and the declarations are taken wider than that (as far as the `spec fn` that callee contracts call).
- IR key: the source text of the definition (the positions of runtime checks) and its qualified normal form, the caller hashes of the executable functions it calls, and the proved obligations that can be used inside that definition (a call component with a failure keeps its checks, so the IR of that component is generated again).
- Only fully proved definitions store their proof result. Failures always run again. The obligations of a reused definition are counted as proof-cache hits.
- Each line of the file carries a SHA-256, and a line that does not match, a different format version, or a file from a different compiler is ignored and rebuilt. The compiler is named by the file's second line, `id VERSION+DIGEST` (a SHA-256 that `build.rs` makes from `src/**`, `toolchain.env` and the standard library), and not by the keys: a file of another build is not read at all, so no entry meets another compiler, and two builds that compute the same keys write the same lines below it (`entries_do_not_depend_on_the_compiler_identity` in `src/incremental.rs`).
- `bmb verify --emit-smt` needs every script, so it turns reuse off (the proof cache is still used).
- Adding or removing a `spec fn` does not re-encode definitions that do not reach it (`adding_an_unrelated_spec_fn_reencodes_nothing` in `tests/incremental.rs`: the scripts are byte for byte the same too). A signature change re-encodes only the definitions that reach that declaration.
- Proved obligations are stored not by byte offset but by the position of the syntax node in the definition (`incremental::node_spans`: name, parameters, result, contract, body, depth first), and on a hit they are moved to the positions in the current source text (ADR-0059 §4). So changes of whitespace, comments and layout inside a definition do not re-encode (`layout_inside_a_definition_reencodes_nothing`, audit included). A path is one node whatever its length, so a definition that reuses another's entry of the same key (the same text calling `f` inside unit `u` and `u::f` from another unit) gets its proofs on its own nodes (`a_twin_with_paths_of_another_length_keeps_its_proofs`). The IR is generated again (the IR key holds the source text). The file format is `bmb incremental cache v3`.
- Names (ADR-0063 §4): the proof key contains no names. The key is the nameless text of the definition (the printing of `identity::Ids`: bound variables are positions, fields and variants are declaration positions, built-ins are names) and, for each item it reaches, a number inside the key (`@k`, in order of first reference) and the nameless text of what the query reads from that item (`incremental::nameless_reads`: for executable and proof callees the caller surface, for the `spec fn` of `#[uses]`, of the recursive component and of type invariants the body, for other `spec fn` the declaration, for types the declaration, for trait methods the declaration and the functions that define it). The rows above write what this key reads, by name. A definition that was only renamed has the same key, and the store is also looked up by key, not by path, so it uses the result that the old name stored (two definitions that differ only in name also use one result: without the names the read set is the same, so the verdict is the same). The script digest that is stored is that of the canonical text the solver receives. Over 502 renames, re-encodings, proof-cache misses and audit mismatches are all 0. Tests: `a_rename_reencodes_nothing` (audit included), `nameless_keys_tell_apart_what_queries_read` (pairs that differ only in name have the same key; pairs that differ in a predicate of a callee contract, the same callee twice, a different field, an unfolded body or a field type have different keys; a body that is not unfolded changes nothing).
- An executable function that is called enters the key by its caller hash: the contract hash without `#[uses]` (`fmt::caller_text`, ADR-0043). `#[uses]` unfolds bodies only in that function's own queries, so if only the `#[uses]` of a callee changes, only that function is re-encoded (`verify_stats_name_the_reencoded_definitions`; for audit mode `edits_that_shift_spans_or_change_context_keep_outputs_exact`). The `iface` of `bmb hash` and of the map is unchanged (it contains the target `id`s of `#[uses]`).
- `bmb reads <file.bmb|DIR>..` (ADR-0065 §2): gives the proof key of each definition as rows. It is the read set of the proof. `{"def","kind","key","contract","decl","uses","reads":[{"kind","path","digest"},..]}`. The kinds of rows are `self` (the qualified normal form), `component`, `callee` (the caller hash of the callee), `spec` (the text of an unfolded `spec fn`), `names` (a `spec fn` seen by name only, no hash), `decl` (SMT declaration), `type`, `invariant`. `contract` and `decl` are the values that the keys of other definitions take from this definition. At the end, `{"type","digest"}` for each type. The rows are recorded by the same code that builds the keys (`incremental::Session::keys`), so if the rows are the same the keys are the same. The converse breaks only for renames: the key contains no names. A warm `verify --stats` re-encodes only the executable definitions whose rows changed (`tests/reads.rs`). The commutation judging harness uses it.
- `--stats FILE` (`verify`, `emit-llvm`, `build`) writes what the cache did as one line of JSON: `{"encoded":[..],"reused":[..],"lowered":[..],"ir_reused":[..],"proof_cache_hits","proof_cache_misses","audit_mismatches":[..],"damaged"}` (definition paths are sorted, for `verify` the IR lists are empty, `damaged` is the number of damaged cache lines that were ignored), and `emit-llvm` and `build` add `"runtime_checks"` at the end (the number of runtime checks left in the IR because they were not proved). Standard output is unchanged. `verify --audit` proves the definitions that the cache would reuse anyway, compares them with the stored result (canonical script digest, status, proved obligations) and writes the definitions that differ into `audit_mismatches` (the output is what was proved again). `emit-llvm --audit` and `build --audit` also lower again the IR that would be reused and compare it. BCB measures the re-proof set per commit.

## Editing surfaces (ADR-0073)

Two write surfaces for the H-EDIT and H-GRAIN measurement edition (the edit sets of the `bmb-bench` repository (https://github.com/lang-bmb/bmb-bench)). In both, as with `write`, one call commits and proves the whole workspace, and the commit follows the same rules as a transaction (on a structural or type error the whole is refused and nothing is written). The resulting files are stored in normal form (`workspace::plan_files`: the whole new file is checked, and `src/UNIT.bmb` must contain exactly one top-level unit `UNIT`).

- **File diff** (`--file-tools`, `src/udiff.rs`): the rules of `git apply --recount`. The line counts of a hunk are not trusted but counted again. The line number in the head is the first place to look; if it matches in several places, the one closest to that number is taken, and if there is no number it must match in exactly one place. Context and deletion lines must match exactly, whitespace included (no fuzz). If it does not match, it says which line is missing (and says so if only whitespace differs). `--- /dev/null` is a new file, `+++ /dev/null` is a deletion, and a file that was emptied is also a deletion. A line without a prefix inside a hunk is an error (it does not silently drop the hunks after it). In the commit result, files whose text as written by the normal form differs are reported as `reformatted`.
- **JSON AST** (`--ast-tools`, `src/ast_json.rs`): the document is an object whose keys are the top-level unit names. A unit has `summary`, the name-keyed `units`, `types`, `traits`, `impls` (type name) and `fns`, and the array `trait_impls`. Other nodes use `kind` and the field names of `ast.rs`. Names, paths (`a::b`) and operators are strings; empty lists, `false` and absent parts are omitted; there are no positions. What the normal form discards (function attributes other than `effects` and `uses`, unit attributes other than `summary`) and the parser's recovery forms (`use`, a `let` without a type, a destructuring `let`, `..base`, a wildcard arm) are not represented. `edit_ast` applies an RFC 6902 JSON Patch (atomic) to the document, reads the tree as a program, prints it in normal form and parses it again to confirm that it is the same tree (this blocks text injection such as a keyword in a name position). If it differs, it returns the pointer of the first place that differs and the shape as parsed again (example: an `if` statement at the end of a block becomes the block's value `tail`). The positions in diagnostics and proof results are replaced by `at`, the pointer of the innermost node that contains the position (for `verify` too, on this surface). If `patch` arrives as JSON text, it is parsed and used.
- Without the flags, `tools/list` and every response are the same bytes as before (frozen set, ADR-0021). The whole corpus round-trips through the tree (`tests/ast_json.rs`: `bmb ast` → write into an empty workspace with `edit_ast` → the same normal form and the same tree).

## The front-end cache of the MCP server

`bmb mcp` keeps front-end results in memory between calls (`FrontCache` in `src/lib.rs`). On every call `src/*.bmb` is read again (other writers and direct edits are seen too). A file whose name, position and source text are the same as in the last call is not lexed and parsed again, and its syntax tree and diagnostics are reused (spans contain file positions, so a file whose position changed is parsed again). If anything changed, the checker runs again over the whole program (the tables are global). The map index (`map::Index`: units, definitions, edges, reverse edges) is rebuilt at the first map request after a change, and definition hashes are computed on first use. If nothing changed, everything is reused. A definition-level query does only range lookups in the index (outgoing edges are an interval of the sorted edge set, incoming edges are the reverse-edge table). The responses are the same bytes as if a new server were started for every call (`tests/mcp_cache.rs`: sessions that mix queries, maps, `verify`, `build` and commits, commits by another server, direct edits, syntax errors, and shifts of file positions). The measurement is among the m3 results of the `bmb-bench` repository (https://github.com/lang-bmb/bmb-bench) (the front-cache report of 2026-10-24).

## Code generation

- Proved obligations are passed to LLVM as facts, without checks: no overflow → `nsw`/`nuw`, in range → an unchecked `getelementptr inbounds`, nonzero divisor → an unchecked `sdiv`/`udiv`. Each such line carries a `; proved Exxxx` comment.
- Unproved obligations remain as checks that go to a trap (`; unproved: ..`). The trap (`@bmb_trap`) flushes standard output and then is `llvm.trap`, so, as with a Rust panic, what was printed before remains. `bmb build` refuses such programs.
- A `&mut` slice parameter is `noalias`, and a `&` slice is `readonly` (ADR-0015).
- Closed world: one module is the whole program, so every function (the BMB `main`, `bmb_print_i64` and `bmb_print_u64` included) is `internal`, and only the C entry point `@main` is visible outside. LLVM inlines freely and deletes unused functions. In the 7 baseline benches the executables went to 0 BMB function symbols (2 to 4 before) and shrank by 100 to 180 bytes. The difference in run time was inside the measurement noise (±10%).

## Added queries

These queries were added besides the 7 queries of ADR-0020 §5. The existing queries and row formats are not changed.

| Query | Result |
| --- | --- |
| `impact DEF [body\|iface]` | A row `{"path","reason"}` for each definition to prove again if the body (`body`) or the contract and signature (`iface`, the default) of DEF is changed, and a summary row `{"summary":true,"changed","change","reprove","defs"}`. `reason`: `changed` (itself), `calls` (a caller: the contract changed), `uses` (unfolded by `#[uses]`), `names` (uses by name a `spec fn` whose signature changed). A proof sees a callee only through its contract and a `spec fn` only through `#[uses]` (ADR-0017 §4), so the impact stops after one step. If DEF is a struct or enum (ADR-0026 §6), the definitions that use by name that type or a type that contains it are `types`, and from those among them that use it on their surface (the signature and contract of an executable function, the whole of a `spec fn`) it spreads one more step by `calls`, `uses` and `names`. The remaining definitions that values of that type pass through (the type is in a local, a parameter, a result or a callee signature) are `values`: the type invariant is assumed and proved there (ADR-0060 §3) |
| `duplicates` | A row `{"hash","defs"}` for each group of definitions with the same identity (`id`, ADR-0059 §6) (`hash` is that `id`; only groups with two or more definitions; in `id` order; `defs` in path order), and a summary row `{"summary":true,"groups","duplicate_defs","defs"}`. An identity has no names, so alpha-equivalent definitions that differ only in the names of the definition, unit, parameters, locals, labels and fields, definitions that call the same definitions, and copies of recursive and mutually recursive definitions are grouped (DESIGN.md §7.2, corpus `tests/duplicates/`) |

| `effects [DEF]` | The effect view (DESIGN.md §7.2). With DEF, a row `{"def":DEF,"effect":"io","path"}` for each `io` definition reached from DEF by executable calls (`calls` edges) (DEF itself and the built-ins `print_i64` and `print_u64` included) (`path` is the shortest call path from DEF to that definition; in path order of the reached definitions), then a row of the same form with `"effect":"alloc"` for each definition that declares `alloc`, and a summary row `{"summary":true,"def","io_reached","defs","alloc_reached"}`. Without DEF, a row `{"def","effect":"io","path"}` for each definition that reaches a built-in `io` operation (the shortest path to the nearest operation; in definition path order), then an `"effect":"alloc"` row for each definition that reaches an allocating operation (a definition whose own operations allocate), and a summary row `{"summary":true,"io_reaching","io_defs","defs","alloc_reaching","alloc_defs"}`. If there are several shortest paths, the definition paths are compared in turn and the smallest is chosen (independent of call order and definition order). It uses only the map edges and proves nothing (it is one of the queries that need no proof). The effect check (E0603) blocks `io` calls from `pure`, so every definition that reaches `io` is declared `io`. A definition declared `io` that reaches no operation does not appear in the result without DEF (the difference between `io_defs` and the number of rows) |
| `effect E` | The list of definitions for one effect (ADR-0030 §5, `E` is `alloc` or `io`). For each executable definition that declares `E` or needs it (it is in `eff*`), `{"def","effect","declares","requires","source"}` (in path order; `source` is `own` for its own operations and built-in `io` calls, `callee` for through calls only, `null` for declared only), and a summary row `{"summary":true,"effect","declares","requires","defs"}`. It uses only the map edges and the checker's tables and proves nothing |
| `tests` | The remaining test area (ADR-0003, DESIGN.md principle 4). A row `{"path","test_reasons","sites","lines"}` for each executable definition that still needs tests (in path order), and a summary row `{"summary":true,"exec_defs","test_needed_defs","io_defs","unproved_defs","test_sites","test_lines"}`. The reasons are the same as `test_reasons` of L1: `io` (`io` is in `eff*`: the contract does not say the order and content of the output), `unproved` (there is a failed obligation, so the contract itself does not stand). `sites` is the number of built-in `io` operations that the definition calls directly (where a test should aim), and `lines` is the number of lines of the normal form. `spec fn` and definitions that are only declared `io` and reach no operation are not counted. It uses the proof state, so it proves (the same as `status`). It is the BMB-side value of G8. If the effects grow (the ADR-0030 proposal: `panic`, `nondet`, trust grades), the reasons grow |

### Query scope

Queries that grow with program size take path arguments and answer only for that scope (BNB measurement: at 10,000 definitions, `units` is 1.18MB and `status` is 2.5MB). The bytes of the output of the form without arguments are unchanged.

- **Paths:** each argument is one full path of a unit, definition or type. A path selects that item and everything under it: `u` is the unit `u` and its definitions, types and inner units, `u::f` is one definition, `u::T` is the type and its `impl` functions. A definition made by function-value lowering (`<u::__closure$0 as ..>::call`) belongs to the scope of its own unit. Several paths are a union. A path that points at nothing is an error (`unknown definition or unit`) and nothing is proved.
- **Rows:** of the rows of the unscoped answer, the rows of the definitions in scope, in the same order and the same bytes. The summary row gets `"scope":[path..]` (in name order, no duplicates) after `"summary":true`, and the counts are those inside the scope (`defs` is the number of definitions in scope).

| Query | With a scope |
| --- | --- |
| `units [PATH..]` | The L0 rows of the units, definitions and types in scope (no summary row) |
| `status [PATH..]` | The rows of the definitions in scope and the summary of the scope. Only the definitions in scope are proved (`verify::verify_only`, the same route as `surface DEF`: the rows are the same bytes as with the full proof, `tests/mcp_cache.rs`) |
| `tests [PATH..]` | The rows of the definitions in scope and the summary of the scope. Only the definitions in scope are proved |
| `duplicates [PATH..]` | The groups that contain at least one definition in scope. A group appears whole (the twin outside the scope is the answer). `duplicate_defs` is the number of definitions in the groups shown |
| `effects [PATH..]` | If the argument is one definition, what that definition reaches, as before (the reachability view). Otherwise (a unit, several paths), the rows of the definitions in scope from the unscoped list (for each definition, the path to the nearest operation) |
| `effect E [PATH..]` | The rows of the definitions in scope and the summary of the scope |
| `text PATTERN [PATH..]` | Text search in bodies (ADR-0146). A row `{"path","line","text"}` for each line that contains `PATTERN` (literal, case-sensitive, no pattern language) in the normal form of the definitions and types in scope: `line` is the line number inside the normal form of that definition (1 for a type declaration), and `text` is the line with leading and trailing whitespace removed; for a line longer than 200 bytes it is 200 bytes starting 60 bytes before the first occurrence (truncation is marked with `..`). In path and line order, with a summary row `{"summary":true,"pattern","matches","defs"}` at the end. The MCP description mentions this query only with `--bounded` (the description without the flag is that of the frozen set, unchanged) |
| `edges DEF [out\|in\|both] [DEPTH] [KIND,..]` | The fourth argument is the edge kinds joined by commas (`calls`, `const`, `contract`, `passes`, `proof_calls`, `reads`, `spec_calls`, `trait`, `types`, `uses`, `writes`). Only edges of those kinds are followed: at depth 1 the rows of those kinds, and deeper the closure built from those kinds alone (`calls` does not reach the contract edges of a callee). An unknown kind is an error |

### The window of a response (ADR-0127)

`bmb query|map [--budget BYTES] [--offset ROWS] [--limit ROWS] ..` gives a window of the response (`map::bound`). It is the whole rows that fit in the budget starting from row `offset` (the first row is given even if it exceeds the budget), and no more than `limit` rows. The map head row is a row too. If the window is not the whole response, the last row is `{"truncated":true,"offset":O,"shown":N,"rows":total rows,"bytes":total bytes}`, and if rows remain, `"next"` (the `offset` to continue from) and `"hint"` are added. If the whole fits in the window, the output is the same bytes as without the flags. With no flag at all there is no window.

`bmb mcp --bounded` puts a window with a budget of 32,768 bytes (`map::RESPONSE_BUDGET`) on the results of `query` and `map`, the two tools take `offset` and `limit` (integer) arguments, and the descriptions mention the truncation row, `overview`, the scope arguments and the kind argument of `edges`. The budget is counted in JSONL bytes before the `--compact` view. Without the flag the tool list and the responses are unchanged (`frozen_tool_lists_keep_their_bytes`). `--bounded-16k` puts the same window with a budget of 16,384 bytes (`Server::budget`): which of the two becomes the default is still to be measured, and only one is kept after the verdict.

`query overview [PATH..]` gives one row per unit: `{"kind":"unit","path","summary","units":N,"defs":N,"types":N}`. It is the L0 unit row with its lists replaced by counts, so the row size does not depend on the unit size (67,313 bytes at N=10,000 with 500 units; `units` without a scope is 1,192,293 bytes). It does not run the solver.

Tests: `a_window_shows_whole_rows_and_says_what_it_left_out` (the windows joined together equal the whole, for each budget) and `overview_lists_units_with_counts` in `tests/map.rs`, `bounded_results_are_windows_of_the_response` in `tests/mcp.rs`.

`map` does not take a scope. Each layer has a scoped query: `units PATH..` for L0, `surface DEF` for L1, `edges DEF ..` for L2.

The MCP `query` tool takes the same arguments in the `args` array (the schema and the description are unchanged: the tool-list bytes of the frozen set, `frozen_tool_lists_keep_their_bytes` in `tests/mcp.rs`).

The description of the MCP `query` tool was not changed. The wording the agent sees stays as it is until the real-model measurement is finished. The tool also accepts `impact`, `duplicates` and `effects`.

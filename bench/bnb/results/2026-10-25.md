# BNB 오라클 비교: BMB 맵 도구 대 Rust 파일 도구 (2026-10-25)

백로그 3A-05(ADR-0034 G4)의 첫 측정. 같은 계획으로 만든 BMB 작업 공간과 Rust 쌍둥이 크레이트에서 같은 탐색 질문 27개를 두 팔의 스크립트 오라클로 풀었다. 실제 모델은 돌리지 않았다(유료, 사용자 머신).
원자료: `2026-10-25.jsonl`(커밋 `5d274c1`의 코드, `target/release/bmb`). 표는 `bnb.py table`의 출력이다.

## 재현

```
cargo build --release
BMB=target/release/bmb python3 bench/bnb/bnb.py run --sizes 100 1000 10000 \
    --check-truth --cargo-check --expect all-pass --work W --out R.jsonl
python3 bench/bnb/bnb.py table R.jsonl
```

토큰 수는 결정론적이다(생성기·과제·오라클·컴파일러 출력이 같으면 같은 바이트). 벽시계는 기록만 하고 보고하지 않는다.

## 무엇을 쟀나

- **비용**: 세션의 모든 도구 응답 바이트, 토큰 = ceil(bytes/4)(ADR-0021). 도구 인자(요청) 토큰은 따로 셌다. 시스템 프롬프트·도구 설명은 세지 않았다.
- **정확도**: 정답 집합에 대한 정밀도·재현율, 성공 = 둘 다 1. 예산은 하네스와 같다(도구 호출 40회, `answer` 포함).
- **정답의 동일성**: `--check-truth`가 크기마다 BMB 맵에서 계산한 정답과 `analyze.py`가 Rust 원문에서 계산한 정답을 과제별로, 그리고 구조 전체(실행 호출·`&mut` 쓰기 간선, 계약 간선, io 집합, 중복 묶음)를 비교했다. 세 크기 모두 차이 0.
- **쌍둥이**: `cargo check`(`RUSTFLAGS=-D warnings`) 세 크기 모두 통과.
- **오라클**: 팔마다 그 도구로 찾은 가장 싼 정확한 전략(README "오라클"). 그래서 아래 수치는 팔의 비용 **하한**이다.

## 해석

**정확도는 같다(오라클이므로 당연).** 두 오라클 모두 세 크기에서 27/27, 예산 한도에 닿지 않았다(최대 호출 bmb 4, rust 17). 이 측정이 보이는 것은 정확한 답의 최소 비용이다. 정확도 비교(G4 "동등 이상")는 실제 모델 측정이 해야 한다.

**범위 과제의 비용은 두 팔 모두 크기와 무관하다.** 1,000과 10,000에서 바이트까지 같다(100에서 다른 것은 뒤 단위가 없어 정답이 작기 때문). BMB는 질의 범위에 비례한다(원칙 7). Rust 오라클도 크기와 무관한데, 이는 grep이 맞은 줄만 돌려주고, 오라클이 이 크레이트의 배치 규약(모듈 = 파일, 모듈 단위 `use`)을 알아 `mU::f(` 정규식과 자기 파일의 맨이름 검색으로 거짓 일치 없이 찾기 때문이다. 같은 질문을 맨이름 grep으로 하면 크기에 비례한다(`RustTools`로 잰 값, N=100/1,000/10,000):

| grep(크레이트 전체) | 줄 | 토큰 |
| --- | --- | --- |
| `\bclamp_1\(` (n01 대상의 맨이름) | 10 / 51 / 386 | 107 / 570 / 4,479 |
| `\bmix_6\(` (n03 대상의 맨이름) | 13 / 151 / 1,636 | 135 / 1,629 / 18,305 |
| `^pub fn `(모든 함수 머리) | 100 / 1,000 / 10,000 | 1,222 / 12,351 / 125,957 |

생성기가 단위마다 같은 이름 줄기(`mix_6`, `clamp_1` …)를 쓰므로 이름 충돌이 실제 코드베이스보다 많을 수 있다. 실제 에이전트가 어느 쪽에 가까운지는 실제 모델 측정이 정한다.

**범위 과제에서 BMB는 3.9배 싸다(과제별 1.7~12.3배).** 직접 호출자·계약 변경 영향·`&mut` 인자 전달자는 8~12배: BMB는 간선 몇 줄, Rust는 호출 줄과 그 파일의 함수 머리 목록(둘러싼 함수를 찾기 위해)을 읽는다. 전이 피호출자는 1.7~2.0배로 차이가 작다: `edges DEF out 64`가 호출 간선과 함께 계약·`#[uses]` 간선을 모두 돌려주어 응답 행의 약 70%가 질문과 무관하고(n04, N=10,000: 38행 중 `calls` 11행), Rust는 함수 본문 몇 개만 읽으면 된다. 술어를 쓰는 함수(`requires`)는 2.2배: Rust의 `/// Requires:` 줄 grep이 이미 정밀하다.

**전체 과제에서 BMB의 이점은 줄고, 중복 질문에서는 BMB가 더 비싸다.** BMB에는 정의 하나로 범위를 줄인 `duplicates`와 집합 단위의 `effects`가 없어 오라클이 프로그램 전체 응답을 받는다. `duplicates`는 모든 중복 묶음(10,000에서 12,059토큰)을 돌려주므로 묶음 하나(132개)만 필요한 n27에서 Rust(본문 첫 줄 grep + 문맥, 4,349토큰)의 2.8배를 쓴다. io 호출자(n12·n24)는 호출자 폐포가 3개 이하인데도 전체 `effects`(약 9,300토큰)를 읽는다. 크기에 비례하는 이 비용 때문에 10,000에서 합계 비가 2.1로 내려간다.

**G4 잠정 목표(1만 정의에서 파일 기반 대비 토큰 1/3 이하)에 대해:** 오라클 하한끼리 비교하면 범위 과제에서는 충족(1/3.9), 과제 27개 합계에서는 미충족(1/2.1)이다. 이것은 판정이 아니다. 판정은 같은 모델의 실제 에이전트 측정(호출 수에 따른 대화 누적 입력 토큰 포함)으로 한다. 호출 수는 bmb 과제당 2~4, rust 4~17로, 호출마다 대화 전체를 다시 보내는 실제 에이전트에서는 Rust 쪽 누적 입력이 이 표보다 더 커진다(여기서는 세지 않음).

## 후보 (측정에서 나온 것, 백로그에 넣지 않음)

1. `duplicates DEF`: DEF의 묶음만 돌려주는 범위 질의(n26·n27을 크기 무관으로).
2. `edges`의 간선 종류 거르기(예: `calls`만): 전이 피호출자 응답을 약 1/3로.
3. 정의 집합에 대한 `effects`(또는 `edges` 행에 효과 표시): io 호출자 질문에서 전체 `effects`를 읽지 않게.

## 한계

- 오라클은 하한이다. Rust 오라클은 첫 파일에서 알 수 있는 배치 규약에 기대고, 쌍둥이의 고정 배치에서만 정확하다. BMB 오라클은 맵 의미(호출자 폐포는 `calls` 간선만으로 닫힘)에 기댄다. 두 오라클 모두 정답과 비교해 확인했다.
- 과제는 생성 코드의 구조 질문이다. 의미를 읽어야 하는 질문(무엇을 하는 함수인가)과 수정 질문은 없다.
- 세션 고정비(프롬프트, 도구 설명: MCP `tools/list`와 Rust 도구 3개)는 세지 않았다.

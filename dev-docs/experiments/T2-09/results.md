# T2-09: 라이브러리의 가장 비싼 의무(`utf8::width`)

Z3 4.15.4, 시드 0, rlimit 5,000,000. "전"은 `6a0e0ba7`, "후"는 이 태스크의 커밋이다.

## 원인

`utf8::width`의 사후조건 의무(E0802, 의무 24) 하나가 rlimit 1,843,925(한도의 0.37)였다. 탐침(rlimit 50,000)은 결정하지 못하고 전체 질의가 `unsat`.

```
target/debug/bmb verify --emit-smt OUT lib/utf8.bmb      # OUT/utf8.width.smt2의 "; obligation 24"
z3 -st -v:10 query.smt2                                   # 단계별 비용
```

- 검색은 작다: 충돌 50, 결정 109, 수량자 인스턴스 60, 0.1초.
- 비용은 전처리다: `(ctx-simplify :num-steps 1821059)`. 1,843,925 중 1,821,059가 Z3의 문맥 단순화기(`ctx-simplify`, 양화 질의의 기본 전략 앞단)다.
- 펼침·트리거·비선형이 아니다. 정의를 매크로로 바꾸거나 빼도 `ctx-simplify` 단계 수는 그대로였다.
- 질의의 경로 사실 하나가 `(=> c1 (and .. (=> c2 (and .. (=> c3 ..)))))`로 15단 중첩되어 있었다. 인코더의 `Enc::branch`가 `if`마다 그 쪽에서 얻은 사실(인덱스 범위, 병합 등식, 안쪽 `if`의 사실)을 `(=> c (and ..))` 하나로 묶기 때문이다. `ctx-simplify`는 `and`/`or`의 인자를 형제 인자를 가정하고 앞뒤로 다시 단순화하므로 중첩 깊이에 지수적으로 일한다.
- 층: 컴파일러(인코딩, JUDGMENT §3). 라이브러리를 고치지 않는다(사용자 코드를 쪼개면 우회, §8).

## V5와 라이브러리

V5(고정 ≤ 0.2)가 라이브러리와 게임 프로그램도 본다(`health.py`의 `with_library_headroom`). 한도 근처의 증명이 시드·버전에 깨지는 위험은 라이브러리도 같고, 라이브러리는 우리가 쓰는 코드라 V9 같은 래칫(벤치 기준 해법용)이 아니라 고정 상한이 맞다. 고치기 전이면 0.3688로 게이트가 실패했을 것이다(`scripts/test_health.py`).

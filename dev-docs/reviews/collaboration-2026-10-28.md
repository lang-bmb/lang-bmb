# 협업 논의: 여러 에이전트가 같은 코드베이스를 고친다는 것

> 2026-10-28 · **상태: 논의 중(결정 아님).** 앞선 논의는 `direction-2026-10-28.md`이고, 판단은 `dev-docs/JUDGMENT.md`로 한다.
> 이 문서는 언어 수준의 근본 질문을 다룬다. 원격·멀티세션 도구 서버를 만들자는 제안이 아니다.

## 1. 질문 (사람의 가설)

- 파일은 혼자 쓰는 도구다. 여럿이 같은 파일을 고치면 오류가 난다. 그래서 개발자는 git을 쓰고, 여럿이 함께 쓰려면 DB 같은 중재 프로그램이 필요해진다.
- 에이전트 코딩 시대에 여러 에이전트가 협력한다는 것은 무엇인가?
- BMB에서는 코드 파일이 정본이고 접근은 도구를 거친다. 그 도구가 원격 작업과 여러 세션을 지원한다면 무엇이 달라지는가?

## 2. 파일과 git이 실제로 하는 일

여럿이 같은 자료를 고치는 방법은 둘뿐이다.

- **중재자:** DB 서버처럼 트랜잭션·잠금·격리로 순서를 정한다.
- **병합 대수:** 각자 고치고 나중에 합친다. git의 3-way 병합, 실시간 편집기의 CRDT가 여기에 든다.

git은 줄을 단위로, 텍스트를 기준으로 합친다. 그래서 두 방향으로 틀린다.

| 오류 | 뜻 | 예 |
| --- | --- | --- |
| 거짓 충돌 | 무관한 편집인데 충돌로 판정 | 같은 파일의 이웃한 두 함수를 각자 고침 |
| 거짓 병합(의미 충돌) | 텍스트는 깨끗이 합쳐졌는데 결과가 틀림 | A가 함수의 계약을 바꾸고, B가 옛 계약에 기대는 호출을 더함 |

거짓 병합이 더 위험하다.

- **경험 연구:** 텍스트 충돌 없이 합쳐진 뒤 빌드·테스트가 깨지는 일이 실제 프로젝트에서 관찰된다.
  - Java 저장소 208개를 조사한 연구(Shen 외, TOSEM 2022): 텍스트 충돌 장면 15,886개, 빌드 충돌 79개, 테스트 충돌 33개. 분모가 달라 비율로 바꾸지 않는다.
  - 2016년 예비 연구: 세 프로젝트의 병합 커밋 중 테스트 실패가 4%, 28%, 3%(원문 미확인).
- **업계의 답:** "not rocket science rule"이다. 합친 결과를 시험한 뒤에만 main에 넣는다. 병합 큐(bors, GitHub merge queue, Google TAP)가 이 규칙을 구현한다.
  - 비용: 합칠 때마다 시험 전부를 돌리고, 병합을 줄 세운다.
- **CRDT:** 모두가 같은 텍스트에 도달함(수렴)을 보장한다. 그 텍스트가 컴파일되는지는 보장하지 않는다.

**선례**

- ENVY/Developer(Smalltalk): 메서드 단위로 판(edition)을 저장한 팀 저장소.
- Unison: 정의 단위·해시 정체성. 추가는 충돌하지 않는다.
- Google Piper: 중앙 서버와 커밋 전 시험.

## 3. 핵심 관찰: 협업의 문제는 저장이 아니라 독립성 판정이다

두 편집을 어느 순서로 적용해도 결과가 같고 둘 다 유효하면, 두 편집은 **교환 가능**하다.

- 모든 협업 체계(git, DB, CRDT)는 결국 교환 가능성을 판정하고, 교환 불가능한 경우를 처리하는 장치다.
- 텍스트 기준은 싸지만 양쪽으로 틀린다(§2).
- 옳은 기준은 의미다. "B가 기대는 것을 A가 바꿨는가?"

일반 언어에서는 한 변경이 기대는 것(읽기 집합)에 경계가 없다. 테스트는 아무것이나 읽고, 전역 상태·리플렉션·매크로가 있다. 그래서 합친 결과를 전부 다시 시험해야만 판정할 수 있다. 이것이 병합 큐가 존재하는 이유다.

**BMB에서는 읽기 집합이 이미 계산되어 있다.** 한 정의의 증명이 기대는 것은 다음이 전부다.

- 자기 텍스트
- 부르는 정의들의 계약(`iface` 해시)
- `#[uses]`로 펼치는 `spec fn`의 본문
- 타입 정의

이것이 바로 증분 빌드 키다(ADR-0032·0043). 키가 인코딩이 읽는 것을 다 담는다는 것은 시험으로 확인한다(`with_audit`, `tests/incremental.rs`). 따라서 BMB 코드베이스는 다음과 같은 데이터베이스로 볼 수 있다.

| 데이터베이스 | BMB |
| --- | --- |
| 행 | 정의(정체성 해시, ADR-0059) |
| 무결성 제약 | 모든 정의가 증명된다(게이트) |
| 트랜잭션 | 도구의 쓰기 트랜잭션(ADR-0009) |
| 쓰기 집합 | 트랜잭션이 바꾼 정의 |
| 읽기 집합 | 바꾼 정의들의 증명이 기댄 계약·명세·타입의 해시 |
| 낙관적 동시성 제어 | 커밋 때 읽기 집합이 그대로인지 확인(`expect`, ADR-0059). 달라졌으면 영향받은 정의만 새 상태에서 다시 증명 |

일반 언어의 병합 큐는 "합친 결과 전부 시험"으로 무결성을 지킨다. BMB는 "읽기 집합이 겹친 정의만 재증명"으로 같은 일을 한다. 판정은 증명이므로 거짓 병합이 원리상 0이어야 한다. 이 "이어야"를 재는 것이 §7의 H-COMMUTE다.

## 4. 언어가 하는 몫 (범위 안)

편집이 교환 가능해지는지는 언어 설계가 정한다. 대부분 이미 결정된 것이다.

| 언어 성질 | 협업에서 하는 일 | 상태 |
| --- | --- | --- |
| 계약 경계(모듈 단위 검증) | 읽기 집합이 본문이 아니라 계약이다. 본문 편집끼리는 서로의 읽기 집합에 들어가지 않는다 | 있음(ADR-0032) |
| 전역 가변 상태 없음 | 읽기 집합이 전역이 되지 않는다 | 있음(원장 "효과") |
| 정규형 하나 | 서식 충돌이 없다 | 있음(ADR-0019) |
| 정체성 해시 | 이름 바꾸기가 참조자의 쓰기 집합을 넓히지 않는다(현행 86%가 넓힘) | ADR-0059 제안 |
| **정제 규칙** | 계약 변경 중 `requires` 약화·`ensures` 강화는 호출자의 증명을 깨지 않는다. 그런 변경은 호출자 편집과 교환 가능하다. SMT 함의로 판정하고, 판정이 안 되면(unknown) 충돌로 본다 | 새 후보. 질의는 명세 약화 감지(2D-19)와 같고 방향만 반대다 |
| 효과 선언 | 효과 변화는 계약 변화처럼 다룬다 | 있음 |
| 슬라이스 예산 | 정의가 작을수록 쓰기 집합이 겹칠 확률이 낮다 | 원칙 5 |

결론: 언어가 정할 것은 **교환 관계** 하나다. "두 편집은 언제 독립인가"를 결정론적으로 판정하는 규칙이다.

- **판정 규칙:** 쓰기 집합과 상대의 읽기 집합이 겹치지 않거나, 겹친 변경이 정제다.
- **부산물:** 정제 판정은 그대로 "증명된 하위 호환" 판정이 된다. 5B(안정성 정책)의 semver를 증명으로 정할 수 있다.

## 5. 도구의 몫과 범위 밖

- **도구:** 트랜잭션이 스냅샷의 읽기 집합과 `expect` 전제조건을 기록하고, 커밋 때 교환 관계로 확인한다.
- **범위 밖:** 서버, 복제, 인증, 실시간 동기화, 세션 관리. 언어의 일이 아니고 이미 있는 기반(git, DB)이 할 수 있다.
- **새 기반 없는 대안:**
  - git을 저장과 전송으로 그대로 둔다.
  - BMB 병합 드라이버(`.gitattributes`의 merge driver)를 둔다. 드라이버는 정의 단위로 합치고 교환 관계로 충돌을 판정한다.
  - 병합 큐는 남는다. 하는 일만 "합친 결과 전부 시험"에서 "교환 판정이 실패한 정의만 재증명"으로 바뀐다.

**권장 입장.** 원격·멀티세션 도구 서버는 필요 조건이 아니다.

- 같은 교환 관계를 서버가 쓰면 실시간 협업이 되고, git 드라이버가 쓰면 비동기 협업이 된다.
- 어느 쪽이든 언어가 정할 것은 관계 하나다.
- 서버는 나중의 제품 결정이다. 가설을 재는 데에는 필요 없다(§7의 실험은 모델도 서버도 없이 돈다).

## 6. 여러 에이전트가 협력한다는 것

충돌을 피하는 것은 절반이다. 협력의 꼴은 넷이다.

1. **병렬 분할:** 독립된 과제를 나눠 동시에 한다. 교환 관계가 있으면 거짓 충돌과 거짓 병합 없이 합쳐진다.
2. **계약 우선 분업:** 한 에이전트나 사람이 계약(의도)을 먼저 정한다. 여러 에이전트는 그 계약만 보고 구현을 나눠 맡는다.
   - 각 구현은 계약에 대해서만 증명된다(assume-guarantee). 그래서 합쳐도 의미 통합 실패가 없다. 증명이 합성되기 때문이다.
   - Rust에서는 같은 분업의 통합 실패가 합친 뒤 테스트에서야 드러난다.
   - 모듈 단위 검증이 곧 병렬 개발의 조건이라는 점이 BMB만 주장할 수 있는 몫이다.
3. **맵 = 공유 칠판:** 계약은 있고 증명되지 않은 정의가 열린 작업 항목이다. `query status`가 작업 큐다. 누가 무엇을 맡았는지(점유·임대)는 도구·프로세스의 일이다.
4. **검토:** 사람은 코드가 아니라 계약을 검토한다(E1). 계약이 사람 승인의 단위가 된다. 계약 변경은 정제인지 아닌지로 분류되므로, 검토가 필요한 변경(정제가 아닌 것)만 사람에게 간다.

## 7. 가설

| ID | 가설 | 반증 조건 | 측정 | 모델 |
| --- | --- | --- | --- | --- |
| H-COMMUTE | 교환 관계(쓰기 집합 ∩ 상대 읽기 집합 = ∅, 또는 겹친 변경이 정제)는 건전하다: 교환 가능으로 판정한 편집을 합친 결과는 언제나 증명된다. 그리고 텍스트 병합보다 거짓 충돌이 적다 | 교환 가능 판정을 합친 결과에서 증명 실패가 하나라도 나온다. 또는 거짓 충돌률이 `git merge-file`보다 높다 | BCB 이력의 같은 기준 커밋 위 편집 쌍(그리고 k개 묶음) 표본. 각각 (1) `git merge-file` 충돌, (2) 깨끗한 텍스트 병합의 BMB 증명과 Rust 쌍둥이 테스트 결과(거짓 병합), (3) 교환 판정, (4) 정의 단위 병합의 증명, (5) 재증명 비용 | 아니오 |
| H-SPLIT | 계약을 먼저 고정하고 N개 에이전트가 구현을 나눠 맡으면, 합친 결과의 통합 실패가 0이다. Rust+테스트의 같은 분업은 통합 실패가 0보다 크다 | BMB에서 각자 증명된 구현을 합친 결과가 증명에 실패한다(모듈 검증의 결함). 또는 BMB 분업의 성공률이 단일 에이전트보다 낮다 | m1b·BRB 과제를 계약 고정 + 정의 분할로 나눈 판, 같은 모델 | 예 |

H-PAR(정의 단위 충돌률, 앞선 논의)는 H-COMMUTE 실험의 한 열이 된다.

# 보완 가설 후보 검토 (2026-11-01)

> 사람이 낸 초안 "보완 가설 후보 (AI 코딩 시대 언어 요건)"(부록 A에 원문)을 설계·결정·백로그와 대조한 검토다. 등록은 이 문서가 아니라 ADR로 한다(ADR-0058 §4: 등록부의 가설은 ADR과 논의 기록으로 들어간다). T1의 통과 기준이 "등록부의 모든 가설이 확정·반증·보류"이므로 가설을 더하는 것은 통과 기준 변경이고 사람 승인이 필요하다(AUTONOMY §4). 백로그 `T1-42`.

## 2. 가설별 분류

분류: **등록 권장**(설계 전제를 재는데 기존 가설이 없음) · **재구성 후 등록**(겹침이나 측정 불가 부분을 고치면 됨) · **설계 충돌**(DESIGN 변경 승인 없이는 등록할 수 없음) · **범위 밖·나중**(언어 범위 확대나 생태계 관문에 걸림).

| 가설 | 분류 | 근거 |
| --- | --- | --- |
| H-EFFECT | 등록 권장 | DESIGN §4.1 효과 행이 "테스트 필요 면적 산출, 순수 구간은 증명만으로 충분"을 이미 주장하는데 재는 가설이 없다. G8의 공백(utility §2.1)을 메운다. 선행: 효과 확장 ADR-0030(제안)·`2F-02`(승인 대기), 상태 있는 과제 집합 설계. 지금의 `io` 효과와 `test_needed_defs`(2D-21)로 첫 판을 잴 수는 있다 |
| H-INTENT | 등록 권장 | DESIGN 전제 E1·E2(d)(명세 타당성)를 재는 가설이 없다. 예시·반례 생성은 SMT 모델로 결정론적이라 원칙 6·§8.2 도구 규칙 안이다. 사람 표본과 리뷰 모델 중 무엇을 쓸지 먼저 정해야 한다 |
| H-REVIEW | 등록 권장 | E1을 직접 잰다. H-INTENT와 같은 평가자 결정이 필요하다. 명세 diff는 `bmb weaken`(2D-19)이 이미 계약 변화를 반례와 함께 낸다 |
| H-SMALL | 재구성 후 등록 | qwen BRB의 2/24는 측정 조건이 섞여 있다: 미제출 중 다수가 세션 출력 한도 64,000에서 끝났다(`T0-16`, 권장안은 승인 대기). 조건을 고친 동결 판에서 기준선을 다시 잡아야 격차 변화가 도구·진단의 효과가 된다. H-FAMILIAR와도 겹친다(모델 차이가 팔 차이보다 크다, utility §2.7) |
| H-REPAIR | 재구성 후 등록 | 반례(E0802)와 수리 제안(`fix`, P3 87%)은 이미 있다. "새 판 대 현 판"이 아니라 "제거 판 대 현 판"(절제 비교)으로 정의해야 측정이 된다. `2D-29`와 겹친다 |
| H-COMPAT | 재구성 후 등록(결정론) | 도구가 이미 있다: `bmb weaken`(약해진 계약을 반례와 함께), `impact`(호출자). BCB 이력의 계약 편집 판정이 생성기 정답과 모두 일치한 결정론 근거도 있다(2D-19). 모델 없이 판정할 수 있어 등록하면 바로 "결정론 근거"가 된다 |
| H-DECIDE | 지표로 | 언어에 관한 주장이 아니라 판정기의 공학 성질이다. 등록부 가설보다 지표(G1 곁 또는 지속 관리 V 지표)가 맞다. "같은 뜻인데 미결정"은 세션 기록 재생으로만 가를 수 있다(T0-19 방식). T0-24 뒤 남은 미결정은 재귀 술어뿐이다(`T1-24`·`T1-25`) |
| H-PRIOR | 설계 충돌(일부) | "규칙 완화"는 §4.1 편의 포기 원장(ADR-0045)과 원칙 8(표현 하나)을 바꾸므로 DESIGN 변경 승인이 필요하다. "자동 변환"은 §4("더 장황한 Rust처럼"), §8.2(기계적 표기 자동 채움, Rust 습관 교정) 안이다. 자동 변환 팔만으로 재구성하면 등록할 수 있고, H-FAMILIAR·`2R-04`(대안 문법 오프라인 비교)·`T0-17`과 겹치는 부분을 나눠야 한다 |
| H-GRADUAL | 설계 충돌 | 원칙 4 "증명이 없으면 바이너리도 없다", 목표 "정확성은 제약", 비목표 "빠른 프로토타이핑"과 정면으로 맞선다. 설계 안의 대응물은 근거 있는 탈출구와 미증명 면적 집계다(ADR-0029 제안, `2E-02`~`2E-04` 승인 대기). 재구성 안: "근거 있는 탈출구로 시작한 코드는 편집이 쌓이며 미증명 면적이 줄어든다" |
| H-REFINE | 합치기 | H-SPLIT(계약 고정 분업)과 §8.2 해체·분할 제안, trait 계약 정제(ADR-0046)와 겹친다. H-SPLIT의 과제 집합에 "정제 작성" 팔로 넣는 편이 낫다 |
| H-PARSE | 합치기 | 타입 불변식(ADR-0060)이 값을 잊는 모든 경계에서 증명되므로 "검증된 값만 들어온다"의 기계는 있다. 외부 입력 경계는 원칙 4가 시험이 남는 곳으로 둔다. H-ENCAP 집합에 파서 과제를 더하는 편이 낫다 |
| H-TRACE | 재구성 후 나중 | 도구 체인에는 LLM 판단을 넣지 않는다(§8.2 결정론 규칙). 자연어 요구와 조항의 연결은 에이전트가 근거(원칙 3, 노드 해시에 묶인 구조화 근거, `2E-04`)로 선언해야 하고, 그러면 누락 검출은 결정론적이며 가설은 "에이전트의 연결 정확도"가 된다. 근거 구현(2E) 뒤 |
| H-PROV | 나중 | 정체성 해시(H-ID), 트랜잭션, 세션 기록(INF-17), 근거의 미확인 표시(`2E-04`)와 겹친다. 다중 에이전트 실측(H-SPLIT, 3단계) 때 함께 |
| H-CAP | 나중 | 효과(ADR-0030)가 능력의 첫 형태다. 적대 과제는 H-GAME과 짝이다. `2F-02` 뒤 H-GAME 집합 확장으로 |
| H-FFI | 범위 밖·나중 | 생태계(바인딩)는 원칙 4·6이 측정으로 입증된 뒤에 연다(CLAUDE.md 운영 규칙). 경계의 탈출구 `external_body`는 2E 범위 |
| H-CONC | 범위 밖 | DESIGN에 동시성이 없다(메모리 모델 §5는 참조 저장 금지까지만). 언어 범위 확대(ADR-0016)라 승인과 설계가 먼저다 |
| H-COST | 범위 밖 | 자원 상한 계약은 새 계약 종류이고 DESIGN 근거가 없다. 성능은 G6(안전 Rust ±5%)가 다른 방식으로 본다 |
| H-MIGRATE | 재구성 후 나중 | "동등성 증명"은 Rust 의미론을 증명기에 넣어야 해 지금 측정할 수 없다. 숨은 차등 시험 + 옮긴 코드의 계약 강도(BSB)로 바꾸면 잴 수 있다 |

## 3. 권장안 (JUDGMENT §10)

1. **문제:** 효용 보고서(utility §2.1·§2.6·§2.7)가 보인 공백 중 셋이 등록부에 없다: 상태 있는 코드의 테스트 면적, 사람이 명세만 보는 검토(E1), 모델 격차. 초안은 이 공백을 맞게 짚었지만 스물 가운데 일부는 기존 가설·도구와 겹치고, 둘은 설계와 충돌하며, 넷은 언어 범위나 생태계 관문에 걸린다.
2. **원인과 귀속 층:** 프로세스(등록부 갱신). 가설은 전제(E1~E3)와 원칙에서 나와야 하는데, ADR-0058의 등록이 E1·E2(d)를 재는 가설을 빠뜨렸다.
3. **정석 해와 출처:** 가설을 사전 등록하고 반증 조건을 먼저 적는 사전 등록 관행. 이 저장소에서는 ADR-0040·0058의 방식(ADR + 논의 기록, 판정 기준을 측정 전에 동결).
4. **후보:**
   - (가) 초안 스물을 그대로 등록. C1(DESIGN 원칙 4·8과 충돌하는 둘), C3(측정 불가한 판정 기준: H-MIGRATE의 동등성 증명)을 통과하지 못한다.
   - (나) §2의 "등록 권장"과 "재구성 후 등록" 여섯(H-EFFECT, H-INTENT, H-REVIEW, H-SMALL, H-REPAIR, H-COMPAT)을 ADR로 등록하고, H-DECIDE는 지표로, 합치기 둘은 기존 가설의 과제로, 나머지는 보류(사유)로 기록.
   - (다) 아무것도 등록하지 않고 3단계 뒤 다시 본다. E1을 재는 가설이 계속 없게 된다.
5. **권장과 결정적 기준:** (나). (가)와는 설계 정합(C1)에서, (다)와는 전제 검증 범위(S2, 원인 제거)에서 갈렸다.
6. **영향(정보):** 등록부 행 여섯, T1 통과 기준의 대상 증가. 과제 집합이 필요한 것(H-EFFECT)과 평가자 결정이 필요한 것(H-INTENT·H-REVIEW)은 태스크로 나눈다. H-SMALL은 `T0-16`의 조건 수정 뒤 기준선을 잡는다. H-COMPAT은 2D-19의 결정론 근거로 바로 "결정론 근거" 상태가 된다.
7. **필요한 승인(AUTONOMY §4):** (a) 여섯 가설의 등록(T1 통과 기준 변경). (b) H-INTENT·H-REVIEW의 평가자: 사람 표본 또는 리뷰 모델. (c) 판정 기준 수치(초안 값은 잠정, 기존 G 목표와 맞춤). (d) H-GRADUAL·H-PRIOR의 "완화" 쪽을 원한다면 DESIGN 변경 여부. 승인되면 ADR(등록)과 등록부 행, 태스크(과제 집합 설계, 평가자 프로토콜)를 만든다.
8. **우회:** 없음.

## 부록 A. 제출된 초안(원문)

````markdown
# 보완 가설 후보 (AI 코딩 시대 언어 요건)

> **상태:** 제안. 등록부(`docs/ROADMAP.md`)에 올리기 전 검토용 초안이다.
> **출처:** 효용 종합 평가(`dev-docs/reports/utility.md`, 2026-11-01)에서 드러난 공백과, AI 코딩 시대 언어가 갖춰야 할 능력에서 뽑았다.
> **범위:** 기존 가설(G1~G9, H-STABLE, H-MAINT, H-ID, H-PAR, H-COMMUTE, H-ORACLE, H-ENCAP, H-VIEW, H-SLICE, H-SCALE, H-REUSE, H-GRAIN, H-EDIT, H-SPEC, H-NAME, H-AMORT, H-FAMILIAR, H-SPLIT, H-GAME)과 겹치지 않는 것만 담는다.

## 0. 우선순위

| 순위 | 가설 | 이유 |
|----|----|----|
| 1 | H-EFFECT | "테스트 대폭 감소"가 상태 있는 실무 코드에서도 성립하는지를 정한다 |
| 2 | H-INTENT, H-REVIEW | "사람은 명세만 본다"는 비전의 전제다 |
| 3 | H-GRADUAL | 없으면 채택이 시작되지 않는다 |
| 4 | H-PRIOR, H-REPAIR | 작성 비용(약 18배)을 목표(2배)로 끌어내릴 주된 수단이다 |

## 1. 증명할 수 있는 범위 넓히기

### H-EFFECT — 효과 분리
- **주장:** I/O·상태·외부 호출을 타입의 효과로 드러내면, 증명 가능한 순수 핵심과 테스트가 필요한 껍데기가 분리되고 남은 테스트 면적이 작아진다.
- **측정:** 입출력·상태·외부 의존이 있는 과제 집합에서 `test_needed_defs` 비율과 테스트 코드 줄 수를 Rust 팔과 비교한다.
- **판정 기준(안):** 남은 테스트 면적이 정의의 20% 이하, 테스트 코드 줄이 Rust의 1/3 이하.
- **근거:** utility §2.1 — 지금은 순수 함수 과제만 쟀다.

### H-CONC — 동시성 증명
- **주장:** 동시성 코드에서 데이터 경쟁·교착 부재를 증명할 수 있고, 모델이 이 증명을 통과하는 코드를 쓸 수 있다.
- **측정:** 동시성 과제 집합에서 작성 성공률과 숨은 경쟁·교착 결함 수를 Rust 팔과 비교한다.
- **판정 기준(안):** 숨은 동시성 결함이 Rust 팔보다 유의하게 적고, 작성 성공률 차이가 10%p 이내.

### H-COST — 자원 상한 계약
- **주장:** 시간·메모리 상한을 계약으로 적고 증명하면, 성능 퇴행을 테스트·벤치마크 없이 막는다.
- **측정:** 성능 퇴행을 심은 변경 집합에서 게이트 거부율, 그리고 계약 작성 비용(토큰).
- **판정 기준(안):** 심은 퇴행 거부율 ≥ 90%, 거짓 거부 0.

### H-FFI — 계약으로 감싼 외부 호출
- **주장:** Rust·C 라이브러리를 계약으로 감싸고 경계에서 런타임 검사하면, 자체 생태계 없이 실무 과제를 풀 수 있다.
- **측정:** 외부 라이브러리가 필요한 과제의 작성 성공률, 경계 계약 위반의 런타임 검출률.
- **판정 기준(안):** 작성 성공률이 순수 과제 대비 10%p 이내로 떨어지고, 심은 경계 위반 검출률 100%.

## 2. 명세가 의도와 맞는가

### H-INTENT — 명세에서 예시·반례 생성
- **주장:** 명세에서 생성한 예시·반례를 보여주면, 사람이 잘못된 명세를 코드 리뷰보다 잘 잡는다.
- **측정:** 의도와 어긋난 명세를 심은 집합에서, (a) 코드+명세 리뷰 (b) 생성 예시 확인의 탐지율과 소요 시간을 비교한다.
- **판정 기준(안):** (b)의 탐지율이 (a) 이상, 소요 시간 1/2 이하.

### H-REVIEW — 명세 diff 리뷰
- **주장:** 리뷰어가 명세 diff만 보고도 결함 탐지율이 코드 diff 리뷰 이상이다.
- **측정:** 같은 변경 집합을 명세 diff 리뷰와 코드 diff 리뷰로 나눠 결함 탐지율·리뷰 분량을 비교한다(사람 또는 리뷰 모델).
- **판정 기준(안):** 탐지율 동등 이상, 리뷰 분량 1/5 이하.
- **근거:** utility §2.6 — 명세 판별이 모델에 따라 100% / 68%로 갈렸다.

### H-TRACE — 요구사항 추적
- **주장:** 자연어 요구사항과 명세 조항을 연결하면, 빠진 요구를 도구가 찾아낸다.
- **측정:** 요구 하나를 일부러 뺀 명세 집합에서 누락 검출률.
- **판정 기준(안):** 누락 검출률 ≥ 80%.

### H-REFINE — 단계적 정제
- **주장:** 상위 명세를 하위 명세로 정제하는 방식이면, 큰 과제를 작은 증명 단위로 쪼개 성공률을 유지한다.
- **측정:** 대형 과제를 단일 작성 대 정제 작성으로 나눠 성공률·총 토큰을 비교한다.
- **판정 기준(안):** 정제 작성의 성공률이 높고 총 토큰이 같거나 적다.

## 3. AI의 작성 비용 낮추기

### H-PRIOR — 사전지식에 맞춘 표면 문법
- **주장:** 표면 문법을 모델이 이미 아는 Rust에 가깝게 맞추면 첫 시도 성공률이 오르고 토큰이 준다.
- **측정:** BMB 고유 규칙(`as` 금지, 이름 가림 금지, 명세의 변환 금지 등)을 완화하거나 자동 변환한 판과 현 판의 첫 시도 성공률·성공당 토큰을 비교한다.
- **판정 기준(안):** 성공당 토큰 −30% 이상, 증명 신뢰(G1) 유지.
- **근거:** utility §2.7 — BMB 고유 규칙을 오가는 비용이 큰 몫이다.

### H-REPAIR — 수리형 진단
- **주장:** 실패 진단에 반례와 수리 후보를 함께 주면 수리 반복 수가 준다(2D-29의 확장).
- **측정:** 진단 판별(현 판 대 반례·수리 후보 판) 수리 차례 수, 성공당 토큰.
- **판정 기준(안):** 수리 차례 −40% 이상.

### H-SMALL — 약한 모델 격차 축소
- **주장:** 도구·진단 개선이 약한 모델과 강한 모델의 성공률 격차를 줄인다.
- **측정:** 개선 전후 qwen·sonnet 성공률 격차 변화.
- **판정 기준(안):** BRB 격차(현재 21/24 대 2/24)가 절반 이하로 준다.
- **근거:** utility §6 A.

### H-DECIDE — 판정 결정성
- **주장:** 판정기의 미결정률을 일정 이하로 묶을 수 있다.
- **측정:** 정식 측정 전체에서 "같은 뜻인데 미결정" 비율.
- **판정 기준(안):** 미결정률 ≤ 2%.
- **근거:** utility §2.6, T0-19·T0-24.

## 4. 실무 도입

### H-GRADUAL — 점진 검증
- **주장:** 증명 안 된 부분을 허용하고 런타임 검사로 대신하면 도입 비용이 낮아지고, 시간이 지나며 증명 비율이 오른다.
- **측정:** 점진 모드와 전체 증명 모드의 첫 작성 성공률·토큰, 그리고 반복 편집에서 증명 비율의 추이.
- **판정 기준(안):** 첫 작성 성공률이 Rust 팔과 10%p 이내, 증명 비율이 편집 횟수에 따라 단조 증가.

### H-MIGRATE — 이전과 동등성
- **주장:** AI가 기존 Rust 코드를 BMB로 옮길 때 동작 동등성을 증명할 수 있다.
- **측정:** Rust 모듈 집합의 이전 성공률, 동등성 증명 비율, 숨은 동작 차이 수.
- **판정 기준(안):** 동등성 증명 비율 ≥ 80%, 숨은 동작 차이 0.

### H-COMPAT — 계약 호환성
- **주장:** API 계약을 바꿀 때 하위 호환 여부를 증명으로 가르고, 깨지는 호출처를 정확히 짚는다.
- **측정:** 호환/비호환 변경을 섞은 집합에서 판정 정확도와 영향 호출처 재현율.
- **판정 기준(안):** 판정 정확도 100%, 호출처 재현율 100%.

### H-PARSE — 경계 파서
- **주장:** JSON·DB 같은 외부 데이터 경계에서 파서가 계약을 만들어, 검증된 값만 안으로 들어온다.
- **측정:** 잘못된 입력을 심은 집합에서 경계 거부율, 내부 계약 위반 수.
- **판정 기준(안):** 내부 계약 위반 0.

## 5. 다중 에이전트와 신뢰

### H-CAP — 능력 기반 권한
- **주장:** 코드가 쓸 수 있는 자원을 능력으로 제한하면, 에이전트가 과도한 권한이나 악성 동작을 넣는 것을 막는다.
- **측정:** 권한 남용을 시도하는 적대 과제 집합에서 게이트 차단율.
- **판정 기준(안):** 차단율 100%, 정상 과제 거짓 차단 0.
- **관계:** H-GAME(증명 우회)과 짝을 이룬다.

### H-PROV — 변경 출처
- **주장:** 어떤 에이전트가 어떤 증명으로 무엇을 바꿨는지 기록하면, 결함 원인 추적 비용이 준다.
- **측정:** 결함을 심은 다중 에이전트 이력에서 원인 변경을 찾는 데 드는 토큰·시간을 git 이력 기반과 비교한다.
- **판정 기준(안):** 원인 추적 비용 1/3 이하.
````

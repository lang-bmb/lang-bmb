# BMB 효용 종합 평가

> **살아 있는 보고서.** BMB가 약속한 효용에 지금 얼마나 가까운지를, 이른 판단을 포함해 한곳에 서술한다. 판정 문서가 아니다. 판정은 가설 등록부(`docs/ROADMAP.md`)와 측정 보고서(`dev-docs/measurements/`)가 한다.
> **마지막 갱신:** 2026-11-09. 근거: T0-10(qwen3.8-27b)·T0-11(claude-sonnet-5-5)·T0-13(쓰기 표면)·T0-14(H-NAME)·T0-30(H-EFFECT)·T0-31(H-REPAIR) 정식 측정, 파일럿(`bench/pilot/README.md`), 결정론 실험(`dev-docs/experiments/`). 판정 단위는 ADR-0102, 정식 쓰기 표면은 ADR-0101(`write`).
> **갱신 규칙**(백로그 T0-26, AUTONOMY §3.2): §6의 표는 `bench/utility.py --write`로 만들고, 게이트(`bench utility report`)가 결과 파일과 어긋나면 실패한다. 그래서 정식 측정 결과를 커밋하는 커밋은 이 보고서도 고친다. §1~§5의 서술은 그때 표와 맞춰 다시 읽고 고치며, 국면 종료 감사와 결정론 실험 결과 커밋 때도 고친다. 고칠 때마다 §7에 한 줄을 남긴다.

## 0. 지금의 판단

**공학적 가설(결정론·건전성·변경 안전·성능·크기)은 입증됐다. 이 언어의 존재 이유인 경제적 가설, 곧 쓰기 때 더 치른 비용이 이후의 검증 비용과 결함을 줄인다는 전제 E3는 아직 입증도 반증도 안 됐다.** 비용 쪽은 정식으로 쟀고, 이득 쪽(결함, 누적 비용, 큰 코드)은 숫자가 없다. 그래서 동결 전에 이득 쪽 증거를 먼저 잰다(ADR-0103).

- **입증된 것(결정론):**
  - 판정 신뢰(G1), 성능(G6), 바이너리 크기(G9).
  - 증명의 안정성과 재증명의 국소성(H-STABLE, H-MAINT).
  - 이름 바꾸기의 무효화 0(H-ID).
  - 동시 편집의 의미 충돌을 텍스트 병합이 놓치는 것을 정의 단위가 잡는 것(H-COMMUTE, H-PAR).
  - 계약 변경의 호환 판정(H-COMPAT).
- **방향이 맞는 이른 근거(정식 1회):**
  - 테스트 코드 0줄로 같은 숨은 판정을 통과한다(G8, 순수 함수 과제).
  - 탐색은 두 모델 모두 정확도 100%다(G4 정확도).
  - 정의 단위 한 번 쓰기는 원판보다 어느 칸에서도 D를 넘게 뒤지지 않는다(T0-13). 그래서 정식 표면이 됐다(ADR-0101).
- **반증:**
  - H-EFFECT(sonnet): I/O 껍데기가 테스트 면적으로 남는다. 면적 0.667, 기준 0.2.
  - H-REPAIR(qwen 1회, 약함): 수리 제안이 수리 반복을 줄이지 않았다.
  - 원칙 4의 범위를 순수 핵심으로 적었다(ADR-0102).
- **판정할 수 없는 것:** 숨은 결함을 덜 놓치는가(G5 결함, H-ORACLE). 두 팔 모두 숨은 결함이 0이라 과제가 변별하지 못한다.
- **반대 근거:** 과제 단위 총 토큰(G5). 쓰기 판에서 성공당 토큰은 다음과 같다.

  | 과제 | 모델 | BMB 대 비교군 |
  | --- | --- | --- |
  | BRB | sonnet | Rust의 15.1배 |
  | BRB | qwen | Rust의 1.3~2.4배 |
  | BVB | sonnet | Verus의 0.97배 |

  과제 단위 G5는 미충족으로 기록한다. E3의 판정은 수명 단위(G5-L)와 결함률이 한다(ADR-0102).
- **아직 재지 않은 것:** 누적 검증 비용(G7, H-AMORT)과 큰 코드에서의 효용 축.
  - 큰 코드의 축: 이해(H-COMPREHEND), 리팩터링(H-REFACTOR), 과업 달성(H-TASK), 그리고 규모와 무관함(H-SCALE·H-SLICE).
  - 주 측정 장은 포팅 쌍둥이다: stage0 Rust와 그 BMB 포트의 쌍(ADR-0104).

## 1. 무엇을 효용이라 부르나

쓰기 비용(배우기·쓰기 어려움, 증명 시간)은 설계가 받아들인 비용이다(DESIGN §2, ADR-0041). 효용은 그 비용으로 사는 것이고, 판정 단위는 쓰기 한 번이 아니라 과제 전체, 나아가 코드베이스 수명 전체다.

| 효용 축 | 주장 | 지표·가설 |
| --- | --- | --- |
| 테스트가 필요 없다 | 증명이 테스트를 대신해, 같은 품질에 테스트 코드가 거의 없다 | G8, H-ORACLE |
| 결함이 적다 | 증명 통과는 테스트 통과보다 숨은 결함을 덜 놓친다 | G5(결함), H-ORACLE, H-ENCAP |
| 도구로 읽는다 | 맵·질의로 필요한 것만 읽어, 규모가 커져도 읽기 비용이 늘지 않는다 | G4, H-VIEW, H-SLICE, H-SCALE, H-REUSE |
| 도구로 쓴다 | 정의 단위 편집이 파일 편집보다 싸고 안전하다 | H-GRAIN, H-EDIT |
| 바꿔도 안전하다 | 증명이 안정적이고, 재증명이 국소적이며, 동시 편집 충돌을 정확히 가른다 | H-STABLE, H-MAINT, H-ID, H-PAR, H-COMMUTE |
| 명세가 뜻을 붙잡는다 | 약한 명세를 거르고, 이름 대신 계약이 뜻을 전한다 | G3, H-SPEC, H-NAME |
| 누적 비용이 작다 | 증분 재증명이 테스트 반복 실행보다 싸다 | G7, H-AMORT |
| 결과물이 좋다 | 안전 Rust만큼 빠르고 훨씬 작다 | G6, G9 |
| 큰 코드에서 일이 된다 | 큰 코드베이스에서 이해·리팩터링·과업 달성의 성공률이 같거나 높고 비용이 작다 | H-COMPREHEND, H-REFACTOR, H-TASK, H-SCALE(ADR-0104) |

## 2. 축별 평가

근거 수준: **결정론**(재현되는 실험) > **정식**(동결 집합, 1회, ADR-0066) > **파일럿** > **미측정**.

### 2.1 테스트가 필요 없다 (G8) — 방향 일치, 이른 판단

- **정식(BRB, §6 B):** 같은 숨은 판정을 통과한 세션의 테스트 코드는 BMB 0줄이다. Rust는 sonnet 386줄(성공 세션당 16.1줄), qwen 2,083줄(86.8줄)이다. 파일럿도 0 대 834(opus)·0 대 1,277(haiku)이었다. 목표 "Rust의 1/10 이하"는 수치로는 넘는다.
- **이른 판단인 이유:**
  1. BRB 과제는 순수 함수 하나라 증명이 테스트를 대신하기 가장 쉬운 꼴이다. "남은 테스트 면적"(증명되지 않아 테스트가 필요한 정의, `test_needed_defs`)은 성공 세션에서 모두 0이고, 실패 세션에서만 남는다(sonnet 3세션 4개, qwen 2세션 2개). 입출력·상태·외부 의존이 있는 코드에서 남는 테스트 면적은 아직 재지 않았다.
  2. Rust 쪽 테스트가 실제로 무엇을 막았는지 보이지 않는다. 숨은 결함이 두 쪽 모두 0이라 "그 테스트가 없었으면 결함이 남았는가"를 모른다(§2.2).
- **효과가 있는 코드(T0-30, `bench/brb-effect`):** sonnet 두 팔 4/4에서 BMB의 남은 테스트 면적이 실행 정의의 4/6 = 0.667(기준 ≤ 0.2), 테스트가 필요한 코드 169줄 대 Rust 테스트 41줄이다. H-EFFECT 반증이다. 면적은 `io` 껍데기 정의 자체다. 원칙 4의 대체 범위는 순수 핵심으로 적었다(ADR-0102).
- **효용까지의 거리:** "테스트를 쓰지 않는다"는 관찰됐다. "테스트를 쓰지 않아도 품질이 같거나 낫다"는 §2.2가 판정될 때 성립한다.

### 2.2 결함이 적다 (G5 결함, H-ORACLE, H-ENCAP) — 판정 불가

- **정식:** 자기 검사 통과 & 숨은 실패가 sonnet BMB 0/21 대 Rust 0/24, qwen BMB 0/2 대 Rust 0/24다. 파일럿(opus, haiku)도 모두 0이다. 이 모델들에게 BRB 과제는 테스트만으로도 맞힐 만큼 쉽다.
- **결정론(도구 확인):** H-ENCAP 집합(`bench/brb-encap`)에서 불변식을 깨는 약한 해법을 Rust는 자기 테스트로 4/4 통과시키고, BMB 게이트는 4/4 거부한다. 측정 전 대본 확인이라 모델이 그런 해법을 쓰는지는 모른다(T0-21).
- **효용까지의 거리:** 가장 중요한 주장인데 근거가 가장 적다. 변별되는 어려운 과제(T0-08)와 H-ENCAP 실행(T0-21)이 처음 판정 가능한 측정이다.

### 2.3 도구로 읽는다 (G4, H-VIEW) — 정확도는 충족, 규모 효용은 미측정

- **정식(탐색 과제, §6 C):** 두 모델 모두 m1 5/5, m1b 12/12(P·R=1)다. M2 목표 "탐색 P·R=1 ≥ 80%"를 넘는다.
- **읽기 양:** m1b 코드베이스는 약 26KB(함수 약 116개)다. sonnet은 탐색 세션당 읽은 바이트 중앙값이 900바이트로 코드의 약 3.5%이고, 질의 1번으로 답한다. qwen은 18KB(약 70%)를 5.5번에 나눠 읽는다. 같은 도구에서 모델이 도구를 얼마나 정확히 쓰는지가 읽기 비용을 정한다.
- **작성 과제에서는 읽기 도구를 거의 안 쓴다(§6 D):** BRB의 BMB 세션에서 읽기 호출은 sonnet 3%, qwen 14%다. 과제가 함수 하나라 읽을 것이 없다. 읽기 효용은 이 규모에서 드러날 수 없다.
- **파일 기반과의 비교는 아직 없다.** G4의 핵심인 "파일 기반 대비 토큰 1/3 이하, 크기 무관"은 BNB(1만 정의, Rust 쌍둥이와 파일 도구)가 잰다. 질의 응답 크기와 시간이 코드베이스 크기와 무관하다는 결정론 근거(M1 ✅)만 있다. 정규형 투영(H-VIEW)은 같은 프로그램에서 토큰 13~15% 감소, 본문 없는 압축 투영은 코드의 0.44~0.59배로 재뒀다(결정론, 성공률은 T0-15).
- **효용까지의 거리:** 정확하게 찾는다는 것은 관찰됐다. 규모가 커질 때 싸게 찾는다는 것은 3단계 측정 전까지 주장할 수 없다.

### 2.4 도구로 쓴다 (H-GRAIN, H-EDIT) — 정식 근거, 표면 결정됨

- **정식(T0-13, `e5247e8d`, 같은 커밋 두 모델).** 원판(트랜잭션) → 쓰기 판(`write`):

  | 모델 | m1b | BVB | BRB |
  | --- | --- | --- | --- |
  | qwen | 23/25 → 23/25 | 24/45 → 37/45 | 7/24 → 18/24 (+46%p, D 넘음) |
  | sonnet | 25/25 → 25/25 | 45/45 → 45/45 | 20/24 → 24/24 |

  원판 실패의 큰 몫은 도구 호출 한도였고, 쓰기 판에서는 거의 없다.
- **비용(§6 A).**
  - sonnet의 성공당 토큰: m1b 133,025 → 67,478(−49%), BVB 39,377 → 13,650(−65%, Verus 14,125와 같은 수준), BRB 99,506 → 91,169.
  - 세션당 도구 호출 중앙값: BRB 17 → 3. Rust와 같은 수다.
- **결정:** 정식 측정의 표면은 `write`다(ADR-0101). 원판은 동결된 비교 기준으로 남는다.
- **남은 것:**
  - 파일 diff·JSON AST 표면과의 비교(T1-41, H-EDIT).
  - 큰 코드의 리팩터링(H-REFACTOR, ADR-0104).

### 2.5 바꿔도 안전하다 (H-STABLE, H-MAINT, H-ID, H-PAR, H-COMMUTE) — 결정론으로 입증

- **증명 안정성:** 의무 718개 × 의미 보존 변형 16개에서 판정 변화 0%다(H-STABLE).
- **재증명 국소성:** BCB 이력 재생에서 재증명 ⊆ `impact`다(H-MAINT).
- **이름 바꾸기:** 424건에서 다른 정의의 정체성 변화가 0건이다(이전 컴파일러 87%, H-ID).
- **동시 편집:** 교환 판정은 의미 충돌 192쌍·BCB 113쌍에서 위반이 0이다. 겹친 정의를 재증명하면 거짓 충돌도 0 대 `git merge-file` 3이다. 무엇보다 git은 병합이 실패해야 할 의미 충돌 58쌍 중 57쌍을 깨끗이 합쳐 버린다. 정의 단위는 58쌍 모두를 잡는다(H-COMMUTE, H-PAR).
- **효용까지의 거리:** 이 축은 모델 없이 판정되는 효용이고, 지금 가장 단단하다. 남은 것은 실제 에이전트 둘이 동시에 일할 때 이 성질이 비용을 줄이는지다(H-SPLIT, 3단계).

### 2.6 명세가 뜻을 붙잡는다 (G3, H-SPEC, H-NAME) — 모델에 따라 갈림

- **정식:**
  - BSB(숨은 명세 변이체 판별)는 sonnet 186/186(100%), qwen 126/186(67.7%)이다. M2 목표 ≥ 90%는 강한 모델에서만 충족한다.
  - BVB의 명세 강도 판정에서 "같은 뜻인데 미결정"이 두 모델 모두에서 나왔다(T0-19). 원인은 판정기 쪽(귀납, 재시도 특수화)과 언어 쪽(`exists` 없음)이고, 조치는 T0-24·T0-25다.
- **파일럿:** 이름을 무작위로 바꾸거나 오도해도 37/37, BSB 186/186이었다(H-NAME, BMB 쪽만).
- **효용까지의 거리:** 강한 모델에게는 명세가 뜻을 잘 붙잡는다. 판정기의 불완전성이 효용을 실제보다 낮게 잰다. T0-24가 그 몫을 줄인다.

### 2.7 작성 비용 (G5 토큰, H-FAMILIAR) — 과제 단위 미충족, 수명 단위 미측정

- **정식(§6 A), 쓰기 판의 성공당 토큰.**

  | 집합 | 모델 | BMB | 비교군 | 배수 |
  | --- | --- | --- | --- | --- |
  | BRB | sonnet | 91,169 | Rust 6,047 | 15.1배 |
  | BRB | qwen | 140,644 | Rust 59,563~109,821 | 1.3~2.4배 |
  | BVB | sonnet | 13,650 | Verus 14,125 | 0.97배 |

- **배수가 모델에 따라 갈리는 이유:** 강한 모델의 Rust 기준선은 BRB 과제 하나를 도구 호출 3번에 끝낸다. 과제 단위 2배 목표(ADR-0034)는 그 꼴에서 원리상 닿기 어렵다.
- **두 층 보고(ADR-0102):**
  - 과제 단위 G5는 **미충족**으로 기록하고 궤적을 본다. ADR-0041의 결과(크면 표면·도구를 고친다)는 그대로다.
  - E3의 판정은 수명 단위 G5-L(작성 + 후속 변경 + 결함 수리)과 결함률이 한다.
- **원인(세션 기록, `dev-docs/measurements/t0-10.md` §3.4·§6):**
  - BMB에만 있는 규칙을 오가는 데 든다. 그 일부는 ADR-0095의 입력 별칭·셰도잉 좁힘·`as` 정본이 줄였다.
  - 2R-05(qwen 3회, `dev-docs/measurements/2r05.md`) 결과:
    - 작성 성공률은 0.813 [0.711, 0.885]에서 0.920 [0.821, 1.000]으로, 구간이 겹쳐 실행 간 변동 안이다(방향은 세 회차 모두 같음).
    - 거부된 커밋은 60에서 26으로 줄었다. 되돌아온 쓰기의 비용이 줄었다는 뜻이다.
  - 해법기 미결정이 섞인다.
  - 작은 모델은 규칙을 추론으로 메운다.
- **남은 수단:**
  - 고정 문맥 축소(T0-17).
  - 압축 투영(T0-15).
  - 판정기 미결정 수리(T0-24).
  - 진단의 산문 수리 제안은 H-REPAIR가 qwen 1회에서 반증(수리 반복 1.26 대 0.88)이라, 다시 재기 전까지 새 투자를 멈췄다(ADR-0103 결정 5).
- **H-FAMILIAR:** 모델 차이가 팔 차이보다 크다. 쓰기 판에서 sonnet은 BVB의 성공률·비용 모두 Verus와 같은 수준이다.

### 2.8 누적 비용 (G7, H-AMORT) — 미측정

- BCB N=1,000은 동결과 측정 계획까지 됐다(2A-14e). 측정은 다른 CPU 일과 겹치지 않을 때 하거나, 겹쳐도 오염이 없음을 보인 뒤(INF-19) 한다.
- 설계상 BMB가 가장 크게 이겨야 할 축이다(테스트를 반복 실행하지 않고 바뀐 정의만 재증명). 아직 숫자가 없다.

### 2.9 결과물 (G6, G9) — 입증

- 성능은 안전 Rust의 ±5% 안이다(G6 ✅).
- 바이너리는 벤치 7개 약 14.5KB 대 342KB로 1/20 이하다(G9 ✅).

## 4. 이른 판단의 한계

1. **단일 실행:** 아래 표는 과제당 1회다. qwen으로 같은 커밋을 다섯 번 돌린 T0-12(`dev-docs/measurements/t0-12.md`)에서 작성 성공률의 범위가 m1 30%p(6/10~9/10), m1b 20%p(18/25~23/25)였다. 그래서 1회 측정끼리의 차이는 최소 차이 D = 30%p 이하이면 실행 간 변동 안으로 보고 방향을 주장하지 않는다(ADR-0077 §4). 반복 평균: m1 작성 76.0%(95% 구간 59.3~92.7%, 목표 60% 미정), m1b 84.0%(74.1~93.9%, 충족).
2. **과제 규모:** 함수 하나·정의 수십 개 규모라 읽기·누적 효용이 드러날 수 없다. 이 보고서의 "미측정" 대부분이 규모 문제다.
3. **작성자 편향:** 과제·하네스·컴파일러를 같은 에이전트가 만들었다.
4. **측정 조건:** 추론 토큰이 응답·세션 한도를 먹어 qwen의 BRB는 토큰 예산을 쟀다(T0-16, 다음 측정 차례부터 조건 수정 권장).
5. **판정기 불완전성:** 판정기의 "미결정"이 BMB를 실제보다 낮게 잴 수 있다(T0-19·T0-24).

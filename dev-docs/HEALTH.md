# 지속 관리 지침

> 결정: ADR-0039. 지표 계산: `scripts/health.py`. 기준선: `dev-docs/health/baseline.json`.
> 미션 목표(G1~G6)는 ADR-0034와 `docs/ROADMAP.md`에 있다. 이 문서는 그 아래에서 언어·도구·절차의 상태를 지속적으로 재는 방법이다.

## 1. 쓰는 법

```
python3 scripts/health.py                     # 래칫 확인(게이트가 매 커밋 실행), 실패 시 종료 코드 1
python3 scripts/health.py table               # 현재 값과 기준선을 표로
python3 scripts/health.py accept --reason "…"  # 현재 값을 기준선으로(이유가 이력에 남음)
scripts/ship.sh                               # 커밋된 트리에서 게이트 → 통과 시에만 푸시
```

- **개선**되면 게이트가 `improved:` 줄을 낸다. 같은 작업의 커밋에 `accept`로 반영한다(래칫을 조인다).
- **악화**되면 게이트가 실패한다. 먼저 고친다. 의도된 교환(예: 새 기능으로 증명 비용 증가)이면 백로그 태스크에 이유를 적고 `accept --reason "<태스크 ID>: …"`로 반영한다. 이 경우 AUTONOMY §6에 따라 한 줄 보고한다.
- **고정 규칙**은 `accept`로 넘길 수 없다. 완화는 ADR과 사람 승인이 필요하다.

## 2. 지표

| ID | 지표 | 규칙 | 왜 |
| --- | --- | --- | --- |
| V1 | 시험이 없는 진단 코드 수 | 고정 0 | 모든 진단에는 그것을 내는 시험이 있다 |
| V3 | 코퍼스·시드에서 증명되지 않은 정의 수 | 고정 0 | 기준 코드가 증명되지 않으면 회귀 |
| V4 | 코퍼스·시드 증명 비용 합(`rlimit`) | 예산 +10% | 인코딩 변경의 비용을 통제(벤치 부하 확장은 INF-11) |
| V5 | 가장 비싼 의무 / `Z3_RLIMIT` | 고정 ≤ 0.2 | 한도 근처의 증명은 시드·버전에 따라 깨진다 |
| V6 | 같은 입력의 `verify` 출력이 두 번 같은가 | 고정 참 | 결정론(원칙) |
| S1 | 외부 크레이트 수 | 고정 0 | 공급망·결정론, 포팅 범위 |
| S2 | 컴파일러가 실행하는 외부 프로세스 | 동일(바뀌면 ADR) | 신뢰 기반의 경계 |
| S3 | 생성 바이너리의 libc 밖 동적 의존 | 고정 없음 | 생성 코드의 자기 완결성 |
| S4 | stage0 Rust 줄 수(테스트 제외) | 보고 → 4D부터 예산 +2% | 기능 동결(ADR-0037 §3) |
| S5 | 라이브러리 API(`bmb::`)에 묶인 통합 시험 파일 수 | 래칫(감소만) | 포팅 뒤에도 쓸 수 있는 시험(CLI 경유) |
| S6 | BMB로 쓴 컴파일러 줄 수(`selfhost/`) | 래칫(증가만) | 포팅 진행 |
| P1 | 기대 출력이 있는 실행 프로그램 수 | 래칫 | 기능은 프로그램으로 보인다 |
| P2 | 저장소의 BMB 줄 수 | 래칫 | 실제로 쓰인 BMB의 양 |
| P3 | 반례·수정 제안이 붙은 오류 진단 비율 | 래칫 | 에이전트가 고칠 길 |
| O1 | ADR 파일과 색인의 불일치 수 | 고정 0 | 결정 기록의 정합성 |
| O2 | 건전성 퍼저 수 | 래칫 | 새 기능은 퍼저와 함께 |

현재 값은 `python3 scripts/health.py table`로 본다. 기준선 수립 시(2026-10-25) 값: V4 2,172,366, V5 0.0049, S2 {clang, z3}, S4 12,296, S5 30/31, P1 6, P2 3,578, P3 0.46, O2 6.

**알려진 한계:** V4·V5는 코퍼스와 벤치 시드만 본다. 1B-37 원안(모든 `i64` 배열에 범위 공리)은 BSB 킬 검사 2개를 한도 초과로 만들었지만, V4는 +1.0%만 움직였다. 벤치 부하의 비용은 INF-11에서 더한다.

## 3. 신뢰 기반(TCB)

"증명되었다"는 판정이 기대는 구성 요소와 각각을 확인하는 장치다.

| 구성 요소 | 틀리면 | 확인 장치 | 남은 위험 |
| --- | --- | --- | --- |
| 의미 인코딩(`verify.rs`) | 거짓 증명 | 건전성 퍼저 6종(독립 해석기 대조), 반례 재실행 | 퍼저의 검출력 미측정 → 1B-38 |
| Z3 4.15.4 | 거짓 증명·판정 불가 | 버전 고정(INF-02), 시드 안정성(`bmb stability`) | 단일 솔버 → 1B-39(승인) |
| 증명 캐시·증분 빌드 키 | 낡은 증명 재사용 | 캐시 무효화 시험, 캐시 유무 출력 동일 | — |
| 코드 생성(`codegen.rs`)·clang/LLVM 18 | 증명과 다른 실행 | 검사 제거 빌드와 전체 검사 빌드의 해석기 대조 | LLVM 최적화 자체는 신뢰 |
| libc·Linux | 실행 환경 | — | 신뢰 |
| stage0 씨앗(4G 이후) | 부트스트랩 오염 | 고정점, 씨앗 재현 절차 | ADR-0037 |

## 4. 자립 사다리

| 칸 | 조건 | 상태 |
| --- | --- | --- |
| L0 | 외부 크레이트 0, 외부 프로세스 {z3, clang}, 생성 바이너리는 libc만 | ✅ (S1·S2·S3) |
| L1 | 통합 시험이 CLI로 돈다 | S5 = 30/31, 4A-04 |

**남기는 의존:** Z3, LLVM/clang, libc, Linux(신뢰 기반). 벤치 하네스와 스크립트의 Python(표준 라이브러리만)은 언어 밖 측정 도구다. 4G 뒤에 BMB로 옮길지 정한다(5D-03).

## 5. 실용성 점검

1. 언어 페이즈(2B~2G, 2S)는 그 기능을 쓰는 실행 프로그램을 `tests/run/`에 2개 이상 더해야 닫는다. 2S·4C 뒤에는 입출력이 있는 실제 도구를 포함한다.
2. 쓰려다 못 쓴 것은 `dev-docs/measurements/m1.md` §6 마찰 표에 적고 처리 칸을 채운다. 빈 처리 칸이 있으면 페이즈를 닫지 않는다.
3. 오류 진단은 고칠 길(반례·수정 제안)을 준다. 비율 P3는 내려가지 않는다.

## 6. 점검 주기

| 주기 | 할 일 |
| --- | --- |
| 매 커밋 | `scripts/ship.sh`(게이트 + 래칫 + 푸시) |
| 매일 | 야간 장기 퍼징(INF-07), 성능 회귀(INF-12) |
| 페이즈 종료 | 종료 감사(AUTONOMY §3.2) + `health.py table` 출력을 `dev-docs/health/<페이즈>.md`로 커밋하고 다섯 축(M·V·S·P·O)을 한 표로 보고 |
| 실제 모델 측정 뒤 | G1~G6 갱신. 못 미친 지표마다 원인 조사 태스크 |

## 7. 지표 자체의 점검

지표가 회귀를 못 잡으면 지표가 틀린 것이다. 실제로 일어난 회귀마다 "어느 지표가 잡았어야 했나"를 묻고, 없으면 지표나 시험을 더한다(예: 1B-37 → INF-11). 증명기 검출력(1B-38)은 이 원칙을 계획적으로 적용한 것이다.

# 문법 1차 평가 (2R-02)

> 상태: 1차 평가. 저울은 ADR-0036이다. 실제 모델 근거(2R-03·2R-05)가 아직 없어 C1(사전 지식 전이)은 **예측**이다. 측정값은 모두 오프라인 결정론적 측정(E1)이다.
> 재현: `python3 bench/syntax/measure.py`, `--uses-experiment target/release/bmb`, `--trigger-experiment target/release/bmb`(`--seed GLOB`로 코퍼스 교체), `--probe target/release/bmb`. 컴파일러는 커밋 9426c7d 기준이다.

## 1. 방법과 한계

- **읽기 코퍼스.** `bench/m1b/seed`의 정본이다. 단위 9개, 정의 116개(`fn` 53, `spec fn` 63), 26,051바이트(≈6,513토큰)다. 슬라이스와 맵이 보여 주는 형태다.
- **쓰기 코퍼스.** m1·m1b 작성 과제 36개의 기준 해법(`put`)이다. `fn` 41개, `spec fn` 67개, 23,703바이트다. 과제를 통과하려고 에이전트가 내야 하는 형태다.
- **토큰.** 어휘 토큰은 BMB 렉서의 근사다. 어휘 토큰마다 구성 하나에 배정하므로 합이 100%가 된다. 바이트 근사는 ADR-0021의 `ceil(bytes/4)`다.
- **습관 반응.** 한 줄 형태 69개(받아들여지는 대조 형태 포함)를 `bmb check`에 넣어 진단 코드와 `fix.replacement` 유무를 확인했다(§2.4). 입력은 `bench/syntax/habit_probes.txt`에 있고, `--probe target/release/bmb`가 형태마다 첫 진단의 코드와 수정 종류를 출력한다. 첫 진단이 다른 원인이면(예: `g(x)?`의 미정의 `g`) 전체 진단을 따로 확인했다.
- **한계 1(작성자 편향, m1 §2).** 코퍼스는 컴파일러를 만든 에이전트가 썼다. 그래서 도출률이 높게 나올 수 있다. 예: 트리거를 항상 첫 `a[k]`에 둔 습관.
- **한계 2(규모).** 정의 116개다. `#[uses]` 기본 규칙의 증명 안정성은 큰 코퍼스(m3)와 시드 변동(`bmb stability`)으로 다시 재야 한다.
- **한계 3(C1).** 실제 모델 로그가 없다. 아래 C1 판단은 형태가 유효한 Rust·Verus인지, 습관 진단에 기계 수정이 있는지에서 나온 예측이다.

**정리.** `#[uses]`·`#[effects]`·`#[trigger]`(변수 하나)·`let`의 타입·`-> ()`는 이 코퍼스에서 100% 도출된다. 합치면 읽기 토큰의 15.9%, 쓰기 토큰의 12.9%다(트리거는 `spec fn` 몫과 겹친다). 루프 경계 상용구 4.4%와 2.6%는 형태가 정해진 꼴이다. 이 몫에는 에이전트의 판단이 없다. 그런데 지금은 에이전트가 직접 써야 하고, 빠뜨리면 커밋이나 증명이 실패한다. m1 §6의 "`#[uses]` 누락이 반복되었다"가 그 사례다.

### 2.3 이름 붙은 술어 규칙(원칙 3, E0501)

| 측정 | 읽기 | 쓰기 |
| --- | ---: | ---: |
| `spec fn` 수 | 63 | 67 |
| 계약 절 하나에서만 쓰이고 다른 곳에서는 안 쓰이는 술어(단일 사용) | 32(51%) | 47(70%) |
| 단일 사용 술어의 머리(`spec fn 이름(매개변수) -> bool { }`) 토큰. 인라인이면 사라지는 몫의 하한 | 662(**8.7%**) | 963(**11.3%**) |
| 계약 절에 쓰이지 않는 술어(불변식·다른 술어 전용) | 12 | 19 |
| 양화사 없는 술어 | 42 | 28 |
| 본문이 같은 동의어 묶음(`query duplicates`) | 2묶음 6정의: `r <= a.len()` 넷(`count_ok`·`descents_bound`·`count_bound`·`at_most_len`), `i < a.len()` 둘(`idx`·`acct`) | — |

- E0501에는 `replacement`가 없다. 안내 문구만 있다.
- Verus는 계약 절에 임의의 식을 받는다. `ensures r == x,`는 Verus 사용자에게 가장 흔한 형태다. 예측 C1 손실이 크다.
- 같은 함수의 루프 `invariant`와 `assert`는 인라인 식을 받는다(`invariant k <= a.len(), c <= k,`). 계약만 이름을 요구하는 비대칭이다. 원칙 3을 계약에만 적용한 결과다.
- 이름의 이득은 둘이다. 하나는 L1·`contracts PRED` 질의가 술어 이름으로 답한다는 것이다(m1b 탐색 과제 n08·n09가 이것에 기댄다). 다른 하나는 동등 규약 병합(DESIGN.md §8.1)이다. 다만 병합은 아직 구현되지 않았다(3D). 동의어 6정의가 보여 주듯 이름이 같은 조건을 하나로 모아 주지도 않는다.

**관찰**
- 습관 지표(ADR-0021, E02xx / `tx_commit`)는 위 습관의 절반 이상을 세지 않는다. E0303·E0501·E0103·E0211·E0402·E0404·E0301이 그렇다. 특히 **Verus 습관은 하나도 E02xx로 나오지 않는다.** `int`, `0 <= i < n`, `exists`, `open spec fn`, `@`, `#![auto]`, `by(..)`이 그 예다. BMB의 비교 대상이 Verus(BVB, ADR-0034)인데 Verus 습관이 측정 밖에 있다. ADR-0036 §6이 2R-03에서 이를 따로 세게 했다.
- `+=`는 진단 표·설계 문서 어디에도 결정으로 적혀 있지 않다. 일반 구문 오류로만 거부된다. 시드에는 `x = x op e` 꼴 대입이 33개, 기준 해법에는 36개 있다.

## 3. 구성 목록과 1차 평가

**표기**
- 출처: R = Rust, V = Verus, 신 = 신규.
- 현행: 설계(DESIGN.md·ADR)가 함의하는 판정. "차용(필수화)"는 Rust에서 선택인 표기를 필수로 만든 것이다.
- 잠정: 저울(ADR-0036)에 따른 1차 판정. "+별칭"은 정본은 그대로 두고 쓰기 표면에서 습관 형태를 받아 도구가 옮기는 입력 별칭(ADR-0036 §1)이다.
- 증거 수준은 E0(논증)·E1(오프라인 측정)이다.

## 4. 교차 관찰

1. **판단 없는 표기가 쓰기 실패의 원인이 된다.** §2.2의 100% 도출 표기와 경계 상용구가 쓰기 토큰의 약 15%다. 이 표기들은 지금 에이전트가 써야 하고, 빠뜨리면 커밋 거부(E0201·E0209·E0601·E0511·E0506)나 증명 실패(`#[uses]` 누락)가 된다. 원칙 6("명시성은 산출물의 성질이고, 그 노동은 도구의 몫")에 비추면 거꾸로다. 그 노동을 지금은 에이전트가 진다. 정본의 명시성은 지키되 쓰기 표면에서 받아 주는 쪽이 저울(O1·O3)상 우세하다.
2. **습관 지표가 습관의 일부만 센다.** §2.4. 2R-03은 ADR-0036 §6 대응표로 다시 센다.
3. **기계 수정의 공백과 결함.**
   - E0303·E0501·E0211·E0203·E0204·E0205·E0506·E0511, 절 순서, `+=`에는 `replacement`가 없다.
   - E0104의 16진 수정은 값을 바꾼다. `bmb fix` 자동 적용을 넓히기 전에 고쳐야 한다(백로그 후보).
   - `vec!` 수정은 2G에서 의미가 바뀐다.
4. **비대칭.**
   - 계약은 이름 붙은 술어만 받는데, 불변식과 `assert`는 인라인을 받는다.
   - 내장 메서드(`len`·`wrapping_*`, 제안 `push`)는 메서드 구문인데, 사용자 함수는 메서드 구문을 금지한다(ADR-0026).
   - 내장 `print_i64`는 맨이름인데, 내장 `Option::Some`은 전체 경로를 요구한다(제안).

   각각 근거가 있지만, 에이전트가 하나의 규칙으로 일반화하기 어렵다. 예측 C1 손실이다.
5. **Verus 습관은 측정과 진단 밖에 있다.** BVB(Verus 대비 +10%p)가 목표인데 `int`, 연쇄 비교, `exists`, `open spec fn`, `@`, `#![auto]`, `by(..)`가 모두 E0103·E0211·E0402로 끝나고 수정이 없다.
6. **반대 방향의 근거도 있다.** 다음 구성은 저울에서 현행이 우세하므로 바꾸지 않는다.
   - 경로 호출(K3)
   - 셰도잉 금지(C4 반례 이름)
   - 와일드카드 금지(`impact` 일치)
   - 모든 지역 타입 명시(슬라이스 자급)
   - 2급 참조(ADR-0015)

   이 구성들에 필요한 것은 형태 변경이 아니라 쓰기 표면의 입력 별칭과 기계 수정이다.

## 6. 2R-03·2R-05가 잴 것

**2R-03(1E-10·2A-06 로그, 실제 모델)**
- 구성별 습관 진단 빈도. ADR-0036 §6 대응표로 E02xx 밖의 습관도 센다. 특히 E0303, E0501, E0103 하위 분류(`+=`·`exists`·`open`·`@`), E0211, E0402(`int`), E0205, E0203, E0204, E0601, E0511, E0506을 본다.
- 증명 실패 중 `#[uses]` 누락에 따른 것의 비율. 진단 `fix`가 펼치지 않은 술어를 대는 E0801·E0802(1D-13)로 센다.
- 첫 커밋에 의미 보존 자동 수정을 적용했다면 통과했을 비율(재생).
- 세션 출력 토큰의 구성별 점유. §2.1과 같은 분류를 에이전트 출력에 적용한다.
- 반례를 보고 고친 비율. 셰도잉 개명을 하면 반례 이름이 바뀌므로 C4 근거가 된다.

**2R-05(쌍둥이 A/B, 사용자 머신)**
- 상위 1·2·6은 문법만 바꾼 쌍둥이 과제 집합(m1b 기반, 새 이름으로 동결)으로 잰다. 1회 성공률(G2), BSB 판별률(G3: 특히 2번 인라인 계약), 습관율, 총 토큰을 본다.
- 3·4는 2C·2B 구현이 있어야 한다. 기능 과제를 쓰는 쌍둥이로 잰다.
- 5는 같은 과제에서 "커밋 거부" 대 "커밋 시 자동 수정"의 두 하네스 설정으로 잰다. 측정 조건(MCP 문구 고정, m1 §1)을 바꾸므로 1E-10 뒤에 한다.
- 판정 문턱은 ADR-0036 §5다. 쌍둥이에서 대안만 성공한 과제 수가 기존만 성공한 과제 수보다 3개 이상 많아야 한다.

## 7. 발견한 결함(백로그 후보)

- **E0104의 16진 리터럴 수정이 값을 바꾼다.**
  - 재현: `0x10`에 `bmb fix --print`를 돌리면 `0`이 된다(`compiler/src/lexer.rs`의 접미사 분해가 `x10`을 접미사로 본다).
  - 기대: 16진 리터럴을 따로 진단한다(10진 값으로 바꾸는 `replacement`, 또는 수정 없음).
- **`vec![..]` → `[..]` 수정은 2G 채택 때 다시 정해야 한다**(M4).

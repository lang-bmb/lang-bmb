# ADR-0062: 증명 함수(`proof fn`)와 귀납: 사용자가 쓰는 보조 정리

- 상태: 제안 (2026-10-28 초안. 언어 범위 확대라 채택은 사람 승인, AUTONOMY §4)
- 날짜: 2026-10-28
- 관련: ADR-0017 §4(불투명 `spec fn`, `#[uses]`), ADR-0018 §2(컴파일러 보조 사실과 `tests/lemmas.rs`), ADR-0023(기저 인스턴스 재시도), ADR-0032·0043(증분 키), ADR-0049(`return`·제어 흐름), ADR-0058(트랙, T1·T4), 백로그 T1-14, DESIGN §3 원칙 4·6

## 맥락

BMB에는 사용자가 쓰는 보조 정리가 없다(`compiler/README.md` 표면 규칙에 `proof fn`·`lemma`가 없다). 증명기가 재귀 `spec fn`에 대해 아는 것은 세 가지뿐이다.

- 정의 공리: 양화된 정의식 하나(`verify.rs:4731` `Prog::axiom`).
- 기저 인스턴스 재시도: `unknown`일 때 나타난 적용을 3단계까지 펼친다(ADR-0023, `verify.rs:5480` `ground_instances`).
- 호출의 계약: 호출자는 피호출자의 `requires`를 증명하고(`verify.rs:4133`, E0801) `ensures`를 가정한다.

귀납이 필요한 사실은 이 셋으로 나오지 않는다. "재귀로 정의한 술어 ⇔ 한정 기호로 쓴 술어", "앞부분에서 성립하면 한 칸 늘려도 성립", "두 조각을 이으면 정의가 이어진다" 같은 사실이다. 이번 세션에서 세 곳에서 드러났다.

1. **파일럿 T1-14.** BVB `vc-vv0039-max-of-list`에서 에이전트의 계약 `contains(lst, r)`은 숨긴 계약 `!(forall i. lst[i] != r)`과 같은 뜻이다. `contains`는 재귀 `contains_prefix`로 정의되어 있다. 그런데 숨긴 명세 강도 검사가 "solver could not decide"로 끝나 실패로 기록됐다. 함의에 `contains_prefix`에 대한 귀납이 필요했기 때문이다.
2. **T4 라이브러리.** UTF-8 검증(T4-02), JSON 파서(T4-05), SHA-256(T4-01)의 자연스러운 명세는 "입력이 올바른 조각들의 이음"이다. 이것은 재귀 `spec fn`으로 쓰고, 루프 불변식을 한 칸 늘리는 데 귀납 보조 정리가 필요하다.
3. **2K-06 `numlist`.** 자릿수 불변식이 "경우별로 손으로 펼친 술어"를 요구했다(`dev-docs/health/2K.md` 실용성 절, `dev-docs/measurements/m1.md` §6).

`tests/lemmas.rs`(ADR-0018 §2)는 컴파일러가 신뢰 기반에 넣는 사실을 Z3로 증명하는 곳이다. 사용자 프로그램의 보조 정리를 둘 자리가 아니다.

## 선례 (JUDGMENT S1 순서)

| 출처 | 방식 | 확인 |
| --- | --- | --- |
| Rust | 해당 없음(증명 없음) | — |
| Verus | `proof fn`: `requires`·`ensures`·`decreases`를 갖는 유령 함수. 몸에서 다른 `proof fn`을 (재귀 포함) 부르고 `assert`·`if`·`match`로 경우를 나눈다. 실행 코드에서는 `proof { lemma(x); }` 블록 안에서 부르고, 코드 생성에서 지워진다. 귀납은 재귀 호출로 쓴다(자동 귀납 없음) | [induction](https://verus-lang.github.io/verus/guide/induction.html), [decreases](https://verus-lang.github.io/verus/guide/reference-decreases.html). 이 환경에서 원문이 열리지 않아 검색 요약으로 확인(원문 미확인) |
| Dafny | `lemma`(유령 메서드). 정수·자료형 매개변수의 보조 정리에는 자동 귀납 발견법이 적용된다(`{:induction}`으로 조절) | 원문 미확인(검색에 나오지 않음) |
| Why3 | `lemma`(공리처럼 쓰이는 정리, 별도로 증명), `let lemma` 함수로 귀납 | 원문 미확인 |
| F*·Lean | 전술·증명 항 | 범위 밖(AI가 쓰기 어려운 표면, DESIGN §4 "더 장황한 Rust"와 거리) |

## 결정 (제안)

### 1. 표면

```rust
#[uses(contains, contains_prefix)]
proof fn contains_has_index(a: &[i64], n: usize, r: i64)
    requires n <= a.len(), contains_prefix(a, n, r),
    ensures has_index_below(a, n, r),
    decreases n,
{
    if n > 0 && a[n - 1] != r {
        contains_has_index(a, n - 1, r);
    }
}

#[effects(pure)]
#[uses(contains, contains_prefix, ge_all)]
fn max_of_list(lst: &[i64]) -> (r: i64)
    requires non_empty(lst),
    ensures contains(lst, r), ge_all(lst, r),
{
    // ...
    proof { contains_has_index(lst, lst.len(), m); }
    m
}
```

- `proof fn`은 Verus 표기를 그대로 쓴다. 학습 분포 안의 표면이고, 원장의 "선택을 필수로" 규칙과 충돌하지 않는다.
- 반환 타입은 `()`뿐이라 쓰지 않는다. Verus와 같다. 정규형은 이 생략 하나를 예외로 둔다.
- 효과 속성은 붙이지 않는다(E0256이 거부). `spec fn`처럼 효과가 없다. 실행 함수의 "효과 필수"(원장 "효과") 규칙은 실행 코드에 대한 것이다.
- `requires`·`ensures`는 실행 함수와 같은 규칙을 따른다(이름 붙은 술어 호출, E0501). 재귀 `proof fn`과 상호 재귀에는 `decreases`가 필수다(E0507과 같은 검사).
- **부르는 곳**
  - 실행 함수 안의 `proof { .. }` 블록. 문장 자리에만 오고 값을 내지 않는다.
  - 다른 `proof fn`의 몸(블록 없이).
  - 루프 몸 안의 `proof` 블록도 된다(불변식 유지를 돕는 자리).
- **`proof` 블록 안에 오는 것:** `proof fn` 호출, `assert`, `if`·`match`(경우 나누기), 명세 식만 쓰는 `let`. 실행 함수 호출, 대입, `&mut` 인자는 오지 못한다(E0257: 유령 문맥에서 실행 상태를 바꾸거나 읽을 수 없다).
- `proof fn`의 매개변수는 값과 `&T`뿐이다. `&mut`은 E0257이다. 유령 상태를 실행 코드로 내보내는 길이 없다.

### 2. 의미와 인코딩

- **`proof fn` 자체의 증명은 실행 함수와 같다.** 몸을 기호 실행해 `ensures`를 의무로 낸다(`post_check`). `assert`와 호출 전제는 의무다. 넘침·인덱스 의무는 없다. 몸은 명세 식이고, 명세 산술은 수학적 정수다(ADR-0017).
- **호출은 계약 장치 그대로다(`verify.rs:4098` `call`).** `requires`를 증명하고(E0801), 재귀 성분 안이면 `decreases` 감소를 증명하고(E0809), `ensures`를 가정한다. 새 신뢰 사실은 없다. 보조 정리의 결론은 그 증명이 게이트를 통과했을 때만 쓰인다.
- **귀납은 재귀 호출이다.** 구조적 귀납·수 귀납 모두 `decreases`가 있는 재귀 `proof fn`으로 쓴다. 건전성은 실행 함수 재귀와 같은 종료 의무가 준다.
- **`#[uses]`는 그대로다.** 보조 정리도 불투명 술어를 펼치려면 선언한다(ADR-0017 §4). 보조 정리를 부르는 쪽은 결론만 쓰므로 펼칠 필요가 줄어든다. 이것이 증명 안정성의 이득이다(무관한 문맥을 빼는 원장 "증명 자동화" 행의 연장).
- **지움:** 코드 생성은 `proof fn`과 `proof` 블록을 내보내지 않는다. 런타임 비용은 0이다. IR에 흔적이 없다는 것은 시험으로 확인한다.

### 3. 맵·증분·캐시

- `proof fn`은 맵 L0·L1에 정의로 나온다(`def_kind: "proof fn"`). L2에는 `proof_calls` 엣지가 생긴다(누가 이 보조 정리에 기대는가). DESIGN §7.2의 "증명 의존" 뷰가 이 엣지에서 나온다.
- 증분 키(ADR-0032·0043)는 피호출자 계약을 담는 지금 규칙 그대로다. 보조 정리의 몸이 바뀌어도 계약이 그대로면 부르는 쪽을 다시 증명하지 않는다(계약 방화벽).
- 해시(ADR-0019, 제안 ADR-0059)는 다른 정의와 같다.

### 4. 진단 (번호는 잠정, 채택 때 `compiler/src/diag.rs`에서 확정)

| 코드 | 뜻 | 안내 |
| --- | --- | --- |
| E0256 | `proof fn`에 효과 속성이나 반환 타입 | 지우기(`bmb fix`) |
| E0257 | 유령 문맥(`proof fn` 몸, `proof` 블록)에서 실행 함수 호출·대입·`&mut` | 명세 식으로, 또는 블록 밖으로 |
| E0258 | `proof fn`을 `proof` 블록 밖의 실행 코드에서 부름 | `proof { .. }`로 감싸기(`bmb fix`) |

E0254·E0255(ADR-0060 초안), E0815·E0818·E0820·E0823(채택·제안 ADR)과 겹치지 않는다.

### 5. 자동 귀납은 도구로 (나중)

- 기계적으로 정해지는 보조 정리는 도구가 쓴다(DESIGN 원칙 6). 재귀 `spec fn` 하나의 정의를 따라가는 "앞부분 확장" 꼴과 "재귀 ⇔ 한정 기호" 꼴이 그런 예다.
- `bmb fix`가 의무 실패 진단(E0811 "solver could not decide")에서 그런 꼴을 알아보면 `proof fn` 초안과 호출 자리를 제안한다. 채택은 에이전트가 한다.
- 이것은 언어가 아니라 도구 결정이다. 이 ADR은 그 도구가 내놓을 자리(사용자 `proof fn`)만 정한다.

## 근거 (JUDGMENT §10)

1. **문제.** 귀납이 필요한 사실을 표현할 수 없다.
   - 그래서 같은 뜻의 명세가 판정에서 떨어지고(T1-14), 정석 명세(재귀 술어로 쓴 형식 문법)의 루프 불변식을 증명할 수 없다(T4).
   - 사람이 경우별 술어를 손으로 펼치는 우회가 생긴다(2K-06).
2. **원인과 귀속 층.** 언어. 정석 해법(보조 정리로 귀납 사실을 세우기)을 표현할 수 없다(JUDGMENT §3 둘째 행, §7 판단 질문 1).
   - 컴파일러 층(더 깊은 기저 인스턴스, 더 좋은 트리거)으로는 고칠 수 없다. 귀납은 1차 SMT의 결정 범위 밖이다.
   - 기저 인스턴스를 깊게 해도 유한 펼침일 뿐이다(ADR-0023 결과 절).
3. **정석 해와 출처.**
   - 검증 언어의 보조 정리: Verus `proof fn`, Dafny `lemma`, Why3 `lemma`(S1 b).
   - Rust 꼴 표면과 유령 지움은 Verus가 직접 선례다.
4. **후보 비교.**

## 결과

- **DESIGN §4.1 원장:** 새 행이 필요 없다. "증명 자동화" 행의 "증명마다 사용할 사실 선언"을 보조 정리로 넓히는 것이고, 그 행의 "얻는 것"(증명 안정성)을 그대로 산다. "정의는 기본 불투명" 옆에 "귀납 사실은 `proof fn`으로 명시"를 더한다.
- **가설 등록부:**
  - T1-14의 실패 부류("같은 뜻의 명세가 해법기 미결정으로 떨어짐")가 판정기 결함에서 "에이전트가 보조 정리를 쓸 수 있었는가"로 바뀐다. 판정기(숨은 명세 강도 검사)도 에이전트의 `proof fn`을 작업 공간에서 함께 쓴다.
  - H-FAMILIAR(BVB): Verus 팔은 이미 `proof fn`을 쓸 수 있다. BMB 팔에 없으면 같은 과제에서 BMB가 표면 때문에 불리하다. 공정한 비교의 전제다.
- **여는 것:** UTF-8 검증(T4-02)과 JSON 파서(T4-05)의 "올바른 조각들의 이음" 명세, SHA-256(T4-01)의 블록 반복 명세, BVB의 재귀 명세 과제.
- **제안 태스크(번호는 백로그에서):**

  | 태스크 | 확인 |
  | --- | --- |
  | P1 표면과 검사: `proof fn`, `proof { }`, 유령 문맥 규칙, E0256~E0258, 정규형 | 오류 코퍼스(모든 줄에 안내), 서식 퍼저 왕복 |
  | P2 인코딩: `proof fn` 몸의 증명, 호출 의무·가정, 재귀 감소 | 맞는 코퍼스(재귀 ⇔ 한정 기호, 앞부분 확장, 이음), 틀린 코퍼스(거짓 결론에 반례, 감소 실패) |
  | P3 지움과 맵: 코드 생성에서 제거, L1 `def_kind`, L2 `proof_calls`, 증분 키 감사 | IR에 흔적 없음 시험, `tests/incremental.rs` 감사, 결정론 |
  | P4 퍼저·검출력 | `soundness_specs` 확장, 변이체 셋이 게이트에 잡힘 |
  | P5 실용: `vc-vv0039`의 같은 뜻 명세를 보조 정리로 증명, `numlist` 이주, UTF-8 검증의 이음 명세 | 실행 프로그램 2개 이상(HEALTH §5) |

## 열린 질문

1. 명세 강도 판정(숨은 검사)이 귀납이 필요한 같은 뜻 명세를 어떻게 다룰지. 에이전트가 보조 정리를 함께 내면 판정은 그대로 둔다. 판정기가 결정 못 한 경우를 따로 보고하는 것(`spec_rejections`의 `undecided`)은 이미 했다.
2. `forall` 도입(임의의 `i`에 대해 보이기)을 Verus의 `assert forall .. by { }` 꼴로 둘지, 보조 정리 호출로만 할지.
3. `proof` 블록이 실행 코드의 정규형에서 어디에 오는지(문장 순서 규칙).

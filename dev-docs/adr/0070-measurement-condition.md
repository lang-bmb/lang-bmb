# ADR-0070: 같은 측정 조건은 커밋이 아니라 모델이 보는 것과 판정으로 정한다(ADR-0066 §3 보완)

- 상태: 채택 (사람 승인 2026-10-31: "권장안 채택". 2026-10-31 실행 계획의 승인 안건)
- 날짜: 2026-10-31
- 관련: ADR-0021(측정 절차, 동결), ADR-0066 §3·§5(교차 비교는 같은 커밋, (집합, 모델, 커밋)마다 한 번), 백로그 INF-17·INF-18·T0-11, JUDGMENT §10

## 맥락

- ADR-0066 §3은 교차 비교를 "같은 하네스·같은 커밋"으로 정했다. 커밋은 조건의 대리 지표다. 모델이 보는 것(컴파일러의 진단·증명·도구 설명, 동결 과제, 프롬프트, 어댑터가 만드는 요청)과 판정이 같으면 같은 조건인데, 커밋은 측정과 무관한 수정까지 다른 조건으로 만든다.
- T0-10(qwen)은 결과 행에 판정 필드만 남겼다. 하네스가 작업 공간을 지우고 호출 기록을 남기지 않아 실패 원인을 볼 수 없다(BVB 실패 13개 중 10개가 "증명되는 커밋, 서명 다름"). 세션 기록(INF-17)을 더하면 커밋이 바뀐다. 그러면 ADR-0066 §3 때문에 T0-11(sonnet)은 기록 없이 옛 커밋에서 돌아야 한다. 측정 머신도 게이트웨이 생성에 묶여 세션당 약 10분인데, 병렬 세션(INF-18)도 같은 이유로 쓸 수 없다.

## 결정

1. **같은 조건의 정의.** 두 실행은 집합마다 다음이 모두 같을 때 같은 조건이다. (a) `bmb`를 빌드한 `compiler/` 트리. (b) 동결 과제 입력: 집합의 MANIFEST(숨은 변이체 MANIFEST 포함). BRB MANIFEST가 함께 고정하는 계기 코드(`harness.py`·`judge.py`·`rust_tools.py`)는 제외한다. (c) 하네스: 같은 대본 모델로 두 하네스를 돌렸을 때 모델이 받는 요청 본문 전체와 결과 행의 판정 필드가 바이트 단위로 같다. 나중 하네스가 더한 필드와 `*_seconds` 시간은 비교하지 않는다.
2. **확인 도구.** `bench/condition.py same --base COMMIT --sets ...`가 (b)·(c)를 확인하고 보고서 `bench/conditions/BASE-HEAD.json`을 쓴다. 대본은 둘이다. `oracle`은 기준 해법 뒤 멈춤이고, `stress`는 기준 해법 뒤 없는 도구, 깨진 인자, 호출 한도 넘김이다. 공급자는 둘(`openai`, `anthropic`)이고 실제 어댑터에 가짜 전송을 붙인다. 보고서는 커밋해 근거로 남긴다.
3. **실행.** `run_models.py --same-as COMMIT`은 (a)를 구성으로 지킨다. COMMIT의 컴파일러로 빌드한 `bmb`(`condition.py build`, 출처 `provenance.json`)를 쓴다. 집합마다 보고서가 있어야 시작하고, 보고서 뒤로 `bench/`의 하네스가 바뀌었으면 거부한다. 결과 머리 줄과 요약에 `condition`(기준 커밋, 컴파일러 트리, 바이너리 해시, 보고서)을 남긴다.
4. **ADR-0066 §3의 "같은 커밋"을 이것으로 바꾼다.** 교차 비교는 같은 조건이면 된다. §5의 "(집합, 모델, 커밋)마다 한 번"은 그대로이고, `--same-as` 실행은 자기 커밋의 한 번이다.
5. **(c)가 닿지 않는 곳.** 실제 모델만 가는 어댑터 경로(`length` 종료, API 오류)는 대본이 지나가지 않는다. 그 경로의 코드는 기준 커밋과 같아야 한다고 보고서 사용자가 확인한다. `f83cd47d` 뒤 `model_api.py`·`anthropic_agent.py`에서 바뀐 것은 요청 기록(`requests`, 행에 없음)과 선택 기록(`BMB_CONTEXT_LOG`, 2D-25, 측정에서 끔)뿐이다.

## 근거

- **원인과 층(JUDGMENT §3):** 측정 후 귀속이 막힌 원인은 프로세스 규칙이다. 조건을 대리 지표로 정해, 계기 개선이 비교 가능성을 깬다. 언어·컴파일러 층의 문제가 아니다.
- **정석(S1):** 실험에서 처치와 측정 계기를 버전으로 묶을 때, 계기를 바꾸면 보정(같은 입력에 같은 출력)으로 동등함을 보인다. 여기서는 같은 대본 입력에 대한 요청 본문과 판정이 보정 기준이다. 코드 해시 비교는 기록 기능 하나를 더해도 다르다고 해서 너무 엄격하다. 아무것도 보지 않으면 너무 느슨하다.
- **대안:** (가) 커밋 유지. T0-11이 기록 없이 직렬로 돌고, 교차 비교의 실패도 귀속할 수 없다. (나) 하네스 파일 해시를 조건에 넣음. 기록 기능 자체가 하네스 수정이라 (가)와 같다. (다) 하네스 밖 래퍼로 기록. 동결 파일을 안 바꾸지만, 한도에 걸린 마지막 호출의 결과를 놓치고 원숭이 패치에 기댄다. (라) 이 결정. 갈린 기준은 조건이 "모델이 보는 것과 판정"이라는 정의다.
- **확인한 것(2026-10-31):** `f83cd47d`·`8d569693`의 하네스는 m1에서 지금 하네스와 같았다(대본 둘, 공급자 둘). 하네스의 오류 접두어 한 글자를 바꾸면 요청 본문 차이로, 판정 필드를 바꾸거나 지우면 행 차이로 잡힌다(`bench/test_condition.py`).

## 결과

- T0-11부터 세션 기록(INF-17)과 병렬 세션(INF-18)을 쓴다. 집합마다 T0-10의 커밋을 `--same-as`로 둔다. m1·m1b는 `8d569693`, 나머지 넷은 `f83cd47d`다. 그 컴파일러를 빌드하고 보고서를 커밋한 뒤 실행한다.
- 하네스를 고칠 때 비교가 필요한 이전 측정이 있으면 `condition.py same`을 돌린다. 다르게 나오면 그 수정은 조건 변경이다(새 측정, ADR-0066 §5).
- BRB MANIFEST가 계기 코드를 함께 고정하는 것은 그대로 둔다. 계기 코드를 고치면 MANIFEST를 다시 쓰고, 같음은 (c)가 보인다.
- 비용: 집합마다 확인 한 번(과제마다 세션 여덟: 대본 둘·공급자 둘·트리 둘), 기준 커밋마다 컴파일러 빌드 한 번.

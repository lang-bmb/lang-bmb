# ADR-0025: 두 번째 과제 집합 `m1b`

- 상태: 채택 (자율 채택, AUTONOMY.md §4)
- 날짜: 2026-10-24
- 관련: ADR-0016(M1 범위), ADR-0021(측정 절차), ROADMAP 2A, 백로그 2A-01~2A-05

## 맥락
`m1`(ADR-0021)은 정의 23개 시드와 과제 15개다. 2단계 통과 기준은 "1E보다 넓은 과제 집합에서 측정 5종이 악화되지 않는다"이고(ROADMAP 2단계), 그 집합은 기능보다 먼저 동결되어야 한다(genesis §3.5). `m1`은 작은 시드에서 한 단위짜리 작성과 한 단계 탐색만 재므로, 원칙 6(도구 경유)의 이점이 커지는 상황, 즉 큰 시드·여러 단위에 걸친 수정·영향 분석이 비어 있다.

## 결정

### 1. 범위
- 언어는 M1 부분집합(ADR-0016)을 넘지 않는다. 구조체·열거형·변환(`as`) 등 2B 이후 기능은 쓰지 않는다. 2B 이후 기능을 쓰는 과제는 새 집합(`m2` 등)으로 만든다.
- 프롬프트는 `m1`의 `prompt.md`를 바이트 그대로 쓴다. 집합 사이의 차이가 과제·시드뿐이어야 `m1`과 `m1b` 결과를 나란히 해석할 수 있다. `impact` 질의는 MCP `query` 도구가 이미 받지만 프롬프트에 적지 않는다. 프롬프트가 도구를 알려 주는지는 2D(도구) 페이즈에서 따로 재는 변수다.

### 2. 시드
- `bench/m1b/seed/src/`: 단위 9개, 정의 116개(실행 함수 53, `spec fn` 63), 전부 증명. `bmb import`의 정규형.
- 정수·배열 알고리즘: 유계 산술(`num`), 비트 연산 없는 정수론(`arith`), 배열 기본(`arr`), 선형·이분 탐색(`search`), 정렬 검사·선택 정렬 보조(`order`), 통계(`stats`), 상한 있는 잔액 배열(`ledger`), 작업 상태 기계(`fsm`), `io` 진입점(`app`).
- 깊이 3 이상의 호출 경로(`app::main → ledger::pay_all → ledger::transfer → ledger::deposit`, `app::report → stats::spread → stats::max_of → num::max2`)와 `&mut` 쓰기 경로(같은 `ledger` 경로, `order::selection_sort → order::select_step → arr::swap`)를 포함한다.

### 3. 과제
과제 37개: 작성 25, 탐색 12. 형식은 `m1`과 같다(ADR-0021 §1·§2). 유형은 셋이다.

| 유형 | 과제 | 판정 |
| --- | --- | --- |
| 새 정의 작성 | w01~w11, w22~w24(`tasks` 단위), w13·w25(기존 단위에 추가) | ADR-0021 §2 그대로 |
| 기존 정의 강화(여러 정의·영향) | w12 `stats::spread`, w14 `ledger::transfer`, w15, w16, w17 `fsm::run`, w18, w19 `order::select_step` | 대상의 명세 강도 + 작업 공간 전체 증명. w12·w14·w17·w19는 피호출자의 계약도 강화해야 증명되므로 그 호출자(영향 범위)가 계속 증명되는지가 판정에 들어간다 |
| 여러 단위 작성 | w20(`num::abs_diff`와 `tasks::max_gap`) | 과제의 `also_check`에 둔 정의마다 시그니처·명세 강도를 따로 판정, 모두 통과해야 성공 |
| 탐색 | n01~n12 | 정답은 하네스가 맵 질의로 계산. 직접 호출자, 전이 호출자·피호출자(`closure`), `impact` 행(n04~n07), 계약 뷰, `&mut` 쓰기 간선, `#[uses]` 사용처, 효과 |

- 작성 과제는 모두 기준 해법과 약한 대조군(`weak_reference`)을 가진다. 기존 정의 강화 과제(w15~w18)의 약한 대조군은 빈 트랜잭션, 즉 "시드를 그대로 둔 답"이다.
- 영향 분석 탐색(n04~n07)의 정답은 `bmb query impact DEF iface|body`의 행이다. 증명이 피호출자를 계약으로만, `spec fn`을 `#[uses]`로만 보므로 영향은 한 단계에서 멈춘다(ADR-0017 §4). 전이 호출자를 답하면 정밀도가 떨어진다(n07).

### 4. 동결과 비교 규칙
- `bench/m1b/MANIFEST`가 `prompt.md`·`seed/src/*`·`tasks/*`의 SHA-256을 담는다. 하네스는 `--set bench/m1b`로 이 집합을 고르고, MANIFEST가 다르면 실행을 거부한다(ADR-0021 §1과 같다). `bench/m1`은 바뀌지 않는다.
- 결과 파일의 요약 행에 `task_set`(집합 이름)과 `manifest`(MANIFEST의 SHA-256)를 기록한다.
- **집합을 섞지 않는다.** `harness.py summarize`는 `task_set`이 다른 파일을 한 표로 묶지 않고 거부한다(`task_set`이 없는 이전 결과는 `m1`). 보고서에서도 `m1`과 `m1b`의 수치를 합치거나 평균 내지 않는다.
- **모델 비교**는 같은 집합·같은 MANIFEST·같은 컴파일러 커밋에서 돌린 결과 파일끼리 `summarize`의 열로만 한다. 결과 파일은 `bench/<집합>/results/<날짜>-<모델>.jsonl`. 컴파일러 커밋이 다르면 진단·힌트가 달라지므로 표의 "컴파일러 커밋" 행으로 드러내고, 비교에서 그 차이를 적는다.
- 과제당 세션 한 번, 재시도 없음, 한도(도구 호출 40회)는 ADR-0021 §3 그대로다. 과제를 고치려면 새 이름(`m1c` 등)으로 만든다.

### 5. CI
검증 게이트(`scripts/check.sh`)가 `m1b`에서 기준 해법 전부 성공과 약한 대조군 전부 실패를 확인한다(ROADMAP 2A 통과 기준 2).

## 근거
- 같은 프롬프트를 쓰면 집합 간 차이가 과제·시드로 한정된다. 프롬프트를 바꾸면 `m1` 측정과의 대조가 깨진다.
- "기존 정의 강화" 과제는 큰 작업 공간에서 계약 변경의 파급을 다루게 한다. 작업 공간 전체 증명이 성공 조건이므로, 영향받는 호출자를 놓친 답은 실패한다. 이것이 `impact`·`#[uses]` 지식이 유리한 작성 과제다.
- 영향 정답을 `impact` 질의 출력으로 정하면 하네스가 결정론적으로 계산하고, 증명기의 실제 의존 규칙(ADR-0017 §4)과 일치한다.
- 대안: `m1`에 과제를 추가 → 동결 규칙(ADR-0021 §1) 위반이라 버렸다. 시드를 여러 개로 → 과제마다 시드가 다르면 탐색 비용 비교가 어려워 하나로 했다.

## 결과
- 하네스가 과제 집합 디렉터리를 인자로 받고(`--set`), 탐색 정답에 `reasons`(`impact` 행)·`closure`(전이)·여러 `also` 질의를, 작성 판정에 `also_check`를 지원한다. `m1` 과제 파일은 이 키를 쓰지 않으므로 판정이 바뀌지 않는다.
- 시드가 커서 과제마다 증명 시간이 `m1`보다 길다. 게이트 시간 증가는 백로그 2A-04 기록에 적는다.
- 편향: 정수·배열 한정(ADR-0016), 작성 과제는 모두 작성자 한 명이 기준 해법과 함께 만들었다. 측정 보고에 적는다.

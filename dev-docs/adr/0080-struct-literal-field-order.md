# ADR-0080: 구조체 생성 식의 필드는 선언 순서로 쓴다(검사기가 요구하고 고친다)

- 상태: 채택 (사람 승인 2026-11-01 "권장안 채택, 승인사항 승인": 백로그 2B-13의 안 (가)). ADR-0026 §1 "생성" 행의 "(정규형이 순서를 맞춘다)"와 §6의 "생성 식의 필드는 선언 순서로 정렬한다"를 대체한다
- 날짜: 2026-11-01
- 관련: ADR-0026 §1·§6(데이터 타입 표면과 정규형), DESIGN §3 원칙 8(표현 하나), 백로그 2B-04b, 2B-13

## 맥락

- ADR-0026은 생성 식의 필드를 "모든 필드를 선언 순서로" 쓰고 정규형이 순서를 맞춘다고 했다.
- 2B-04b가 찾은 문제: 필드 식은 적힌 순서로 평가된다. 정규형이 필드를 정렬하면 효과 있는 필드 식(`Pair { b: loud(2), a: loud(1) }`)의 평가 순서가 바뀌어 프로그램의 뜻이 달라진다. 그래서 정규형은 정렬하지 않았고, 검사기는 어떤 순서든 받았다. 결과적으로 한 생성 식에 표기가 여럿이었다(원칙 8 위반). 코퍼스의 두 프로그램(`tests/run/shapes.bmb`, `tests/verify/pass/structs.bmb`)이 선언 순서와 다른 순서로 썼다.
- 후보(2B-13): (가) 검사기가 선언 순서를 요구하고 바꿔 쓴 식을 수정으로 준다. (나) 적힌 순서를 그대로 두고 정규형을 여럿 허용한다. (다) 효과 없는 필드 식만 정렬한다.

## 결정

1. 구조체 생성 식은 필드를 선언 순서로 쓴다. 다른 순서면 검사기가 **E0434**("struct literal fields must be given in declaration order")를 내고, 수정은 같은 식을 선언 순서로 쓴 것이다(`replacement`, `bmb fix`가 적용).
2. 정규형은 생성 식의 필드를 정렬하지 않는다. 선언 순서가 곧 적힌 순서이고 평가 순서다.
3. 같은 필드를 두 번 쓰거나(E0422), 없는 필드를 쓰거나(E0306), `..base`를 쓴 식(E0223)에는 E0434를 내지 않는다. 그 오류의 수정이 먼저다.

## 근거

- **원칙 8:** 한 가지 일에 표현 하나. (나)는 같은 값을 만드는 표기를 순열만큼 둔다.
- **뜻을 지킨다:** 정렬은 효과 있는 식의 평가 순서를 바꾼다. (다)는 "효과 없음" 판정에 기대고, 효과가 있는 식에서는 다시 두 표기가 남는다. (가)는 순서를 사람이나 에이전트가 정하게 하고, 그 순서가 곧 선언 순서다. 평가 순서는 글에 보이는 대로다.
- **기계적 수정:** 고칠 식은 결정론적으로 정해지므로 수정이 붙는다. 에이전트의 Rust 습관(필드 순서 자유)은 진단 한 번과 수정으로 끝난다(원칙 6의 "기계적으로 결정되는 표기는 도구가").

## 결과

- 코드: `check::Checker::struct_lit`의 E0434(`compiler/src/diag.rs` 표), 진단 문서 `docs/diagnostics.md`.
- 코퍼스: `tests/check/err/field_order.bmb`(효과 없는 식과 효과 있는 식 둘), 두 프로그램을 선언 순서로 고침(실행 출력과 증명은 그대로).
- 동결 집합: 순서가 다른 생성 식은 코퍼스의 두 프로그램뿐이었다. 검사기로 확인한 것: 코퍼스, `lib/`, `bench/game`, `bench/brb-encap` 시드 넷(E0434 0건). BRB-encap 과제 모듈의 BMB 해법에는 생성 식이 없다. 모든 동결 집합의 기준·약한 해법은 게이트가 이 컴파일러로 돌린다. 모델이 순서를 바꿔 쓰면 이제 E0434와 수정을 받는다. 컴파일러 트리가 바뀌므로 새 측정 조건이다(ADR-0070 (a)).
- 되돌리기: E0434를 빼면 지금의 (나)와 같다.

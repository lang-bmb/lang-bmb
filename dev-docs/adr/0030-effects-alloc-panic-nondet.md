# ADR-0030: 효과 확장(`alloc`·`panic`·`nondet`)과 테스트 필요 면적

- 상태: 제안 (언어 범위 확대. 채택은 사람 승인, AUTONOMY.md §4)
- 날짜: 2026-10-24
- 관련: DESIGN.md §4.1(효과)·원칙 4·§7.2(효과 뷰)·§8.1(효과 기반 최적화), ADR-0003, ADR-0016, ADR-0020, ADR-0028·0029·0031(제안), ROADMAP 2F, 백로그 2F-01·2D-11

## 맥락
M1의 효과는 `pure`와 `io` 둘이다(ADR-0016). 실행 함수마다 `#[effects(..)]`가 필수이고, 검사는 직접 호출 하나다: `pure` 함수가 `io` 함수를 부르면 E0603(`compiler/src/check.rs`의 호출 검사). 모든 함수가 효과를 선언하므로 직접 규칙만으로 전이가 성립한다. `status`는 `io_defs` 수를 센다(`compiler/src/map.rs`).

M2에서 효과가 둘로는 부족해지는 이유:
- **할당.** `Vec`(ADR-0031 제안)은 할당하고, 메모리 부족이면 중단된다. 할당 여부는 순수 구간 최적화와 테스트 필요 면적에 영향을 준다.
- **중단.** M1에서는 모든 의무가 증명되어야 빌드되므로 실행 중 trap이 없다. 탈출구(ADR-0029 제안)가 들어오면 검사가 남는 정의가 생긴다. 그 사실이 호출자에게 보여야 한다.
- **비결정.** 시간·난수·입력은 같은 입력에 같은 결과라는 전제를 깬다. 아직 원천이 없다.

ADR-0003은 테스트가 필요한 면적을 효과 선언으로 산출하기로 했다. 지금 산출은 "`io` 정의 수"뿐이다. 이 효과 확장에 대한 측정 증거는 아직 없다(1E 과제는 `pure`/`io`만 쓴다).

## 결정(제안)

### 1. 효과 집합(격자)
- 원자 효과는 넷이다. 효과는 이들의 **집합**이고 격자는 부분집합 순서다. `pure`는 빈 집합의 이름이다.

| 효과 | 뜻 | 원천 |
| --- | --- | --- |
| `alloc` | 힙 할당. 메모리 부족이면 중단(Rust의 `handle_alloc_error`와 같음) | `Vec` 생성·증가·복제(ADR-0031). 해제는 효과가 아니다(실패하지 않고 결정론적) |
| `io` | 외부와의 상호작용. 순서가 관찰된다 | `print_i64`, `print_u64`(ADR-0028) |
| `nondet` | 결과가 인자 밖의 것에 달려 있다 | 첫 원천(입력·시간·난수 내장)과 함께 들인다(열린 질문 2) |
| `panic` | 실행 중 trap으로 끝날 수 있다 | 전체 검사 모드로 컴파일되는 정의(ADR-0029 §4) |

- `io`는 다른 효과를 함의하지 않는다(직교). 입력 내장은 `io`와 `nondet`을 함께 갖는다.
- 메모리 부족 중단은 `panic`이 아니라 `alloc`에 속한다. 그렇지 않으면 할당하는 모든 함수가 `panic`이 되어 `panic`이 정보를 잃는다.

### 2. 표면
- `#[effects(pure)]` 또는 `#[effects(e1, e2, ..)]`. `pure`는 다른 효과와 함께 쓸 수 없다(E0607). 정규형은 이름순(`alloc, io, nondet, panic`)이고 중복은 오류(E0607).
- M1 코드는 그대로 유효하다. `#[effects(io)]`는 `{io}`다.
- `main`은 `io`를 포함해야 한다. 다른 효과를 더할 수 있다(E0701의 조건을 "`io` 포함"으로 넓힌다. 메시지만 갱신).

### 3. 검사와 전파
- **필요 효과** `req(f)` = 본문의 고유 효과(내장 호출, `Vec` 연산, 전체 검사 모드면 `panic`) ∪ 실행 callee의 **선언** 효과. 선언 `decl(f)`는 `req(f)`를 포함해야 한다. 아니면 E0606(빠진 효과마다, `#[effects(..)]`를 고치는 `fix.replacement` 포함). 기존 E0603은 `pure`가 `io`를 부르는 경우의 코드로 의미를 유지한다.
- 선언이 필요보다 넓은 것은 허용한다. 선언은 인터페이스다. callee 본문이 바뀌어 효과가 늘면 호출자가 아니라 callee에서 오류가 난다(계약 방화벽과 같은 원리). 쓰이지 않는 선언 효과는 `bmb lint` 경고(W09xx 다음 빈 번호)로 알려 좁히게 한다.
- 맵용 **전이 효과** `eff*(f)` = `req(f)`를 호출 그래프에서 고정점으로 모은 것(SCC 단위, 결정론적 순서). 선언 규칙이 직접 호출마다 성립하므로 `eff*(f) ⊆ decl(f)`가 항상 참이다.
- `spec fn`·명세 문맥은 효과가 없다(E0604 유지). `external_body`(ADR-0029) 본문도 같은 규칙으로 검사한다. 효과는 신뢰하지 않는다.

### 4. 테스트 필요 면적(ADR-0003 구체화)
정의 단위로 `test_reasons`를 계산한다. 비어 있지 않으면 테스트 필요 정의다.

| 이유 | 조건 | 왜 |
| --- | --- | --- |
| `io` | `io ∈ eff*(f)` | 외부 상호작용의 순서·내용은 계약이 말하지 않는다 |
| `nondet` | `nondet ∈ eff*(f)` | 같은 입력에서 다른 결과가 가능하다 |
| `panic` | `panic ∈ eff*(f)` | trap이 일어나지 않음이 증명되지 않았다 |
| `trust` | 신뢰 등급이 `proved`가 아님(ADR-0029) | 계약 자체가 증명되지 않았다 |

- `alloc`만 있는 정의는 테스트 필요가 아니다. 메모리 부족은 환경 조건이고, 값의 정확성은 증명된다. 이 판단은 `alloc`이 필요 이유가 아님을 명시한 것이다(열린 질문 3).
- 면적은 두 단위로 낸다: 정의 수, 그리고 원천 지점 수(효과 원천 호출·연산의 위치 수). 최소화는 원천 지점이 적은 쪽이다. 테스트는 원천 지점을 겨냥하면 된다.
- 최소화 도구: 선언이 필요보다 넓은 효과의 린트, 원천 지점을 감싼 작은 정의로 나누는 분할 제안(DESIGN.md §8.2 해체·분할의 한 사례).

### 5. 질의·맵(ADR-0020 하위 호환: 키 추가만)
- L1 행: 기존 `effects`는 선언 텍스트 문자열 그대로(이제 `"alloc, io"`처럼 쉼표 목록일 수 있음). 추가 키 `effects_required`(`eff*` 배열), `test_reasons`(배열).
- `status` 행에 `effects_required`·`test_reasons` 추가, 요약 행에 효과별 정의 수(`alloc_defs`, `panic_defs`, `nondet_defs`)와 `test_needed_defs`, `test_sites` 추가. 기존 `io_defs`는 의미 그대로.
- `query effects DEF`(2D-11 확장): `eff*(DEF)`의 효과마다 원천까지의 최단 호출 경로 하나(동률은 경로 사전순)와 원천 지점.
- `query effect E`: E를 선언한 정의와 E가 필요한 정의(원천 종류: 고유/callee)의 목록. 2F 통과 기준 "효과별 정의 목록"이 이것이다.

### 6. 코드 생성
- 효과에서 LLVM 함수 속성을 낸다. 모든 함수에 `nounwind`(BMB에는 되감기가 없다).
- `panic ∉ eff*`이고 신뢰 등급 `proved`인 함수에만 `willreturn`·`mustprogress`. 종료는 `decreases` 증명에서, 정상 반환은 trap 부재에서 나온다. 전체 검사 모드 함수에는 내지 않는다(trap은 반환이 아니다).
- 효과가 비어 있고 `&mut` 인자가 없으면 `memory(argmem: read)`(참조 인자가 없으면 `memory(none)`). `alloc`이면 `inaccessiblemem: readwrite`를 더한다. `io`·`nondet` 함수에는 메모리 속성을 내지 않는다.
- 이 속성들은 효과 검사가 보장한다(타입 규칙에서 나온 사실, `noalias`와 같은 지위). 속도 이득은 1E-08처럼 측정으로만 주장한다. 더 큰 효과 기반 최적화(메모화·병렬화, DESIGN.md §8.1)는 측정 후 별도 ADR.

| 습관 | 처리 | 코드 |

### 8. 테스트·퍼저
- 진단 코퍼스: `tests/check/err/effects.bmb`에 E0606·E0607과 SCC(상호 재귀) 사례.
- 속성 테스트: 무작위 호출 그래프와 무작위 선언·고유 효과를 만들고, 검사기 판정이 "모든 정의에서 `decl ⊇ req`"와 같은지, 맵의 `effects_required`가 단순 고정점 참조 구현과 같은지 대조한다.
- 건전성 퍼저: 해석기가 실행 중 실제로 일어난 효과(할당, trap, 출력)를 정의별로 기록한다. 성질: **동적 효과 ⊆ 정적 `eff*`**. 특히 `panic`이 없는 정의는 어떤 허용 입력에서도 trap하지 않는다. 기존 퍼저 6종의 해석기에 기록만 더한다.
- IR 테스트: `willreturn`은 `proved`이고 `panic`이 없는 함수에만 있다. 결정론(두 번 실행 같은 바이트).

## 근거(검토한 대안)

| 안 | 판정 |
| --- | --- |
| **직교 원자 효과의 집합(채택 제안)** | 질의("`alloc`에 닿는 모든 경로")와 테스트 필요 면적이 원자 단위로 나온다. 선언 검사는 집합 포함 하나다 |
| 사슬 격자(`pure < alloc < panic < io`) | 단순하지만 `io`이면서 할당하지 않는 정의와 할당만 하는 정의를 구분할 수 없고, 효과 뷰(DESIGN.md §7.2)가 거칠어진다. 기각 |
| `io`를 최상위(모든 효과 함의)로 | M1 코드가 바로 맞고 `main` 선언이 짧지만, `io` 정의 아래가 모두 테스트 필요가 되어 면적 산출이 무의미해진다. 기각 |
| 선언 없이 효과를 추론만 함 | 명시성을 도구가 채우는 원칙(원칙 6)과 맞지만, 선언이 인터페이스 역할(callee 변경이 호출자에게 번지지 않게)을 잃는다. 선언은 필수, 채우기는 `bmb fix` |
| 선언이 필요와 정확히 같아야 함 | 선언이 완전히 기계적이 되어 인터페이스 안정성이 사라진다. 과잉은 경고로 |
| 메모리 부족을 `panic`으로 | §1 표 아래 이유로 기각 |
| 해제를 `alloc`에 포함 | `Vec`을 값으로 받는 모든 함수가 `alloc`이 되지만 해제는 실패하지 않고 관찰되지 않는다. 기각(열린 질문 3) |

## 결과
- `#[effects]` 속성의 문법이 넓어진다. M1 코드는 바꿀 필요가 없다.
- 효과 하나를 callee에 더하면 모든 호출자의 선언을 고쳐야 한다(Rust의 `async`·`Result` 전파와 같은 비용). `bmb fix`가 기계적으로 채우지만, 변경 영향(`impact`)이 넓어진다. Rust 습관 오류율과 함께 잰다.
- `panic` 효과는 ADR-0029가 채택될 때만 원천이 생긴다. 둘을 함께 승인하는 것이 자연스럽다.

## 열린 질문(측정 1E-07 또는 사람이 정함)
1. **2F의 시점:** 효과 확장의 원천은 다른 페이즈(`alloc`은 2G, `panic`은 2E, `nondet`은 아직 없음)가 만든다. 2F를 그 페이즈들과 묶어 진행할지, 격자만 먼저 넣을지.
2. **`nondet`의 첫 원천:** M2에 입력 내장(`read_i64`)이나 시간 내장을 넣을지. 원천 없는 효과는 검증할 수 없으므로 원천과 함께만 들인다(CLAUDE.md "검증되지 않는 기능은 언어에 넣지 않는다").
3. **`alloc`의 테스트 필요 여부와 해제의 효과:** 제안은 둘 다 아님. 메모리 상한이 중요한 과제가 생기면 다시 본다.
4. **테스트 필요 면적의 단위:** 정의 수 대 원천 지점 수 중 어느 것을 측정 축(DESIGN.md §9 R4)의 대표값으로 할지. `m2`에서 두 값을 모두 보고하고 정한다.
5. **LLVM 속성의 이득:** `memory`·`willreturn`이 기준선 벤치에서 측정 가능한 차이를 내는지. 없으면 속성은 유지하되 성능 주장은 하지 않는다.

# ADR-0073: H-EDIT의 비교 표면: 파일 diff는 `git apply --recount`, JSON AST는 구문 트리 + JSON Patch

- 상태: 채택 (자율 채택, AUTONOMY.md §4: MCP 서버의 선택 플래그·CLI 명령 하나와 새 측정 판. 기본 출력과 동결 집합은 그대로)
- 날짜: 2026-10-31
- 관련: DESIGN.md §9 R2, 원칙 1·6, ADR-0009(트랜잭션), ADR-0011(배치는 도구가), ADR-0019(정규형), ADR-0021(동결), ADR-0070(같은 조건), 백로그 T1-06·2D-24, ROADMAP 가설 H-EDIT·H-GRAIN

## 맥락

- H-EDIT(구조적 주소 + 텍스트 내용의 편집이 파일 diff나 JSON AST 편집보다 1회 성공률이 높다)와 H-GRAIN(정의 단위가 파일·문장 단위보다 총 토큰이 적다)은 같은 과제를 세 표면으로 풀어 비교한다. 정의 단위 표면(`write`, 2D-24)과 그 판(`bench/*-write`)은 있다. 파일 diff와 JSON AST 표면은 컴파일러에 없었다: 구문 트리를 JSON으로 내보내거나 들여오는 길도, diff를 적용하는 길도 없었다.
- 비교가 가설을 반증할 수 있으려면 경쟁 표면이 그 형식의 정석대로, 공정하게 만들어져야 한다(C3). 편집 표현 말고는 같아야 한다: 읽기 도구(`query`·`map`), 커밋 규칙(구조·타입 오류면 전체 거부), 한 호출에 커밋과 증명, 동결 과제·프롬프트의 나머지.

## 결정

1. **공통.** 두 표면 모두 `write`처럼 한 호출이 커밋하고 작업 공간 전체를 증명해 커밋 줄과 증명 결과를 돌려준다. 커밋은 트랜잭션 규칙 그대로다(`workspace::plan_files`: 새 파일 전체를 검사, 오류면 아무것도 쓰지 않음, 저장은 정규형). 파일 배치는 도구의 것이므로(ADR-0011) `src/UNIT.bmb`는 최상위 단위 `UNIT` 하나만 담아야 한다. 선택 플래그(`--file-tools`, `--ast-tools`)로만 보이고, 플래그가 없으면 도구 목록과 응답은 같은 바이트다.
2. **파일 diff(`read_file`, `edit_file`).** 통합 diff를 `git apply --recount`의 규칙으로 적용한다. 헝크 머리의 줄 수는 믿지 않고 헝크에서 다시 센다. 줄 번호는 먼저 찾아볼 곳이고, 여러 곳에 맞으면 가장 가까운 곳, 번호가 없으면 한 곳에만 맞아야 한다. 문맥·삭제 줄은 공백까지 정확히 맞아야 한다(퍼지 없음). 맞지 않으면 없는 줄을(공백만 다르면 그렇다고) 말한다. `/dev/null`로 만들고 지운다. 정규형이 텍스트를 바꾼 파일은 `reformatted`로 알린다(다음 diff 전에 다시 읽으라는 신호).
3. **JSON AST(`read_ast`, `edit_ast`).** 문서는 컴파일러의 구문 트리(`ast.rs`)를 JSON으로 옮긴 것이다(`src/ast_json.rs`, CLI `bmb ast`). 최상위는 단위 이름이 키인 객체, 단위의 정의·타입·trait·impl·하위 단위도 이름이 키라서 JSON Pointer가 경로처럼 정의를 가리킨다(`/calc/fns/twice/body/tail`). 그 밖의 노드는 `kind`와 `ast.rs`의 필드 이름, 이름·경로·연산자는 문자열, 빈 부분은 생략, 위치는 없다. 편집은 RFC 6902 JSON Patch(원자적)다. 들여온 트리는 정규형으로 찍어 다시 파싱하고 같은 트리일 때만 커밋한다. 진단·증명 결과의 위치는 그 위치를 담는 가장 안쪽 노드의 포인터 `at`이다(이 표면의 `verify`도). 정규형이 버리는 것과 파서의 복구 꼴은 트리에 없다.
4. **판과 대본.** `bench/edit/gen.py`가 m1b·BVB·BRB(BMB 팔)에서 `*-diff`·`*-ast`를 만든다. 원판과 쓰기 표면만 다르다: `set.json`(플래그, 숨긴 트랜잭션 도구, `script`), 프롬프트의 도구 절과 "How to work", AST 판은 예제를 트리로도 보인다. 대본 에이전트(기준·약한 해법)는 판의 표면으로 쓴다(`set.json`의 `script`, `bench/m1/surface.py`: 트랜잭션 결과 파일과의 통합 diff, 트리 사이의 JSON Patch). 게이트가 생성 일치와 m1b·BVB 판의 기준 해법 통과·약한 해법 거부를 본다. BRB 판은 `-write`처럼 파일럿 변형이다.

## 근거

- **원인 층(JUDGMENT §3):** 측정할 표면이 없는 것은 도구 층의 빈칸이다. 하네스에서 diff를 적용하거나 JSON을 텍스트로 바꾸면(대안 가) 표면의 의미(오류 문구, 위치, 원자성)가 측정 자산에 들어가고, 컴파일러 진단·정규형과 따로 논다.
- **정석(S1):** 통합 diff의 적용 규칙은 `git apply`(퍼지 없음, 위치 탐색)다. `--recount`를 고른 것은 줄 수가 헝크에서 결정론적으로 계산되는 값이라서다(원칙 6: 도구가 셀 수 있는 것을 에이전트에게 세게 하지 않는다). JSON 문서의 부분 편집은 RFC 6902/6901이 정석이다. 트리의 모양은 ESTree(노드마다 종류 태그)와 syn-serde(빈 부분 생략)의 관례를 따르고, 필드 이름은 새 언어를 만들지 않도록 컴파일러의 구문 트리를 그대로 쓴다.
- **공정성(C3):** 두 경쟁 표면은 각 형식의 강한 판이다: 줄 수 오류를 용서하고, 진단을 그 표면의 주소(파일 줄, 트리 포인터)로 돌려주고, 정의를 이름으로 가리킨다. 그래도 정의 단위 표면이 나으면 가설이 지지되고, 아니면 반증된다.
- **대안:** (가) 하네스가 diff·JSON을 받아 `tx_put`으로 바꿈: 표면 의미가 측정 자산으로 가고 진단이 맞지 않는다. (나) diff를 엄격하게(줄 수까지): 표면이 가설과 무관한 계산 부담을 진다. (다) JSON을 정의 단위로만(`write`의 코드 자리에 트리): 문장 단위 편집(H-GRAIN의 세 번째 단위)이 없어진다. JSON Patch는 정의 단위와 노드 단위를 모두 허용한다. (라) 노드를 배열 위치로만 가리킴: 정의를 이름으로 가리키는 정석 주소(경로)를 버린다. (마) 이 결정.

## 결과

- 동결 판 여섯(`bench/m1b-diff`·`bvb-diff`·`brb-diff`·`m1b-ast`·`bvb-ast`·`brb-ast`). 정식 측정은 백로그 `T1-41`.
- 트리는 텍스트보다 크다(m1b 씨앗: 텍스트 26,051바이트, `bmb ast` 102,643바이트). 이것은 표면의 비용이고 측정 대상이다.
- 하네스의 `commits`·E02xx/커밋은 `tx_commit`만 세어 한 호출 쓰기 표면(`write`·`edit_file`·`edit_ast`)에서 비어 있다(`T1-40`).
- 되돌리기: 플래그·명령·판을 지운다. 기본값과 기존 동결 집합은 이 결정에 기대지 않는다.

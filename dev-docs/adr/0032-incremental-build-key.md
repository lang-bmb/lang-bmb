# ADR-0032: 계약 방화벽 증분 빌드의 키

- 상태: 채택(자율). 증명 키의 "질의 머리" 행과 그 한계는 대체됨(ADR-0033). 피호출자 실행 함수의 "계약 해시"는 대체됨(ADR-0043: `#[uses]`를 뺀 호출자 해시). 키 행의 이름 의존(경로로 적은 피호출자·원문, 바이트 오프셋 위치)은 대체됨(ADR-0059 §4)
- 날짜: 2026-10-24
- 관련: DESIGN.md §8.1, ADR-0017 §4, ADR-0019 §2, 백로그 2D-01·2D-02·2D-10

## 맥락
증명 캐시(2D-01)는 해법기 입력 텍스트 전체를 키로 해 해법기 호출만 건너뛴다. 매 실행은 여전히 모든 정의를 기호 실행으로 인코딩하고 모든 IR을 다시 만든다. DESIGN.md §8.1은 "본문이 바뀌어도 계약이 그대로면 호출자를 다시 검증·컴파일하지 않는다"를 요구한다. ADR-0019 §2는 키의 출발점(본문 해시, 피호출자 계약 해시, 펼치는 `spec fn` 본문 해시)만 정했다.

## 결정
정의마다 결과 두 가지를 캐시 디렉터리(`--cache DIR`, MCP `.bmb-cache/`)의 `defs` 파일에 저장한다(`src/incremental.rs`).

- **증명 결과**: 완전히 증명된 정의만. 상태 줄 수치(의무 수, `rlimit`, `rlimit_max`)와 증명된 의무 목록(정의 시작 기준 상대 위치). 실패한 정의는 저장하지 않고 늘 다시 인코딩·증명한다(진단을 그대로 내기 위해).
- **IR**: 실행 함수의 `define` 조각과 남은 검사 수.

증명 키는 인코딩이 읽는 것 전부다.

| 요소 | 이유 |
| --- | --- |
| 컴파일러 정체성(`CARGO_PKG_VERSION` + `build.rs`가 `src/**`와 `toolchain.env`로 만든 SHA-256), Z3 버전 | 인코딩·도구가 바뀌면 전부 무효 |
| 질의 머리(옵션·시드·`rlimit`·전주곡·모든 `spec fn` 선언)의 해시 | 모든 질의에 그대로 들어간다 |
| 정의의 원문(`fn`부터 닫는 괄호까지)과 한정 정규형(본문 포함) | 원문은 의무 위치(바이트 오프셋)를, 한정 정규형은 이름 해석을 고정한다 |
| 한정 정규형이 이름으로 부르는 정의마다: 실행 함수는 계약 해시, `#[uses]`로 펼치거나 같은 재귀 성분인 `spec fn`은 본문 해시, 나머지 `spec fn`은 이름만(선언은 머리에 있음) | `impact` 질의의 `calls`·`uses`·`names` 간선과 같다 |
| 재귀 성분의 구성원 | 성분 안 호출에 `decreases` 의무가 생긴다 |

IR 키는 컴파일러 정체성, 원문, 한정 정규형, 부르는 실행 함수의 계약 해시(인자·반환 타입), 그리고 그 정의 안에서 코드 생성이 쓸 수 있는 증명된 의무(1B-31의 `usable_proofs` 결과, 상대 위치)다.

파일은 형식 버전과 컴파일러 정체성을 머리에 두고, (종류, 정의)마다 최신 항목 하나를 한 줄로, 줄마다 필드의 SHA-256을 붙여 쓴다. 파싱되지 않거나 해시가 맞지 않는 줄, 다른 버전·정체성의 파일은 무시하고 다시 만든다. 저장된 위치가 정의 범위를 벗어나거나 진단 코드가 목록에 없어도 적중으로 쓰지 않는다.

## 근거
- 키의 요소는 `verify_impl`이 정의 하나를 인코딩하며 읽는 입력을 하나씩 짚은 것이다. 같은 키면 같은 질의 텍스트가 나오므로 증명 캐시와 같은 판정이다. `incremental::with_audit`은 적중해도 다시 계산해 스크립트 해시·상태·증명 목록을 비교하고, `tests/incremental.rs`가 코퍼스 전체와 편집(주석으로 위치 이동, `spec fn` 추가, 하위 단위 추가, 측정식 변경)에서 불일치 0을 확인한다.
- IR 키에 사용 가능한 증명 목록을 넣으므로 같은 호출 성분의 다른 정의가 실패해 검사가 되살아나면(1B-31) 그 성분의 IR은 다시 만들어진다.
- 대안: 본문·계약 해시만으로 키를 만들면 원문 위치가 달라도 적중해 의무 위치가 어긋나고, 머리(전체 `spec fn` 선언)가 바뀐 것을 놓친다. 기각.
- 대안: 인코딩은 늘 하고 IR만 재사용. 안전하지만 인코딩 비용이 남는다. 감사 모드로 키의 충분성을 시험할 수 있으므로 기각.

## 결과
- 1200개 정의(실행 함수 750개) 생성 프로그램에서 따뜻한 `verify`가 증명 캐시만 쓸 때보다 약 4배 빠르다(측정은 백로그 2D-10 근거).
- `spec fn`의 시그니처를 바꾸거나 하나를 더하고 빼면 질의 머리가 바뀌어 모든 정의를 다시 인코딩한다. `impact`는 이름으로 부르는 정의만 꼽지만 질의 텍스트는 실제로 모두 바뀐다(증명 캐시도 모두 놓친다). 머리를 질의가 닿는 선언으로 줄이는 것은 인코딩 변경이라 별도 과제다.
- 원문을 키에 넣으므로 정의 안의 공백·주석 변경도 그 정의를 다시 인코딩한다(증명은 증명 캐시가 받는다). 정의 밖의 편집은 위치만 옮기며 재사용된다.
- `--emit-smt`는 모든 정의의 스크립트가 필요하므로 재사용을 끈다.
- 파일은 증명 캐시처럼 소스 트리만큼 신뢰한다. 손상은 막지만 일부러 고친 항목은 막지 않는다.

# ADR-0042: BCB(누적 검증 비용 벤치)의 설계와 사전 등록

- 상태: 채택(자율)
- 날짜: 2026-10-25
- 관련: ADR-0040(H-AMORT, G7), ADR-0041 §1(보조 지표), ADR-0032·0033(증분 키), ADR-0035(BSB), 백로그 2A-14, `dev-docs/research/테스트 실행 비용 누적 근거/report.md` 권고 2

## 맥락

ADR-0040은 H-AMORT를 BCB로 재기로 했고, 조사 보고서 권고 2가 팔 다섯 개와 반증 조건 네 개를 제안했다. 구현하려면 보고서가 열어 둔 것을 정해야 한다. 편집의 종류와 표현, 두 언어를 같은 편집으로 묶는 방법, R1·R2의 선택 규칙, BMB의 남은 테스트, 툴체인 사건을 재는 방법, 측정이 너무 비싼 팔의 처리, 반증 조건의 수치 판정이다. 측정 전에 정해 커밋해야 사후 조정이 되지 않는다(운영 규칙).

## 결정

### 1. 코퍼스와 이력

- 코드베이스는 `bench/m3/gen.py`의 기본 매개변수로 만든다. 크기는 N = 1,000과 10,000, 깊이 축은 N = 1,000에서 `--depth 2`·`6`이다. Rust 쌍둥이는 `bench/bnb/twin.py`다.
- 이력은 `bench/bcb/history.py`가 고정 시드로 만든다. 커밋은 계획(`gen.Unit`·`gen.choose`)을 고치고, 두 렌더러가 같은 계획을 쓰므로 두 언어가 같은 편집을 받는다. 편집 하나는 단위 파일 하나를 바꾼다.
- 편집 종류: `body`(인터페이스 유지: 상수·템플릿·피호출자·결과 형태), `contract`(잎의 `ensures`에 `_ok` 술어 넣기·빼기), `spec`(`_ok` 술어의 상한 변경), `add`(잎 추가), `remove`(호출자 없는 잎 삭제). 모든 커밋에서 BMB 작업 공간은 전부 증명되고 Rust는 경고 없이 컴파일된다(게이트 `bench/bcb/test_bcb.py`).
- 프로필 세 개: `body-heavy`(70/10/5/10/5%), `contract-heavy`(40/30/10/15/5%), `body-only`(반증 조건 2용). 커밋당 편집 수는 1·2·3개가 60·25·15%, 단위는 균등하게 고른다. 실제 저장소 이력에서 비율을 추정하지 않았다. BMB로 된 실제 이력이 없기 때문이다. 이 점을 편향으로 보고한다.
- 이력 파일은 편집의 결과 값과 커밋마다 트리 전체의 다이제스트를 담는다. 재생은 모든 다이제스트를 다시 만들어야 하고, 다르면 실패한다. K = 1,000.

### 2. 팔

다섯 팔을 같은 머신에서 순서대로(동시 실행 없이) 돌린다. 비용은 커밋마다 자식 프로세스의 CPU 시간(user+sys, `wait4`)이고 벽시계는 따로 기록한다.

| 팔 | 커밋마다 | 선택 규칙 |
| --- | --- | --- |
| R0 | `cargo build` + `cargo test`(전부) | 없음. Cargo 기본 dev 프로필(증분 컴파일 켬) |
| R1 | 같은 빌드 + 선택한 테스트 | 바뀐 단위와, 단위 의존 그래프에서 그것에 전이적으로 의존하는 단위의 테스트. 단위 하나를 Bazel 대상 하나로 본 정확 캐시다 |
| R2 | 같은 빌드 + 선택한 테스트 | 정적 호출 폐포가 바뀐 함수(술어 포함)에 닿는 함수의 테스트. 테스트 입력이 빈 배열을 쓰지 않으므로 생성 코드에서는 정적 폐포가 동적 커버리지와 같다 |
| B0 | 새 캐시로 `bmb verify` + `bmb build` + 남은 테스트 | 남은 테스트 전부 |
| B1 | 유지되는 `--cache`로 같은 일 | 남은 테스트에 R2 규칙 |

- Rust 쌍둥이는 크레이트 하나다. 단위마다 크레이트를 두면 R1이 역의존 크레이트를 다시 컴파일해야 해서 Rust 쪽이 불리해진다. 크레이트 하나와 rustc 증분 컴파일은 Rust에 유리한 선택이다.
- **BMB의 남은 테스트**는 io 정의(`show`)의 출력이다. 출력은 어떤 계약도 말하지 않는다(ADR-0030의 테스트 필요 면적). 테스트는 고정 입력으로 `show`를 부르는 `main` 단위를 같이 빌드해 실행하고, 계획을 평가한 기대 출력과 비교한다. 2D-21(남은 테스트 면적 질의)이 생기면 그 산출로 바꾼다.
- **비싼 기준 팔의 표본화.** R0·B0는 주장에 쓰지 않는 기준 팔이다(보고서 "해석상 주의"). N = 1,000에서는 모든 커밋을 잰다. N = 10,000에서 R0는 10번째 커밋마다, B0는 5개 커밋(0, K/4, K/2, 3K/4, K)만 잰다. 누적값은 표본 평균 × K로 추정하고 "추정"이라고 표시한다. B0의 차가운 증명은 N = 10,000에서 커밋당 약 1,700초다(3A-01).

### 3. 툴체인 사건

사건 커밋은 K·j/5(j = 1..4)이고, 1회 변형은 j = 2만 쓴다. 사건 커밋에서는 먼저 평소처럼 재고, 캐시를 지운 뒤(BMB: 캐시 디렉터리, 컴파일러 정체성·Z3 버전이 바뀐 것과 같은 효과; Rust: `cargo clean`, rustc 업그레이드와 같은 효과) 같은 커밋을 다시 잰다. 차가운 재빌드 뒤의 상태는 따뜻한 상태와 같다(증명 캐시는 내용 주소이고 증분 컴파일은 같은 산출물을 만든다). 그래서 한 번의 실행에서 사건 0·1·4회의 누적값을 모두 얻는다. C_e(K) = C_0(K) + Σ(사건 커밋의 차가운 비용 − 평소 비용)이다.

### 4. 테스트 동등성과 결함

- Rust 테스트는 실행 정의마다 하나다. `requires`를 만족하는 입력으로 함수를 부르고, 쌍둥이 본문의 `debug_assert!`(계약)와 넘침·범위 패닉으로 판정한다. 변이체는 W0904 연산자(2D-09·2D-16)를 두 언어의 같은 본문 위치에 적용한 것이다. 입력은 결정론적 후보열(경계값, 고정 시드 무작위)에서 그 정의의 BMB 계약이 죽이는 변이체를 모두 죽일 때까지 늘린다. 정의별로 두 판별률을 보고한다.
- 결함: 커밋마다 편집된 실행 정의 하나에 변이체 하나를 심은 곁가지 트리를 만든다. 변이체는 결정론적으로 고르고 생존 변이체(계약이 구별하지 못하는 것)도 포함한다. 각 팔은 그 커밋의 선택 규칙대로 곁가지에서 돈다. 팔이 실패하면(증명 실패, 남은 테스트 실패, 선택된 Rust 테스트 실패) 결함을 잡은 것이다. 곁가지는 이력에 들어가지 않는다.

### 5. 반증 조건(사전 등록)

아래 하나라도 성립하면 H-AMORT를 그 범위에서 반증된 것으로 기록한다. 결과는 1회 실행, 재시도 없이 보고한다.

1. N = 10,000, K = 1,000, 사건 0회에서 C_B1(K) ≥ C_R1(K). `body-heavy`와 `contract-heavy`를 따로 판정한다.
2. `body-only`에서 커밋당 B1이 다시 증명한 정의 수의 평균이, R2가 다시 돈 테스트가 실행하는 서로 다른 정의 수의 평균 이상이다(계약 방화벽 우위 없음). N = 1,000과 10,000을 따로 판정한다.
3. 사건 4회(Rust도 같은 커밋에 `cargo clean`)에서 C_B1(K) > C_R1(K). 프로필별로 판정한다.
4. 모든 프로필을 합한 결함 검출률에서 B1 < R2.

손익분기 커밋 수 k*에는 쓰기 비용 W(CPU로 환산)가 필요하다. W는 BRB 실측(사용자 실행)에서 오므로, BCB는 W의 함수로 k*(W) = min{k : C_B1(k) + W ≤ C_R1(k)}를 보고하고 수치는 BRB 결과가 커밋된 뒤 채운다.

## 근거

- 편집을 계획 수준에서 기록하면 두 언어의 편집이 구성상 같다. 텍스트 diff를 언어 간에 옮기는 방식보다 확인이 쉽다(BNB와 같은 방식).
- 사건을 같은 실행 안에서 이중으로 재면 사건 위치가 같은 세 변형을 세 번 돌릴 필요가 없고, 사건 사이의 잡음 차이도 섞이지 않는다.
- 기준 팔 표본화는 주장하지 않는 팔에만 쓴다. 판정에 쓰는 B1·R1·R2는 모든 커밋을 잰다.
- 대안: Rust를 단위마다 크레이트로. Bazel에 더 가깝지만 Rust 쪽 컴파일 비용이 커진다. 공정한 기준선 원칙에 따라 Rust에 유리한 쪽을 골랐다.

## 결과

- 측정 비용: N = 10,000에서 판정 팔 셋 × 커밋 1,000개 × 프로필 3. 1회 실행은 수 시간이다. 게이트는 N = 100, 작은 K로 하네스 논리만 확인한다.
- 생성 코드는 실제 코드보다 증명이 쉽고 테스트가 가볍다(보고서 "해석상 주의"). 결과는 이 코퍼스의 범위로만 주장한다.
- 첫 구현에서 드러난 것: `iface` 해시가 `#[uses]`를 담아(ADR-0019) 증분 키(ADR-0032)가 피호출자의 `#[uses]` 변경에도 호출자를 다시 증명한다. 건전하지만 방화벽이 그만큼 넓다. N = 100 이력에서 body 편집의 35~43%가 `#[uses]`를 바꿨다. BCB는 현재 동작 그대로 재고, 개선은 2D-22(채택된 ADR 변경이라 승인)로 둔다.

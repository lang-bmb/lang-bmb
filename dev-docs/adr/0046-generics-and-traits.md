# ADR-0046: 제네릭과 trait

- 상태: 채택 (2026-10-26, 사람 승인 "1/2 채택, 승인", 백로그 2V-12)
- 날짜: 2026-10-26
- 관련: ADR-0045(판단 기준), ADR-0026 §1(사용자 제네릭·trait 미룸), ADR-0027, DESIGN.md 원칙 5·6·8, §4.1 "다형성"·"타입", 점검 `dev-docs/reviews/2V-01-judgment-retro.md` R5, 백로그 2V-06


## 채택 시 확인 (2026-10-26)
- 진단 번호(`compiler/src/diag.rs`와 제안 ADR-0029·0030의 잠정 번호를 피해 비어 있음을 확인): E0235 blanket impl, E0236 `dyn Trait`, E0237 타입 인자 생략(기계 수정), E0311 겹치는 impl·모호한 trait 메서드, E0312 trait와 타입 어느 쪽 단위에도 없는 impl, E0428 경계 불충족, E0429 타입 인자 개수, E0817 impl 메서드가 trait 계약을 정제하지 않음.
- 열린 질문: 1(상수 제네릭)·2(연관 타입)·4(구조적 `Eq`·`Ord` 파생)는 열어 둔다. 3(기본 메서드 본문)은 넣는다(Rust 표준, trait 계약만으로 증명된다).
- 구현 페이즈: ROADMAP 2T(제네릭).

## 구현 시 확인 (2026-11-08, 2T-09)
- `Vec<T>`(2026-11-08, 2T-10): 타입 매개변수는 `Vec`의 원소가 될 수 있다(그 전에는 E0402여서 §결과의 제네릭 컨테이너를 쓸 수 없었다). `Vec`의 원소가 될 수 없는 타입(배열이나 배열을 담은 데이터 타입, 2O-03b)이 그 매개변수에 들어오지 않도록, 정의(구조체·열거형의 필드, 함수의 시그니처·`let`·타입 인자, `impl`의 모든 함수)가 `Vec<T>`로 쓰는 매개변수는 암묵 경계 `elem`을 갖고 인스턴스마다 E0428로 확인한다(`check::elem_params`). trait 메서드와 impl 함수의 경계 비교에서 `elem`은 뺀다(각 몸의 `Vec`에서 나온다).
- `String`은 내장 `Eq`·`Ord`를 가진다(2026-11-08, 4B-04): Rust의 바이트 사전순이다. ADR-0092 §2 표가 `BTreeMap<K: Ord, V>`와 바이트 문자열 키의 맵(stage0 포팅)을 범위로 정했고 그 키가 `String`이다. 열린 질문 4(데이터 타입의 구조적 파생)와는 별개다. 제네릭 정의는 그대로 정렬 위 비해석 전순서로 한 번 증명된다. `String` 인스턴스에서 비교는 텍스트의 순서(인코더는 텍스트를 `&[u8]`로 낮추므로, 타입 인자가 그것인 인스턴스의 비교를 `text_cmp_spec`·`text_cmp_code`로 보낸다: `verify::text::is_lowered_text`), `==`는 길이 안의 바이트 같음이다. 전순서 공리는 길이 안의 바이트로 같음을 정한 바이트 사전순에서 성립하므로(반대칭은 그 같음으로) 제네릭 증명은 인스턴스에서도 건전하다. 코드 생성은 인스턴스의 비교를 `bmb_str_cmp`로 한다(`codegen::text::text_targ`). 시험 `tests/verify/pass/text_ord`(`"B" < "a" < "ab" < "é"`), `fail/text_ord`(반대 주장, 자신보다 작음).
- trait의 `Self`는 §2의 다른 타입 매개변수와 같은 소유 규칙을 따른다: 경계는 그 trait 하나이고 `Copy`가 없으므로, `self: Self`와 `Self` 값은 이동한다. 첫 구현(2T-07a)은 검사기가 `Self`에 `Copy` 경계를 몰래 붙여 `Vec`·`String`·`Box`를 담은 타입이 trait을 구현하지 못했다(2M-03 감사에서 발견). 이 결정 안의 구현 교정이고 새 결정이 아니다. `Self`를 `T: Copy + Tr`의 `T`에 넘기던 명세 술어(`scored<T: Copy + Score>`)는 `Copy`를 빼서 옮겼다(Rust의 `Self`도 `Copy`가 아니다). 상위 경계(`trait Tr: Copy`, Rust의 supertrait)는 수요가 나올 때 따로 정한다.

## 맥락
ADR-0026은 사용자 제네릭과 trait를 "제네릭 페이즈로" 미뤘지만 그 페이즈는 로드맵에 없다. 그래서 정렬된 맵 같은 컨테이너와 정렬·탐색 같은 알고리즘을 타입마다 복제하거나 내장해야 한다는 우회가 권장안에 들어갔다(점검 R5·R12). Rust에서 제네릭과 trait는 표준 라이브러리 전체의 바탕이고, 검증 쪽 선례(Verus)도 제네릭 정의를 한 번 증명한다. 원장(DESIGN §4.1 "다형성")이 금지하는 것은 blanket impl과 암묵적 trait 해석이지 제네릭 자체가 아니다.

## 결정

### 1. 범위
| 넣음 | 뺌(사유) |
| --- | --- |
| 함수·구조체·열거형·고유 `impl`의 타입 매개변수 `<T, U>` | 상수 제네릭(배열 길이 매개변수는 열린 질문 1) |
| trait 경계 `T: Ord`, `T: Ord + Copy`, `where` 절 | 고계 경계, `?Sized` |
| `trait Name { fn ..; spec fn ..; }`: 메서드 시그니처와 계약 | 연관 타입·연관 상수(열린 질문 2), 기본 메서드 본문(열린 질문 3) |
| `impl Trait for Type`, `impl<T: B> Trait for Wrap<T>`: 겹치지 않는 명시적 impl | `impl<T> Trait for T` 같은 blanket impl, 특수화(원장 "다형성") |
| 내장 trait `Copy`, `Eq`, `Ord`(계약과 함께, 정수·`bool`·`u8`에 내장 impl) | trait 객체 `dyn Trait`(정적 호출 대상: 원장 "호출 해석") |
| 호출의 타입 인자 `max::<i64>(a, b)` | 타입 인자 생략은 도구가 채운다(§3) |

### 2. 의미
- 타입 매개변수는 소유 규칙을 따른다. 경계에 `Copy`가 없으면 `T` 값은 이동한다(ADR-0031 §2, ADR-0047). `Copy` 경계가 있으면 복사다.
- trait 메서드 호출은 `Trait::method(x, ..)` 또는 수신자 구문(ADR-0051)으로 쓴다. 대상은 경계와 인자 타입으로 정적으로 정해진다. 둘 이상의 경계 trait에 같은 이름이 있으면 경로 형태를 요구한다(Rust와 같음).
- 일관성: 한 (trait, 타입) 쌍에 impl은 하나다. impl은 trait나 타입 중 하나와 같은 단위에 둔다(Rust의 orphan 규칙을 단위 경계로).

### 3. 표면과 정규형
- 정본은 타입 인자를 적은 호출 `f::<T>(..)`이다. 타입 인자를 생략하면 진단과 함께 기계적 수정이 인자 타입에서 채운다(원칙 6: 명시성은 산출물의 성질, 노동은 도구의 몫). 인자 타입이 모두 명시되어 있어(원장 "타입") 단일화는 결정론적이다.
- 맵 L1은 타입 매개변수와 경계를, L2는 제네릭 정의로 가는 호출 간선과 타입 인자를 기록한다.

### 4. 증명 인코딩
- 제네릭 정의는 **한 번** 증명한다. 타입 매개변수는 SMT 비해석 정렬(`declare-sort`)이고, 경계 trait의 메서드는 그 정렬 위의 비해석 함수와 trait 계약(사실)이다. 슬라이스 자급(원칙 5)은 "본문 + 의존 계약 + 경계 trait의 계약"으로 지켜진다.
- 호출자는 타입 인자를 대입한 피호출자 계약을 쓴다(정렬을 구체 정렬로 바꾼 사본).
- `impl Trait for Type`은 trait 계약의 의무를 진다: impl의 각 메서드가 trait의 `requires`보다 약한 전제와 `ensures`보다 강한 결과를 가짐(Verus·Dafny의 trait 정제 의무와 같음).
- 내장 `Ord`의 계약은 전순서 공리(반사·반대칭·추이·전체)다. 정수 impl은 `<=` 그 자체다.
- 데이터 타입 인스턴스(`Pair<i64, bool>`)는 ADR-0027 인코딩을 인스턴스별로 쓴다.

### 5. 코드 생성
- 단형화한다(rustc와 같음). 인스턴스 이름은 경로와 타입 인자의 정규 텍스트에서 결정론적으로 만든다. 증분 IR 키는 인스턴스별이다.

### 6. 거부할 Rust 습관과 진단(번호는 채택 때 `diag.rs`에서 확정)
| 습관 | 처리 |
| --- | --- |
| `impl<T> Trait for T`(blanket) | 거부, 안내: 타입별 명시 impl |
| `dyn Trait`, `Box<dyn Trait>` | 거부, 안내: 열거형으로 닫힌 변형, 또는 제네릭 경계 |
| 타입 인자 생략 | 진단 + 기계 수정(채움) |
| `#[derive(PartialEq, Ord, ..)]` | 기존 처리(ADR-0026) + 구조적 `Eq`·`Ord` 파생은 열린 질문 4 |

E0207의 "generic parameters are not supported in milestone 1"과 "`impl Trait for T` is not supported"는 채택과 함께 없어진다(코드 E0207은 다른 미지원 구성에 남는다).

## 근거(검토한 대안)
| 안 | 판정 |
| --- | --- |
| **제네릭 + trait 경계, 정의마다 한 번 증명, 단형화 코드(채택 제안)** | Rust 표면 그대로(S1). Verus가 같은 방식으로 제네릭을 한 번 증명한다. 컨테이너·알고리즘을 라이브러리로 쓸 수 있다 |
| 맵·집합 등 컨테이너만 내장 | 사용자 정의 컨테이너를 막고, 내장과 사용자 정의의 규칙이 갈린다(S3). 표준 라이브러리가 컴파일러에 묶인다 |
| 단형 라이브러리 복제 | 우회(ADR-0045 §3). 복제마다 증명 비용과 맵 노드가 는다 |
| 인스턴스마다 증명(템플릿) | 증명 비용이 인스턴스 수에 비례하고, 제네릭 정의의 계약이 정의 자체로 검증되지 않는다 |

## 결과
- 표준 라이브러리(4B)가 제네릭 컨테이너(`BTreeMap<K, V>`, `BTreeSet<T>`)와 알고리즘(`sort<T: Ord>`)으로 쓰인다(점검 R12).
- 증명 인코딩에 정렬 매개변수와 trait 계약이 들어온다. 안정성(V7)과 비용(V4)을 구현 때 잰다.
- 퍼저: 데이터 퍼저에 제네릭 컨테이너와 경계를 넣는다.

## 열린 질문
1. 상수 제네릭(`[T; N]`의 `N`): 배열 반환과 함께 필요해질 수 있다.
2. 연관 타입: 반복자가 없으므로(ADR-0049) 당장 필요 없다. 필요해지면 따로 정한다.
3. 기본 메서드 본문: trait 계약만으로 증명되므로 넣을 수 있다. 첫 구현에서 뺄지 정한다.
4. 구조적 `Eq`·`Ord` 파생: `#[derive]` 금지(ADR-0026)와의 관계. 실행 코드의 데이터 타입 `==`(ADR-0026 열린 질문 1)과 함께 정한다.

# ADR-0079: 명세의 `exists`

- 상태: 채택 (사람 승인 2026-11-01 "권장안 채택, 승인사항 승인": 백로그 T0-25. 언어 범위(ADR-0016)를 넓힌다)
- 날짜: 2026-11-01
- 관련: ADR-0016(언어 범위), ADR-0017 §4(명세 인코딩), ADR-0023·0075(기저 인스턴스 재시도), ADR-0045(판단 기준, 편의 포기 원장), 백로그 T0-19, T0-25

## 맥락

- 에이전트는 존재 꼴 계약에 Verus의 `exists` 한정 기호를 먼저 쓴다. 파일럿 2차 BVB 45세션 중 11세션, 존재 꼴 과제 다섯이 모두 그렇고, qwen의 BRB `t12`도 그렇다(`dev-docs/experiments/T0-19/results.md` §3).
- BMB에는 `exists`가 없었다. 컴파일러는 그것을 E0103 "expected `;`, found `:`"와 틀린 기계적 수정("insert `;` before `:`")으로 거부했다.
- 에이전트가 대신 쓴 꼴(재귀 술어, 색인 술어 트리거)은 같은 뜻인데 판정기가 결정하지 못하는 꼴이었다(T0-19 (가)·(나)). (나)는 T0-24(ADR-0075)가 풀었다. 상류 원인인 `exists`의 부재는 남았다.
- JUDGMENT §7: 편의 포기 원장(DESIGN §4.1)에 없는 제한은 결함이다. `exists`는 Verus의 정석 표면이고(DESIGN §1 "Verus 계열 명세 문법"), 같은 뜻을 `!(forall|x| !P)`로 쓰게 하는 것은 원장에 없는 엄격화다.

## 결정

1. **표면.** 명세 문맥에 `exists|x: T, ..| e`를 둔다. 문법·묶음·문맥 규칙은 `forall`과 같다. 묶음 변수는 정수 타입이고(E0402), 명세에서만 쓴다(E0503). `#[trigger]`가 하나 이상 있어야 하고(E0511), 트리거들이 모든 묶음 변수를 함께 언급해야 한다(E0512). 모든 트리거는 한 다중 패턴이다. 진단 문구는 한정 기호의 이름을 쓴다.
2. **구문 트리.** `ExprKind::Forall`을 `ExprKind::Quant { q: Quantifier, binders, body }`로 넓힌다(`Quantifier::Forall | Exists`). 정규형은 `exists|..| ..`이고, JSON AST(ADR-0073)의 종류는 `"exists"`다. 정체성 해시(ADR-0059)는 정규형을 따르므로 `forall`과 `exists`를 가른다. `exists`는 예약어가 된다(코퍼스·시드·라이브러리에 이 이름의 식별자는 없다).
3. **인코딩.** SMT `exists`다. 묶음 변수의 정렬, 범위 사실, 트리거 패턴은 `forall`과 같다. 범위 사실은 `forall`에서 `=>`의 앞이고 `exists`에서는 `and`의 한 항이다. 한정 기호 안의 재귀 호출의 감소 의무는 둘 다 "묶음 변수의 모든 값에 대해"다(2V-05). 기저 인스턴스 재시도(ADR-0075)는 이미 `exists`가 묶는 변수를 센다.
4. **도구.** 트리거 린트 W0906, 맵의 호출 간선, 이름 바꾸기·참조 찾기, 명세 약화 감지(`bmb weaken`)는 같은 노드를 지나므로 그대로 적용된다.

## 근거

- **원인과 귀속 층:** 언어(원장에 없는 제한, JUDGMENT §7)와 도구(틀린 수정). 판정기를 고치거나(후보 B) 프롬프트로 "`exists` 대신 `!(forall ..)`"를 가르치는 것(후보 D)은 증상을 다른 층에서 흡수한다(T0-19 §5).
- **정석:** Verus·Dafny 모두 명세에 `exists`를 두고 트리거 규칙을 `forall`과 같게 한다. SMT-LIB의 `exists`는 패턴을 받는다(부정 위치에서 인스턴스화).
- **한 노드로 넓힌 이유:** 두 한정 기호는 묶음·트리거·문맥 규칙이 같고 인코딩의 두 군데(연결자, 기호)만 다르다. 변형을 따로 두면 모든 순회가 두 갈래를 같이 다뤄야 하고, 하나를 빠뜨리면 한 한정 기호에서만 생기는 결함이 된다.
- **확인(T0-19 판정기, 동결 하네스 그대로):** BVB 808 과제에 `r == (exists|j| j < arr.len() && #[trigger] arr[j] == k)`로 쓴 계약과 루프 불변식이 증명되고 숨은 명세 검사에 받아진다(`dev-docs/experiments/T0-19/judge.py`, `accepted: true`).

## 결과

- 시험: 통과 코퍼스 `tests/verify/pass/exists.bmb`(사후조건, 사전조건, 루프 불변식의 `exists`), 실패 코퍼스 `tests/verify/fail/exists.bmb`(반례가 붙은 E0802, 그리고 `exists` 사전조건에서 나온 범위 사실로 증명되는 색인), 검사 코퍼스 `tests/check/err/exists.bmb`(E0511·E0512·E0402·E0503). 같은 코퍼스로 정규형 왕복, JSON AST 왕복, 결정론 시험이 돈다.
- 진단 문구: E0510의 수정 문구가 "`forall` or `exists` body"가 된다. 한정 기호의 E0402·E0503·E0512에는 수정 안내가 붙는다(정수 색인으로 묶기, 명세 함수로 옮기기, 그 변수를 언급하는 항도 트리거로). 그래서 `tests/check/err/specs.jsonl`·`places.jsonl`의 다섯 줄이 바뀌고, 수정 안내가 붙은 오류의 비율(P3)이 0.8722 → 0.8778이다. 진단 표(`docs/diagnostics.md`)의 E0510·E0511·E0512·W0906 설명이 두 한정 기호를 함께 말한다.
- 측정 조건: 컴파일러 트리가 바뀌므로 새 조건이다(ADR-0070 (a)). 동결 프롬프트와 집합은 그대로다. BVB 이식 규칙(`bench/bvb/README.md` T3 "M1에 `exists` 없음")은 동결 집합의 기록이라 고치지 않는다.
- 되돌리기: 파서에서 `exists`를 빼면 이전 표면이다(구문 트리의 `Quantifier`는 남아도 된다).

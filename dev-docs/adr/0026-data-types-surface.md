# ADR-0026: 데이터 타입 표면: 구조체·열거형·`match`·`impl`

- 상태: 제안
- 날짜: 2026-10-24
- 관련: DESIGN.md 원칙 3·6·8, §4.1·§5, ADR-0013·0015·0016·0019·0020·0027, 백로그 2B-01

## 맥락
M1(ADR-0016)은 구조체·열거형·`impl`을 뺐고, `Option` 부재가 가장 먼저 걸릴 것으로 보았다. 2B는 이것을 넣는다(ROADMAP 2B). Rust 표면을 승계하되(ADR-0013) M1에서 굳힌 규칙(정규형 하나, 모든 타입 명시, 셰도잉 금지, 계약은 이름 붙은 술어, 호출 대상이 구문으로 확정)과 2차 참조(ADR-0015)를 데이터 타입에도 그대로 적용해야 한다. 이 ADR은 표면과 검사기 의미만 정한다. 증명 인코딩은 ADR-0027이 정한다.

## 결정

### 1. 범위
| 넣음 | 뺌(사유) |
| --- | --- |
| 이름 붙은 필드의 `struct` | 튜플 구조체, 유닛 구조체, 튜플 타입(형태 하나: 원칙 8) |
| `enum`의 유닛 변형 `A`, 튜플 변형 `B(T, U)` | 구조체형 변형 `C { x: T }`(형태 하나. 필드 이름이 필요하면 구조체를 싸서 `C(CData)`) |
| 내장 `Option<T>`, `Result<T, E>` | 사용자 제네릭, `trait`, `impl Trait for T`(제네릭 페이즈로 미룸. 제네릭 없이 trait는 이름공간 이상의 일을 하지 않는다) |
| 고유 `impl T { fn .. }`(이름공간) | 메서드 호출 구문, `self` 수신자(§4.1 호출 해석 금지) |
| `match`(변형마다 한 갈래) | `if let`, `while let`, `let else`, `matches!`, 가드, 중첩·or(`\|`)·리터럴·범위 패턴 |
| 필드 타입: 정수, `bool`, 고정 배열 `[T; N]`, 다른 구조체·열거형 | 참조 필드(ADR-0015, 기존 E0403), 슬라이스 필드, 재귀 타입(힙은 2G) |

### 2. 값 의미
- 2B의 데이터 타입은 힙을 담지 않는 **평범한 값**이다. 대입·인자 전달·반환은 복사다. `#[derive(Clone, Copy)]` 없이 그렇다. 이동이 의미를 갖는 타입은 힙과 함께 2G에서 정한다(백로그 2B-04 "이동 없는 값 의미").
- 참조는 인자 위치에만(ADR-0015): `&Point`, `&mut Point`, `&[Point]`, `&mut [Point]` 매개변수. 구조체를 반환하는 것은 값 반환이라 허용한다.
- `#[derive(..)]`는 쓰지 않는다. 구조적 동등 `==`는 **명세 문맥에서만** 내장이다(SMT 동등). 실행 코드의 데이터 타입 `==`는 2B에 없다(Rust에서도 `derive(PartialEq)` 없이 안 된다. 필요하면 필드를 비교하는 함수를 쓴다). 측정에서 마찰이 크면 재검토한다.

### 3. 구문(한 가지 형태)
| 일 | BMB 형태 | 규칙 |
| --- | --- | --- |
| 선언 | `struct Point { x: i64, y: i64 }`, `enum Shape { Dot, Circle(i64), Rect(Point, Point) }` | `mod` 안에. 단위 안에서 타입·함수·`spec fn`은 한 이름공간(이름 하나에 정의 하나) |
| 생성 | `Point { x: 1, y: e }`, `Shape::Circle(r)`, `Option::Some(v)`, `Option::None` | 모든 필드를 선언 순서로(정규형이 순서를 맞춘다). 변형은 항상 `타입::변형`. 다른 단위는 `geo::Point { .. }` |
| 필드 읽기 | `p.x`, `p.q.x`, `a[i].x` | `p: &Point`·`&mut Point` 매개변수도 `p.x`(필드 투영은 구문으로 확정되므로 호출 해석 금지에 걸리지 않는다). `(*p).x`는 `p.x`로 |
| 필드 쓰기 | `p.x = e;`, `a[i].x = e;` | `let mut` 지역 또는 `&mut` 매개변수의 자리. 전체 교체는 `*p = Point { .. };` |
| 분기 | `match s { Shape::Dot => e0, Shape::Circle(r) => e1, Shape::Rect(a, b) => e2 }` | 갈래는 변형마다 정확히 하나, 선언 순서, 와일드카드 갈래 없음. 페이로드 자리는 새 이름 또는 `_`. 바인딩 이름도 셰도잉 금지 규칙을 따른다 |
| 연관 함수 | `impl Point { fn norm1(p: &Point) -> i64 { .. } }`, 호출 `Point::norm1(&p)` | 타입당 `impl` 블록 하나, 타입과 같은 단위. 경로는 `unit::Point::norm1` |

`match`의 망라성은 검사기가, 각 갈래의 의무(그 변형이라는 경로 조건 아래)는 증명기가 확인한다(ROADMAP 2B 기준 2). 와일드카드를 금지하므로 변형을 추가하면 그 열거형의 모든 `match`가 망라성 오류로 드러난다. `impact`(백로그 2D-02)가 계산하는 영향과 같은 범위다.

### 4. 명세
- 명세 문맥에서 필드 읽기, `match`(값을 내는 식), 명세 `==`를 쓸 수 있다. `old(p)`는 `&mut` 구조체 매개변수에도 쓴다(`old(p).x`).
- 계약 절은 여전히 이름 붙은 술어 호출만(원칙 3). 변형 판별은 `matches!` 대신 이름 붙은 `spec fn`의 `match`로 쓴다.
  ```rust
  spec fn is_some(o: Option<i64>) -> bool { match o { Option::Some(_) => true, Option::None => false } }
  ```
  `is_some`·`is_ok` 같은 판별 술어를 내장할지는 열린 질문이다(§열린 질문 2).
- 반례는 Rust 표기로 돌려준다: `p = Point { x: 1, y: 2 }`, `o = Option::Some(992)`(ADR-0027).

### 5. 거부할 Rust 습관과 진단 코드
`compiler/src/diag.rs`에서 비어 있는 범위를 쓴다. 번호는 2B-04에서 확정하고, 제안 범위는 다음과 같다.

| 범위 | 범주 |
| --- | --- |
| E0212~E0239 | Rust 습관(E02xx 계속). 아래 표 |
| E0305~E0319 | 이름: 알 수 없는 타입·필드·변형, 중복 필드·변형, 타입 밖 단위의 `impl`, 두 번째 `impl` 블록 |
| E0412~E0439 | 타입: 생성자 필드 누락·초과, 페이로드 개수, 구조체가 아닌 값의 필드 접근, 열거형이 아닌 값의 `match`, 망라성(빠진 변형·중복 갈래), 실행 코드의 데이터 타입 `==`, 재귀 타입 |
| E0814 재사용 | 증명 게이트가 아직 다루지 않는 구성(기존 코드) |

| 습관 | 제안 형태 | 기계적 수정 |
| --- | --- | --- |
| `#[derive(..)]` | 지운다(복사·명세 동등이 내장) | 예 |
| `Some(x)`, `None`, `Ok`, `Err` | `Option::Some(x)` 등 전체 경로 | 예 |
| `Point { x, y }`(필드 축약) | `Point { x: x, y: y }` | 예 |
| `Point { x: 1, ..p }`(갱신 구문) | 모든 필드 나열(`y: p.y`) | 예(검사기가 필드를 안다) |
| `_ =>` 갈래 | 빠진 변형마다 갈래(`_` 페이로드, 같은 본문) | 예 |
| `if let P = e { A } else { B }` | `match`(나머지 변형 → `B`) | 예 |
| `while let`, `let .. else` | `match`와 `while` | 아니오 |
| `p.f(..)`(메서드 호출) | `T::f(&p, ..)` | 예(시그니처의 참조 종류로 `&`/`&mut`) |
| `&self`, `&mut self`, `self` | `this: &T` 등 이름 붙은 매개변수 | 예(본문의 `self` → `this`) |
| `.unwrap()`, `.expect(..)` | `match`로 실패 경로를 명시(panic 없는 전함수, §4.1 실패) | 아니오 |
| `let Point { x, y } = p;` | `let x: i64 = p.x;` … | 예 |
| `(*p).x` | `p.x` | 예 |
| 가드·중첩·or(`\|`)·리터럴 패턴 | 갈래 본문의 `if`, 중첩 `match` | 아니오 |
| 튜플 구조체·튜플·구조체형 변형 | 이름 붙은 필드 구조체 | 아니오(이름이 필요) |

`matches!`·`vec!` 등은 기존 E0202(매크로)이고, 수정 메시지만 이 표의 형태를 가리키게 한다. `?`는 기존 E0206이다. `use E::*`·`trait`·`impl Trait for T`는 언어 범위 밖(기존 E0207 계열)이지 습관 오류가 아니다. 이 습관들은 Rust 습관 오류율(DESIGN.md §4.1, R4)로 센다.

### 6. 정규형·해시·맵(ADR-0019·0020)
- 정규형: 단위 안에서 하위 단위 → 타입(이름순, 각 타입의 `impl` 블록이 바로 뒤) → 함수(이름순). 구조체 필드와 변형은 **선언 순서를 유지**한다(정의의 일부다). 생성 식의 필드는 선언 순서로 정렬한다. `impl` 안의 함수는 이름순.
- 해시: 타입 선언은 본문 해시 = 계약 해시(선언 자체가 표면이다. `spec fn`과 같은 처리). 타입을 언급하는 정의의 한정 정규형은 타입을 전체 경로로 쓴다.
- 맵(하위 호환 추가만): L0 `def_kind`에 `"struct"`·`"enum"`, `impl` 함수는 `unit::T::f` 경로의 `"fn"`. L1 타입 행의 `signature`는 선언의 정규형. L2에 새 `kind` `"types"`(정의가 시그니처·본문·계약에서 타입을 언급)를 추가하고, `impact`는 타입 변경을 `reason: "types"`로 전파한다.
- 타입 능력 뷰(DESIGN.md §7.2)는 `impl` 블록이 타입당 하나라 평탄화가 자명하다.

## 근거
- **표면 승계(ADR-0013):** 모든 허용 형태는 그대로 유효한 Rust다(`Point::norm1(&p)`는 Rust의 연관 함수 호출, `Option::Some`은 Rust에서도 유효). "선택을 필수로"의 예: 변형 경로 한정, 모든 필드 명시, 갈래 전부 나열.
- **호출 해석 금지(§4.1):** 메서드 호출 구문은 수신자 타입과 auto-ref에 기대어 대상을 정한다. 경로 호출만 두면 L2 `calls` 엣지가 구문에서 바로 나온다.
- **정규형 하나(원칙 8):** `match` 하나로 `if let`·`matches!`·`let else`를 대신한다. 형태가 하나면 동형 함수 탐지(`duplicates`)와 정규형 해시가 그대로 통한다.
- **와일드카드 금지:** 변형 추가가 모든 사용처를 증명기 이전에 드러낸다. 변경 영향(§7.2)과 일치한다.
- **값 의미:** 힙이 없으면 이동과 복사가 관찰상 같다. 이동 검사를 2G로 미뤄 2B의 검사기·증명기 범위를 줄인다. 참조 필드 금지는 ADR-0015의 귀결이다.
- **명세 동등만 내장:** SMT 동등은 공짜이고 계약에서 자주 필요하다. 실행 `==`는 코드 생성·`derive`와 얽히므로 측정으로 필요를 확인한 뒤 넣는다.
- **명시성은 도구의 몫(원칙 6):** 거부 표의 대부분은 기계적 수정을 가진다. 에이전트가 Rust 습관대로 써도 `bmb fix`가 정규형으로 옮긴다.

검토한 대안: (1) `trait`·`impl Trait for T`를 2B에 포함: 제네릭 없이 쓸모가 없고, 겹침 없음 검사를 제네릭과 함께 설계해야 한다. (2) 메서드 호출 구문 허용 + 도구가 해석: 해석된 대상이 텍스트에 없어 슬라이스 자급(원칙 5)을 깬다. (3) 구조체형 변형 허용: 형태가 둘이 되고 생성·패턴 문법이 두 벌이 된다.

## 결과
- 구현 태스크 2B-03(구문·정규형)~2B-07(맵)이 이 표면을 따른다. 사람 승인 전에는 구속력이 없다(ROADMAP 진행 규칙).
- 갈래 본문 중복(와일드카드 금지)과 필드 전부 나열로 코드가 길어진다. 슬라이스 크기 측정(R4)에 드러난다.
- 실행 `==`, 판별 술어, 구조체형 변형, 메서드 구문의 부재가 Rust 습관 오류율을 올릴 수 있다. 2B-10 측정으로 확인하고, 유추 손실이 크면 되돌린다(§4.1 대응 3).

## 열린 질문
1. 실행 코드의 구조적 `==`를 내장할지(코드 생성에서 필드별 비교로 펼침).
2. `Option::is_some` 같은 판별 술어를 명세 내장으로 둘지, 사용자가 `spec fn`으로 쓰게 할지(표준 술어 단위 `std::option`을 둘 수도 있다).
3. 타입 불변식(Verus `type_invariant`): 생성·필드 쓰기마다 의무를 붙일지. 필드 공개 범위(`pub`)가 없으므로 2B에서는 넣지 않는 쪽이 기본안이다.
4. `Option<T>`·`Result<T, E>`의 `T`에 허용할 타입: 2B 기본안은 정수·`bool`·구조체·열거형(중첩 `Option<Option<i64>>` 포함).
5. 실행 코드의 `match`가 값을 내는 식이므로, 갈래가 모두 `()`일 때 문장 형태(`match ..;`의 `;` 유무)를 정규형에서 어떻게 쓸지.

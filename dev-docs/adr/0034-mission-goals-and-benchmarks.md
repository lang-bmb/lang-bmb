# ADR-0034: 미션 목표와 벤치마크 체계

- 상태: 채택 (사람 승인 2026-10-24, 권장안). 목표값은 잠정이며 1E-10 결과로 한 번 확정한다
- 날짜: 2026-10-24
- 관련: DESIGN.md §2(전제·목표)·§3(원칙)·§9 R4, ADR-0021(측정 절차), ADR-0025(`m1b`), ROADMAP 2A·2H·3E

## 맥락
지금 측정은 BMB 안에서만 닫혀 있다(m1·m1b 과제, Rust 성능 기준선, 퍼저). "BMB가 미션을 달성했는가"를 판정하려면 두 가지가 더 필요하다.

1. **외부 위치:** 공개 벤치마크에서 같은 모델이 다른 검증 언어(Verus·Dafny·Lean)로 얼마나 하는지와 비교할 수 있어야 한다.
2. **전제 검증:** DESIGN.md의 전제 E2·E3("병목은 검증과 탐색이다", "쓰기 비용을 올려 검증·탐색 비용을 낮추는 거래는 이득이다")를 직접 재는 비교 실험이 없다. 지금 측정은 BMB가 "된다"는 것만 보이고 "더 낫다"는 것은 보이지 않는다.

## 조사: 공개 벤치마크 (2026-10 기준, 수치는 각 논문 보고값이며 서로 직접 비교할 수 없다)

### 검증된 코드 생성 (가장 가까운 비교 대상)
| 벤치마크 | 언어 | 규모 | 과제 | 보고된 수준 |
| --- | --- | --- | --- | --- |
| Verus-Bench (AutoVerus, OOPSLA 2025) | Verus/Rust | 150 | 주어진 코드·명세에 증명 작성 | 에이전트 시스템 91%(137/150), GPT-4o 직접 45%. 후속 KVerus 재현에서는 AutoVerus 87/150 |
| Vericoding (2025-09) | Dafny·Verus·Lean | 명세 12,504(Verus 2,334) | 형식 명세 → 코드+증명 | 기성 LLM: Dafny 82%, Verus 44%, Lean 27% |
| VeriContest (NeurIPS 2026) | Verus/Rust | 946(이후 1,007) | 자연어 → 코드·명세·증명, 양·음 테스트 포함 | 최고 모델: 코드 92%, 명세 48%, 증명 14%, 종단 5.3% |
| VERINA (2025) | Lean 4 | 189 | 코드·명세·증명 생성 | o4-mini: 코드 61%, 명세 51%, 증명 3.6% |
| DafnyBench / Clover | Dafny | 수백 / 수십 | 주석(불변식 등) 복원 / 3중 일관성 | 참고용 |

**관찰:** 공개 결과에서 병목은 코드가 아니라 **명세와 증명**이다(VeriContest: 코드 92% 대 종단 5%). BMB의 차별점(반례, 힌트, `#[uses]` 자동 채움, 린트, 영향 분석)이 겨냥하는 곳이 정확히 여기다. 또 Verus는 BMB와 표면이 같아 **과제를 이식해 같은 모델로 직접 비교**할 수 있다.

### 명세 품질
| 벤치마크 | 측정 |
| --- | --- |
| nl2postcond (FSE 2024) | 사후 조건의 정확성과 판별력(틀린 구현을 거부하는가) |

BMB는 명세 강도 검사(ADR-0021, 숨은 기준 계약 함의)와 변이 린트(W0904)를 이미 갖고 있어 같은 지표를 계산할 수 있다.

| MCP-Bench, MCPAgentBench | 도구 사용 에이전트의 상호작용 수·**1k 토큰당 점수**(토큰 효율) 정의를 차용 |

### 성능
Rust 기준선 하네스(`bench/baseline`, 안전·unchecked Rust 대비)가 이미 있다. 외부 비교는 Benchmarks Game 류 과제를 같은 하네스로 이식하는 것으로 충분하다.

## 결정(제안)

### 1. 북극성
> **같은 모델·같은 예산에서, 에이전트가 BMB로 쓴 코드는 Rust+테스트로 쓴 코드보다 결함이 적고, 검증된 언어(Verus)로 쓴 코드보다 1회 성공률이 높으며, 코드베이스가 커져도 탐색 비용이 늘지 않고, 성능은 안전 Rust와 같다.**

이를 다섯 목표로 나눈다. 각 목표는 지표, 벤치마크, 단계별 목표값을 갖는다.

| 목표 | 지표 | 벤치마크 | M1(지금) | M2 | M3 |
| --- | --- | --- | --- | --- | --- |
| G1 판정 신뢰 | 건전성 위반 수, 거짓 반례 수 | 퍼저 7종(게이트·야간) | 0 | 0(새 기능 포함) | 0 |
| G2 1회 정확성 | 작성 과제 1회 성공률(명세 강도 검사 포함) | m1·m1b, **BVB**(아래) | m1 ≥ 60% | m1b ≥ 60%, BVB에서 Verus 대비 +10%p | m2 ≥ 60% |
| G3 명세 품질 | 변이체 판별률(숨은 변이체를 명세가 거부하는 비율) | m1b 작성 과제 + 변이 | 측정 시작 | ≥ 90% | ≥ 90% |
| G4 탐색 확장성 | 질의당 토큰·시간의 크기 무관성, 탐색 정확도, 파일 기반 대비 토큰 비 | m3(1만 정의), **BNB**(아래) | 응답 크기 무관 ✅, 시간 무관 ✅ | 탐색 P·R=1 ≥ 80% | 1만 정의에서 파일 기반 대비 토큰 1/3 이하, 정확도 동등 이상 |
| G5 전제 E2·E3 | 숨은 결함률, 총 토큰(쓰기+검증), 벽시계 | **BRB**(아래) | — | 결함률 Rust+테스트의 1/2 이하, 총 토큰 2배 이내 | 같은 조건에서 총 토큰 Rust+테스트 이하 |
| G6 성능 | 안전 Rust 대비 시간 비 | `bench/baseline` + 이식 과제 | ±5% ✅ | ±5% | 증명 기반 최적화가 측정될 때만 "더 빠름" 주장 |
| (공통) Rust 습관 오류율 | E02xx / 커밋 | 모든 에이전트 측정 | 기록 | 감소 추이 | 감소 추이 |

목표값은 출발점이다. 1E-10(실제 모델) 결과가 나오면 첫 보정을 하고, 이후에는 단계 종료(2H, 3E) 때만 바꾼다. 측정 절차의 규칙(동결, 1회, 재시도 없음, 편향 명시)은 ADR-0021을 따른다.

### 2. 만들 벤치마크

| 이름 | 내용 | 비교 대상 | 단계 |
| --- | --- | --- | --- |
| **BVB** (BMB-Verus Bench) | 공개 Verus 과제(Verus-Bench, Vericoding Verus, VeriContest)에서 BMB 범위에 드는 것을 이식. 원본 명세를 숨은 기준 계약으로. 같은 모델을 원본 Verus 툴체인에서도 돌린다 | 같은 과제·모델의 Verus 결과(직접 실행) + 논문 보고값(참고) | 2A 직후(M1 범위 과제만), 2B 이후 확장 |
| **BRB** (BMB vs Rust+tests) | 같은 과제를 (a) BMB+증명, (b) Rust+에이전트가 쓴 테스트로 풀게 하고, 숨은 적대적 테스트와 변이체로 결함을 잰다. 토큰·시간·결함률 | Rust+테스트 | M2 측정(2H)의 핵심 |
| **BNB** (BMB Navigation Bench) | m3 생성기로 만든 1만 정의 코드베이스와, 같은 구조로 생성한 Rust 쌍둥이. 같은 탐색·수정 질문을 BMB(MCP 맵 도구)와 Rust(파일·grep 도구)로 | 파일 기반 에이전트 | 3A·3E |
| **BSB** (Spec strength) | m1b 작성 과제마다 숨은 변이체 집합. 에이전트 명세의 판별률 | nl2postcond·POSTCONDBENCH의 정의 | 2A |
| m1 / m1b / m2 / m3 | 기존·계획된 내부 과제 집합 | 자기 자신(추이) | 진행 중 |

공정성 규칙(ADR-0021 확장): 비교군은 같은 모델·같은 토큰 상한·같은 1회 규칙. Rust 쪽 도구도 같은 수준으로 지원한다(컴파일러 오류, 테스트 실행 도구). 이식한 과제는 원본 출처와 변환 규칙을 함께 커밋하고, 이식에서 빠진 과제의 비율과 이유를 보고한다(선택 편향 공개).

### 3. 하지 않는 것
- 일반 코딩 벤치마크(SWE-bench 등)에서 점수를 내는 것은 목표가 아니다. BMB에는 그 생태계가 없다(4단계 전).
- 논문 보고값과 우리 측정을 한 표에서 순위로 비교하지 않는다. 비교는 우리가 같은 조건에서 직접 돌린 것만 한다.

## 근거
- 공개 검증 코드 벤치마크의 병목(명세·증명)이 BMB의 차별점과 정확히 겹친다. 이식 비교가 가장 싼 외부 검증이다.
- E2·E3는 BMB의 존재 이유인데 직접 재는 실험이 없다. BRB 없이는 "증명 언어가 테스트보다 낫다"를 주장할 수 없다(genesis §3.5: 주장은 측정으로만).
- 원칙 7은 m3에서 응답 크기·시간 모두 성립을 확인했다(`bench/m3/results`). 남은 것은 같은 질문을 파일 기반으로 풀 때와의 비교(BNB)다.

## 결과
- 채택되면 ROADMAP의 2A·2H·3E 통과 기준에 목표값을 넣고, 백로그에 BVB·BSB(2A), BRB(2H 준비), BNB(3A) 태스크를 만든다.
- 유료 실행이 늘어난다(모든 비교군을 같은 모델로 돌려야 함). 실행은 사용자 머신, 예산은 사람이 정한다.
- Verus 툴체인 설치가 측정 환경에 필요하다(BVB 비교군).

## 승인된 결정(2026-10-24, 권장안 채택)
1. 북극성은 채택. 목표값은 **잠정**으로 ROADMAP에 넣고, 1E-10 결과가 나오면 한 번 확정한다(그 뒤에는 단계 종료 때만 바꾼다).
2. G5 기준: 2단계는 "결함률 Rust+테스트의 1/2 이하, 총 토큰 2배 이내", 3단계는 "총 토큰 이하".
3. 측정 모델: 주 측정은 프런티어 모델 1개, 규모 효과 확인용으로 작은 모델 1개. 토큰 상한과 도구 호출 40회는 ADR-0021 그대로.
4. BVB: 공개 Verus 과제에서 30~50개 표본을 뽑아 원본 Verus를 같은 모델로 직접 실행한다. 논문 보고값은 참고로만 쓴다.
5. BRB: Rust 쪽에 property-based 테스트 도구(proptest)를 허용한다. 가장 강한 현실적 테스트 관행과 비교한다.
6. MCP 도구 설명: 첫 실행(m1, m1b)은 동결한 설명으로 한다. 이어서 새 도구(`impact`·`uses`·`lint`·`fix`)를 노출한 m1b 실행을 한 번 더 해서 도구 효과를 따로 잰다.

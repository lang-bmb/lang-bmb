# ADR-0088: 게이트웨이 용량 장애는 세션 결과가 아니다

- 상태: 채택 (자율 채택, AUTONOMY.md §4: ADR-0066·ADR-0021 범위 안의 측정 기반 처리). ADR-0066의 "재시도로 고쳐지지 않는 오류" 규칙을 보완한다
- 날짜: 2026-11-04
- 관련: ADR-0021 §1·§3, ADR-0066(게이트웨이 특성), ADR-0070, 백로그 INF-23·T0-33·T1-41

## 맥락

2026-11-04 06:50~07:07에 측정 셋을 동시에 돌렸다(qwen `bvb-write` 반복 병렬 4, qwen `brb-write` 반복 병렬 1, sonnet T1-41 병렬 4). 두 가지 장애가 났다.

- **sonnet 지출 한도:** 게이트웨이가 HTTP 402 `cap_reached`("spend cap on all its wallets", 일 단위, 2026-11-05 00:00 UTC 초기화)를 돌려줬다. 4xx라 어댑터가 재시도하지 않았고, ADR-0066대로 세션이 `stop: "api_error"`로 끝나 그때 상태로 판정됐다. 그 뒤 세션은 모델에 한 번도 닿지 못한 채 0초 만에 실패로 기록됐다. `bvb-ast` 44/45, `brb-diff` 22/24, `brb-ast` 24/24, `m1b-ast` 3/25가 그랬다.
- **qwen 동시 요청 한도:** HTTP 429 "The wallet has 8 requests in flight"와 502가 재시도(약 2분)를 넘겨 `bvb-write` 반복 1에서 세션 하나가 `api_error`로 끝났다. 원인은 동시 세션 합 9가 지갑의 동시 요청 한도 8을 넘은 것이다(측정 운영 실수).

ADR-0066의 규칙은 모델 쪽 원인(문맥 초과 HTTP 400)을 전제로 했다. 용량 장애는 모델·언어·과제 어느 것과도 관계가 없다.

## 결정

1. **지출 한도는 실행을 멈춘다.** HTTP 402 `cap_reached`는 `model_api.CapReached`로 올라가고 어떤 에이전트도 잡지 않는다. 그 세션의 행은 쓰이지 않고 실행이 끝난다. 한도가 풀린 뒤 같은 명령으로 재개하면 그 세션은 처음부터 한 번 돈다(INF-16: 행을 쓰기 전에 끊긴 세션은 결과가 없으므로 재시도가 아니다).
2. **동시 세션 합은 8 이하.** 한 지갑(게이트웨이 자격 증명)으로 동시에 도는 모든 실행의 `--jobs` 합을 8 이하로 둔다(BRB 팔은 1). 429·5xx는 지금처럼 전송 실패로 재시도한다.
3. **이 수정 전 실행의 처리.** 용량 장애(402 `cap_reached`, 재시도를 넘긴 429)로 끝난 세션이 하나라도 있는 집합 실행은 통째로 무효로 하고 같은 커밋·같은 조건에서 다시 돈다. 무효 판정은 결과를 보기 전의 규칙(오류 메시지의 종류)으로만 하고, 성공·실패와 무관하다. 무효 실행은 결과 디렉터리에 두지 않고 측정 보고서에 집합, 세션 수, 오류 종류를 적는다. 해당하는 것은 위 다섯 실행이다. 같은 시간대의 `m1b-diff`·`bvb-diff`(sonnet)와 `brb-write` 반복 1(qwen)은 용량 장애 세션이 없어 유효하다.

## 근거

- 용량 장애 세션을 실패로 세면 측정이 게이트웨이 운영 상태를 잰다. 같은 집합을 같은 커밋에서 다시 도는 것은 ADR-0021 §3의 "과제 재시도"가 아니다. 모델의 답을 본 뒤 고르는 것이 아니라, 모델이 답하지 못한 실행을 규칙으로 버리기 때문이다.
- **기각한 것:** (가) 무효 세션만 다시 돌려 행을 바꿔 넣기. 같은 실행 안에서 세션을 골라 다시 도는 것이라 실행 단위 규칙(ADR-0077 §1)과 맞지 않는다. (나) 402도 재시도. 한도는 일 단위라 재시도가 몇 시간을 기다리게 되고, 그동안 실행이 멈춰 있는 것과 같다.

## 결과

- 코드: `bench/m1/model_api.py`의 `CapReached`와 `post_json`. 시험: `bench/m1/test_model_api.py`의 `test_the_spend_cap_stops_the_run`.
- 운영: 측정 체크아웃(`e5247e8d`)의 하네스에는 이 수정이 없다. 그 커밋에서 sonnet을 돌릴 때는 한도를 넘지 않게 집합 단위로 나눠 돌리고, 끝난 뒤 `api_error` 행의 오류 종류를 확인한다.
- 되돌리기: `CapReached` 분기를 지우면 ADR-0066 그대로다.

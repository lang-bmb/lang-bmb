# ADR-0082: 필드가 같은 두 타입은 정체성 하나를 가진다(구조 정체성 유지)

- 상태: 채택 (자율 채택, AUTONOMY §4: ADR-0059 범위 안의 결정. ADR-0059를 바꾸지 않는다)
- 날짜: 2026-11-02
- 관련: ADR-0059 §1(정체성, 명목 타입과 trait), ADR-0063, ADR-0074(`expect`), 백로그 T1-28, 2D-19

## 맥락

- ADR-0059 §1은 타입의 텍스트에 그 타입의 trait `impl`만 넣는다. 그래서 trait를 구현하지 않고 필드가 같은 두 구조체는 같은 `id`를 가진다(`tests/verify/pass/structs.bmb`의 `geo::Point`·`arrs::Point`, 2D-19 정렬에서 발견).
- Rust는 두 타입을 섞지 않는다(명목). 물음(T1-28): 고유 `impl`이나 선언 위치를 텍스트에 넣어 정체성을 가를지, 구조가 같으면 같은 정체성으로 둘지. `id`로 짝짓는 도구(`expect`, `rename`의 확인, `weaken`의 짝짓기)가 이 경우를 다뤄야 한다.

## 결정

1. 구조 정체성을 유지한다. 필드(와 trait `impl`)가 같은 두 타입은 같은 `id`다. ADR-0059는 그대로다.
2. `id`를 읽는 도구는 정체성을 경로의 값으로 다루고, 정체성으로 정의를 찾지 않는다. 지금 그렇다:
   - `expect DEF ID`는 경로 DEF의 현재 정체성과 비교한다. 같은 정체성의 다른 경로가 바뀌어도 영향이 없다.
   - `rename`의 확인은 정체성을 다중 집합으로 비교한다(정렬한 목록). 같은 정체성이 둘이면 둘로 센다.
   - `weaken`은 경로로 먼저 짝짓고, 정체성으로 짝지은 두 정의는 텍스트가 같아 어느 쪽과 짝지어도 판정이 같다.
   - `query duplicates`가 같은 정체성의 정의 묶음을 보여 준다(정보).
3. 시험이 이 동작을 지킨다: `tests/workspace.rs`의 `equal_types_share_an_identity_and_the_tools_tell_them_apart`(같은 정체성, 하나를 이름 바꾸기, 하나를 바꾼 뒤 다른 하나의 `expect`는 통과·바뀐 경로의 낡은 `expect`는 거부).

## 근거

- **정체성은 뜻이다(ADR-0059 §1):** BMB에서 trait 없이 필드가 같은 두 타입의 값은 할 수 있는 일이 같다(필드 읽기·쓰기, 생성, 증명의 데이터형, 코드 생성의 배치). 두 타입을 섞는 프로그램은 검사기가 거부하므로(명목 검사), 정체성이 같아도 프로그램 하나 안에서 뜻이 섞이지 않는다. 고유 `impl` 함수는 각자 경로와 정체성을 가진 정의라 타입의 텍스트에 넣지 않아도 갈린다.
- **선언 위치를 넣으면** 같은 타입을 다른 단위로 옮기기만 해도 정체성이 바뀌어 ADR-0059의 목적(이름·위치는 메타데이터)에 어긋난다. 고유 `impl`을 넣으면 함수 하나를 더하는 편집이 타입과 그것을 쓰는 모든 정의의 정체성을 바꾼다(계약 방화벽과 같은 문제, ADR-0063 맥락).
- **이름 바꾸기 포획:** 두 같은 타입 사이에서 이름이 다른 쪽을 가리키게 되는 포획은 다중 집합 비교가 보지 못한다. 그러나 그 포획은 뜻을 바꾸지 않는다(값의 연산이 같고, 고유 `impl` 함수를 부르면 그 함수의 정체성이 달라 다중 집합이 바뀐다).

## 결과

- 코드 변경 없음. 시험 하나.
- 되돌리기: ADR-0059 §1을 바꿔 타입 텍스트에 고유 `impl`의 함수 정체성이나 선언 경로를 넣는다(승인 필요).

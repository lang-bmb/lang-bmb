# 판단 기준

> 채택: 2026-10-26(사람 지시, ADR-0045)
> 모든 권장안, 설계 결정, 태스크 도출과 우선순위, 구현 방식 선택, 검토는 이 문서로 판단한다. 권장안에는 적용한 기준 번호를 적는다.
> 관련: `docs/DESIGN.md`(정의·원칙), `dev-docs/AUTONOMY.md`(누가 결정하는가), `dev-docs/HEALTH.md`(지표).

## 1. 이 문서가 정하는 것

- **무엇이 최선인가**를 정한다. **누가 결정하는가**는 `AUTONOMY.md` §4가 정한다.
- 두 질문은 섞지 않는다. 승인이 필요하다는 사실은 덜 좋은 해를 권하는 이유가 되지 못한다. 최선의 해를 권하고, 필요한 승인은 따로 적는다.

## 2. 근본 원칙

1. **원인이 있는 층에서 고친다.** 문제는 원인이 있는 층(언어, 컴파일러, 도구, 프로세스, 자산, 외부)에 귀속시키고 그 층에서 해결한다(§3). 다른 층에서 증상을 흡수하지 않는다.
2. **정석을 택한다.** 숙련된 엔지니어가 시간 제약 없이 고를 확립된 방법을 택한다(§4 S1). 고유 해법은 선례가 없거나 선례가 BMB 정의와 충돌할 때만 쓰고, 그 이유를 적는다.
3. **비용은 기준이 아니다.** 작업량, 영향 범위, 기존 자산 보존은 해를 고르는 근거가 아니다(§5). 0.x 동안은 과감한 리팩터링을 언제나 허용한다(§6).
4. **규칙과 지표는 수단이다.** 규칙이 열등한 해를 강제하면 그 규칙을 재검토한다. 지표를 맞추려고 해를 바꾸지 않는다(§9).
5. **우회는 표시된 임시 조치일 때만 둔다.** 근본 해를 당장 할 수 없으면 우회에 근본 해의 백로그 ID와 해제 조건을 붙인다(§11). 표시 없는 우회는 결함이다.

## 3. 원인 귀속

| 관찰된 문제 | 귀속 층 | 조치 | 하지 않는 것 |
| --- | --- | --- | --- |
| 검사기·증명기·코드 생성이 옳은 프로그램을 거부하거나, 비싸게 증명하거나, 불필요한 런타임 검사를 남긴다 | 컴파일러 | 검사·인코딩·알고리즘을 고친다 | 프로그램·명세·코퍼스를 컴파일러에 맞춰 고치기. 거부 진단으로 언어 범위를 좁히기 |
| 정석 해법을 언어로 표현할 수 없다(맵을 만들 수 없다, 재귀 자료를 쓸 수 없다, `Vec`을 필드에 둘 수 없다) | 언어 | 표현식을 더하거나 바꾼다(ADR) | 단형 복제, 문맥 매개변수 펼치기, 아레나 강제 같은 우회를 영구 해법으로 두기 |
| 결정론적으로 계산할 수 있는 일을 에이전트가 한다(기계적 수정, 표기 채우기, 영향 계산) | 도구 | 도구가 하게 한다(DESIGN 원칙 6) | 프롬프트·관례·문서로 메우기 |
| 규칙·게이트·지표·태스크 절차 때문에 열등한 해를 택하게 된다 | 프로세스 | 규칙 개정을 제안한다(ADR) | 규칙에 맞춰 해를 비틀기 |
| 명세·코퍼스·벤치·측정 자산이 틀렸다 | 자산 | 고친다. 동결 자산은 재동결 절차와 판 번호로 고친다 | 기대 출력을 조용히 바꾸기 |
| 외부 도구(Z3·LLVM·libc)의 결함·한계 | 외부 | 재현 사례를 남기고, 대응은 컴파일러 안의 격리된 한 곳에 표시해 둔다 | 사용자 코드나 명세로 흡수하기 |
| 사용자 코드·명세 자체의 결함(예: 스스로 다시 맞는 트리거) | 사용자 | 컴파일러는 진단과 기계적 수정으로 알린다 | 컴파일러가 사용자의 선택을 몰래 바꾸기 |

- **옳은 프로그램의 기준:** Rust·Verus에서 정석인 코드와 명세다. BMB가 의도적으로 금지한 형태(§7, DESIGN §4.1 원장)는 예외다.
- 증상이 여러 층에 걸치면 가장 아래의 원인부터 고친다. 위층의 조치는 원인을 고친 뒤에도 필요할 때만 남긴다.

## 4. 해법 선택 기준

### 4.1 제약 (어기면 후보에서 뺀다)

| 번호 | 제약 | 내용 |
| --- | --- | --- |
| C1 | 건전성 | 증명 게이트를 약하게 하지 않는다. 증명되지 않은 사실을 가정하거나 최적화에 쓰지 않는다 |
| C2 | 결정론 | 같은 입력이면 같은 출력 바이트(진단, 맵, IR, 증명 판정) |
| C3 | 정직성 | 주장은 코드 경로와 측정으로만 쓴다. 벤치 문제·프롬프트 동결, 1회 성공률을 재시도 없이 보고(genesis §3.5) |
| C4 | 정의 | DESIGN §1·§3(에이전트가 쓰는 Rust 방언, 코드가 정본, 맵은 파생물, 모호성 0, 증명이 최적화 근거)를 지킨다. 정의를 바꾸는 것이 최선이면 정의 개정을 제안한다(승인) |

### 4.2 선호 (위에서부터 차례로 비교한다)

| 번호 | 기준 | 판단 질문 |
| --- | --- | --- |
| S1 | 정석성 | 확립된 방법인가? 출처 순서: (a) Rust 언어와 표준 라이브러리 (b) 검증 언어·도구(Verus, Dafny, F*, Why3, Lean) (c) 컴파일러 공학(rustc, LLVM, 표준 교재) (d) PL 이론 |
| S2 | 근본성·일반성 | 원인을 없애는가? 이 사례만이 아니라 같은 부류 전체를 푸는가? 특례 분기로 증상을 누르지 않는가? |
| S3 | 일관성·개념 경제 | 기존 개념과 합성되는가? 한 가지 일에 한 가지 방법인가? 내장과 사용자 정의가 같은 규칙을 따르는가? |
| S4 | 목표 함수 | ADR-0041의 극대화 항목: 안정성, 성능, AI 코딩 효율(총 토큰·탐색·쓰기, Rust 습관 오류율), 테스트 최저, 바이너리 크기, 재사용, 결정론·변경 안전성, 런타임 의존 최저 |
| S5 | 증거 | 측정, 선례, 증명 중 무엇이 뒷받침하는가? |

동률이면 더 일반적이고 더 단순한 쪽을 택한다.

## 5. 기준이 아닌 것

다음은 해를 고르는 근거로 쓰지 않는다. 권장안의 "영향" 칸에 정보로만 적는다.

- 작업량, 바뀌는 줄 수, 영향 범위, 일정
- 기존 코드·테스트·코퍼스·기대 출력의 보존. 이것들은 갱신 대상이다
- 채택된 ADR이나 현행 규칙과 같다는 것. 채택된 ADR도 새 ADR로 대체할 수 있다
- 승인 없이 할 수 있다는 것
- 지표 수치 자체. 지표는 증상 탐지기다
- 지금까지 그렇게 해 왔다는 것

**경고 신호:** 권장 근거에 "작업이 적다", "영향이 작다", "현 규칙상", "승인 없이", "지표가 나빠져서", "코퍼스를 바꾸면 통과한다"가 들어가면 §3으로 돌아가 원인 층을 다시 정한다.

## 6. 0.x 리팩터링 정책

- 안정성 정책(5B-01)이 채택되기 전까지 하위 호환 의무가 없다. 표면 문법, 내부 구조, 맵 스키마, 진단 문구, 정규형을 최선의 형태로 바꿀 수 있다.
- 바꿀 때는 같은 커밋에서 코퍼스, 기대 출력, 문서, 진단 표를 갱신하고 게이트를 통과한다. 기계적 이주가 가능하면 `bmb fix` 교체로 제공한다(DESIGN 원칙 6).
- 큰 리팩터링은 태스크로 쪼갠다. 쪼개기 위해 해를 줄이지 않는다. 태스크 크기 규칙(AUTONOMY §3.2)은 분해 규칙이지 해를 축소하는 규칙이 아니다.
- 유지되는 식별자 규칙: 진단 코드 번호와 ADR 번호는 재사용하지 않는다. 기존 진단 코드의 의미를 바꾸는 것은 승인을 받는다(AUTONOMY §4).

## 7. 언어 기능 판단

- **제한의 정당성:** 언어의 제한은 DESIGN §4.1 편의 포기 원장에 있고 그 "얻는 것"을 실제로 회수할 때만 정당하다. 그 밖의 제한(아직 구현하지 않음, 인코딩이 어려움, 컴파일러를 단순하게 두려는 것)은 결함으로 백로그에 올리고 고친다.
- **"검증되지 않는 기능은 넣지 않는다"의 해석:** 기능은 증명 인코딩과 함께 들어온다. 인코딩이 어렵다는 것은 기능을 빼는 이유가 아니라 인코딩을 만들 이유다. 원리적으로 증명 대상이 될 수 없는 것(외부 세계와의 경계)만 근거가 있는 탈출구로 둔다(ADR-0041의 "표현력 제한"은 이 뜻이다).
- **표면:** Rust의 정석 형태를 쓴다(DESIGN §4). 다른 형태는 원장 항목과 충돌할 때만 쓰고, 원장에 행을 더한다.
- **판단 질문:** (1) 정석 Rust 프로그램이 이 기능 없이 어떻게 바뀌는가? (2) 그 변형은 원장의 어떤 "얻는 것"을 사는가? 답이 없으면 기능을 넣는다.

## 8. 컴파일러 판단

- 옳은 프로그램의 거부(은퇴한 E0814 같은 "아직 받지 않음" 진단), 해법기 한도 초과, 증명된 프로그램에 남는 런타임 검사는 컴파일러 결함 목록이다. 줄이는 것이 목표다.
- 증명 비용 문제는 인코딩(보조 정리, 트리거, 분해, 펼침 전략)으로 푼다. 사용자에게 우회 명세나 우회 코드를 요구하지 않는다.
- 성능은 생성 코드와 증명 기반 최적화로 푼다(DESIGN 원칙 9).
- 사용자 명세 자체의 결함은 사용자 층이다(§3 마지막 행). 컴파일러는 진단으로 알리되 사용자의 트리거·명세를 몰래 바꾸지 않는다(C1·C4).

## 9. 프로세스·지표 판단

- 규칙이 열등한 해를 강제한다는 사실이 곧 개정 제안의 근거다. 개정은 ADR로 남긴다.
- 옳은 변경이 지표를 악화시키면 `health.py accept --reason`으로 받아들이고, 지표가 잘못 재고 있으면 지표를 고친다. 지표를 위해 코드·명세·코퍼스를 바꾸지 않는다.
- 측정 정직성 규칙(벤치 동결, 1회 성공률, 공정한 기준선)은 C3이라 유지한다. 측정 설계가 틀렸으면 새 판으로 다시 동결한다.

## 10. 권장안 형식

권장안(보고, ADR 근거, 태스크 도출)은 이 순서로 쓴다.

1. **문제:** 관찰과 재현
2. **원인과 귀속 층:** §3
3. **정석 해와 출처:** S1
4. **후보 비교:** 제약 C1~C4 통과 여부, 선호 S1~S5
5. **권장과 결정적 기준:** 어느 기준에서 갈렸는가
6. **영향(정보):** 바뀌는 범위, 리팩터링, 이주. 판단 근거가 아니다(§5)
7. **필요한 승인:** AUTONOMY §4
8. **우회가 불가피하면:** 임시 표시, 근본 해의 백로그 ID, 해제 조건

## 11. 우회 원장

- 지금 근본 해를 할 수 없어 둔 우회는 백로그에 "우회" 표시와 근본 해 ID를 함께 올린다. 코드에는 백로그 ID만 적는다(TODO 주석 금지, AUTONOMY §3.2).
- 페이즈 종료 감사는 그 페이즈가 남긴 우회 목록을 확인한다. 해제 조건이 충족된 우회는 근본 해 태스크를 다음 웨이브에 넣는다.

## 12. 기존 문서와의 관계

- DESIGN §2 트레이드오프 원장의 "표현력 제한"은 §7의 뜻으로 읽는다.
- AUTONOMY §1 "판단 기준은 문서에 있다"의 첫 문서가 이 문서다. §4 결정 권한은 그대로다.
- 운영 규칙(genesis §3.5)은 C1·C3에 들어 있다.
- 이 기준으로 기존 결정을 다시 볼 때는 §10 형식으로 권장안을 쓰고, 채택된 ADR을 바꾸는 것이면 새 ADR로 한다.

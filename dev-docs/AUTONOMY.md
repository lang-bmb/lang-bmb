# 자율 진행 계획

> 갱신: 2026-10-25
> 에이전트가 사람의 개입 없이 백로그를 소화하기 위한 규칙이다. 사람의 개입 지점은 §4의 표로 한정한다.
> 관련: `docs/ROADMAP.md`(단계·통과 기준), `dev-docs/BACKLOG.md`(태스크), `CLAUDE.md`(커밋 규칙).

## 1. 원칙

- **판단 기준은 문서에 있다.** 설계(`docs/DESIGN.md`), 결정(`dev-docs/adr/`), 통과 기준(`docs/ROADMAP.md`)이 판단의 근거다. 문서에 근거가 없는 큰 판단은 §4에 따라 사람에게 넘긴다.
- **완료는 기계가 확인한다.** 모든 태스크의 완료 기준은 명령이나 테스트로 확인할 수 있어야 한다. 그렇지 않으면 더 쪼갠다.
- **기준을 낮추지 않는다.** 막히면 통과 기준을 완화하지 않고 막힘으로 기록한다.
- **기록은 백로그와 ADR에만 남긴다.** 세션 로그·핸드오프 문서는 만들지 않는다. 다음 세션은 백로그만 읽고 이어 간다.

## 2. 작업 루프

한 사이클은 태스크 하나다.

1. **동기화.** 작업 브랜치를 원격과 맞춘다. `dev-docs/BACKLOG.md`의 "지금 할 일"과 🔄 상태를 읽는다.
2. **선택.** §3.1의 규칙으로 태스크 하나를 고른다. 상태를 🔄로 바꾼다.
3. **분해.** 완료 기준을 한 번의 커밋으로 충족할 수 없으면 하위 태스크(`1B-03a` 등)로 쪼개 백로그에 올리고, 첫 하위 태스크부터 한다.
4. **구현.**
5. **검증 게이트.** `scripts/check.sh`(INF-05)가 통과해야 한다. 통과 여부는 출력이 아니라 **종료 코드**로 판단한다(파이프로 잘라 보면 실패가 가려진다: 커밋 `8dcdb33`·`6947378`이 그렇게 게이트 실패 상태로 푸시되었다). 게이트는 지속 관리 지표의 래칫(`scripts/health.py`, ADR-0039)도 확인한다. 지표가 개선되면 같은 커밋에서 기준선을 갱신하고, 의도된 악화는 백로그 이유와 함께 `health.py accept --reason`으로만 반영한다(`dev-docs/HEALTH.md` §1).
6. **기록.** 상태를 ✅로 바꾸고 근거(커밋 해시, 테스트 이름)를 적는다. 작업 중 발견한 일은 §3.2에 따라 새 태스크로 올린다. "지금 할 일"을 갱신한다.
7. **커밋·푸시.** 코드와 백로그 갱신을 같은 커밋에 넣는다. 커밋 규칙은 `CLAUDE.md`를 따른다. 푸시는 `scripts/ship.sh`로 한다(커밋된 트리에서 게이트를 돌리고 종료 코드 0일 때만 푸시, INF-10).
8. **반영.** §5의 정책에 따라 main에 반영한다.

다음 사이클로 넘어가기 전에 §6의 보고 조건을 확인한다.

## 3. 태스크 선택과 도출

### 3.1 선택 규칙

의존이 모두 ✅인 ⏳ 태스크 중에서 아래 순서로 고른다.

1. 다른 태스크를 막고 있는 것(의존하는 태스크가 많은 것).
2. 현재 단계 통과 기준에 직접 연결된 것(BACKLOG의 "통과 기준 추적" 표).
3. ADR 태스크. 구현보다 결정을 먼저 한다.
4. 같은 조건이면 ID 순.

현재 단계의 태스크가 모두 막혔을 때만 다음 단계 태스크를 당겨 온다.

### 3.2 도출 규칙

새 태스크는 여섯 경로로만 생긴다. 모두 BACKLOG에 ID를 받아 올린다. 코드에 `TODO` 주석을 남기지 않고, 필요하면 백로그 ID만 적는다.

| 경로 | 언제 | 무엇을 |
| --- | --- | --- |
| 통과 기준 역산 | 단계 착수 시 | 통과 기준마다 그것을 확인하는 테스트·측정 태스크가 있는지 "통과 기준 추적" 표로 대조하고, 빈칸을 태스크로 만든다 |
| 설계 대조 | 단계 착수 시 | `docs/DESIGN.md`의 원칙·§8 회수 항목 중 이 단계 범위인 것을 태스크로 만든다 |
| 구현 중 발견 | 수시 | 버그, 한계, 보수적 근사, 빠진 진단을 발견 즉시 등록한다 |
| 측정 결과 | 측정 후 | 기준에 못 미친 지표마다 원인 조사 태스크를 만든다 |
| 단계 종료 감사 | 단계 종료 직전 | 통과 기준을 하나씩 실제로 확인하고, 미충족 항목을 태스크로 만든다. 모두 충족해야 단계를 닫는다 |
| 지속 관리 | 페이즈 종료·회귀 발생 시 | `health.py table` 스냅샷을 `dev-docs/health/<페이즈>.md`로 커밋하고 다섯 축(ADR-0039)을 점검한다. 실제 회귀를 어떤 지표도 잡지 못했으면 지표·시험 태스크를 만든다(HEALTH.md §7). 언어 페이즈는 실용성 규칙(HEALTH.md §5)을 통과 기준에 더한다 |

**태스크 작성 조건:** 완료 기준이 명령·테스트로 확인 가능하고, 한두 커밋 크기이며, 의존이 명시되어 있어야 한다.

## 4. 결정 권한

| 구분 | 에이전트가 자율로 | 사람의 승인 필요 |
| --- | --- | --- |
| 구현 | 내부 구조, 알고리즘, 리팩터링, 버그 수정, 테스트·코퍼스 추가 | — |
| 진단 | 새 진단 코드 추가(번호 규칙 준수) | 기존 코드의 의미 변경·재사용 |
| 의존성 | 표준 라이브러리만 쓰는 구현 | 외부 크레이트 추가(결정론·공급망 영향) |
| 결정 기록 | 기존 ADR과 DESIGN.md 범위 안의 구현 수준 결정을 ADR로 작성·채택(예: 정수 인코딩, 포매터 규칙, 맵 스키마). "자율 채택"으로 표시하고 §6에 따라 보고 | DESIGN.md의 정의·원칙·비목표 변경, 채택된 ADR 대체, 언어 범위(ADR-0016) 확대·축소 |
| 계획 | 태스크 분해·순서·추가, 막힘 기록 | 단계 추가·삭제, 통과 기준 변경 |
| git | 작업 브랜치 커밋·푸시, main fast-forward(§5) | force push, 브랜치·태그 삭제, 히스토리 재작성 |
| 외부 | — | 공개 행위(릴리스, 이슈·PR 공개 코멘트), 유료 API 사용(1E 에이전트 측정 실행 등), 라이선스 |

판단이 애매하면 승인 필요 쪽으로 분류한다.

## 5. 브랜치와 반영

- 작업은 세션의 작업 브랜치에서 한다.
- 검증 게이트를 통과하고 CI(INF-01)가 초록이면, main이 작업 브랜치의 조상인 경우에 한해 main을 fast-forward한다.
- fast-forward가 불가능하면(main이 앞서 있으면) main을 작업 브랜치에 병합하고 게이트를 다시 통과시킨 뒤 반영한다.
- CI가 생기기 전에는 로컬 게이트 통과를 조건으로 한다.

## 6. 보고와 중단

다음 경우에만 사람에게 보고한다. 그 외에는 다음 사이클로 계속 진행한다.

| 조건 | 행동 |
| --- | --- |
| §4의 승인 필요 항목에 닿음 | 그 태스크를 🚫(사유: 승인 대기)로 두고 질문 하나로 보고. 다른 태스크로 계속 진행 |
| ADR을 자율 채택함 | 한 줄 보고(결정과 되돌리는 방법). 진행은 멈추지 않음 |
| 같은 태스크에서 접근을 바꿔 3번 실패 | 🚫로 두고 시도 내역을 백로그에 요약한 뒤 보고 |
| 환경 문제(도구 부재, 권한 거부) | 우회할 수 있으면 우회하고 기록, 아니면 🚫와 필요 조치를 보고 |
| 단계 통과 기준을 모두 충족 | 단계 종료 감사 결과를 보고. 다음 단계 착수는 승인 후 |
| 진행 가능한 태스크가 없음 | 막힌 태스크 목록과 각 해제 조건을 보고 |

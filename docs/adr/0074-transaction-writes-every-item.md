# ADR-0074: The `put`·`remove` of a transaction write every item of a unit by address (types, `impl` functions, traits, trait impls)

- Status: Accepted (approved by the maintainer 2026-11-01 "recommendation accepted, approval items approved"). Drafting approved 2026-10-31, the §10 recommendation of backlog T0-23. The implementation is T0-23
- Date: 2026-10-31
- Related: DESIGN.md §6 (writing is a transaction), ADR-0009 (transactions), ADR-0011 (layout is the tool's), ADR-0021 (freeze), ADR-0026 §3·§6 (one `impl` block per type, normal form), ADR-0046 §2 (coherence of trait impls and units), ADR-0059 §1·§5 (identity, `rename`·`expect`), ADR-0060 (type invariants), ADR-0070 (same condition), ADR-0073 (edit surfaces), backlog T0-20·T0-23·T0-09·T0-21·T1-20, JUDGMENT §10

## Context

- Transactions write only functions. `Op::Put` (`compiler/src/workspace.rs`) wraps `code` in a `mod`, parses it, and puts only `m.fns` into the unit; if there are other items, `non_fn_items` names them and rejects the whole transaction (T0-20 (1)). `Op::Remove` also looks only in `m.fns`. Functions are `fn`·`spec fn`·`proof fn` (all `FnDef`).
- So the agent cannot add a type or fix fields, variants or `#[invariant(p)]` (ADR-0060), and cannot write `impl` methods, traits or trait impls. A unit with data types cannot be built with MCP alone. T0-09 (`bench/brb-encap`) lays the seed down as files, and takes the new operation as a function of the unit, not a method ("it cannot write types or `impl` blocks, so a new operation is a function of the unit" in `prompt-bmb.md`). The Rust arm uses `impl` methods.
- Other operations of the same transaction already handle these items by address. `rename` accepts `unit::f`·`unit::T::f`·`unit::T`·`unit::Trait` (`Fn`·`ImplFn`·`Type`·`Trait` of `TargetKind`; trait methods are rejected). `expect` accepts every key of `identities` (`Def`·`Type`·`Trait` of `identity::Key`). `Def` includes the `impl` function `unit::T::f`, the trait default body `unit::Trait::m`, and the trait impl function `<unit::T as unit::Trait>::f` (`check::TraitImplInfo::fn_path`). The map and the status lines of `verify` use the same paths.
- The language and compiler already check and prove these items (ADR-0026·0046·0060). The `edit_file`·`edit_ast` of the edit surfaces (ADR-0073) also replace whole files, so they can write types, `impl`s and traits. Only the definition-level surface stayed at functions.

## Decision

### 1. Items and addresses

Five kinds of unit items are written and removed by address. The address is the path the map, `expect` and `rename` already use. Inside a unit, types, traits, functions and sub-units are one namespace (checker E0302), so one path is one item.

| Item | Address | `put` | `remove` |
| --- | --- | --- | --- |
| Function (`fn`·`spec fn`·`proof fn`) | `unit::f` | Replaces or adds the function of the same name (the current rule) | That function |
| Type (`struct`·`enum`, with attributes) | `unit::T` | Replaces or adds the whole type declaration of the same name (fields, variants, type parameters, attributes). Does not touch the `impl` block | The type and its inherent `impl` block (`unit::T::*`) |
| Inherent `impl` function | `unit::T::f` | Each function of `impl T { fn f .. }` is merged into T's `impl` block (2 below) | That function. The block too if it is the block's last function |
| Trait (method signatures, contracts, default bodies) | `unit::Trait` | Replaces or adds the whole trait declaration of the same name | The trait and its default bodies (`unit::Trait::*`) |
| Trait impl | `<unit::T as unit::Trait>` | Replaces or adds the whole impl block of the same (trait, type) pair | That impl block |

- The address of a trait impl is the front part of its function paths (what `TraitImplInfo::fn_path` writes before `::f`). At merge time it is before checking, so the same rule is computed syntactically. If the trait path is one segment and the target unit has a trait of that name, it is `unit::Trait`; otherwise it is as written (full path, the built-ins `Ord`·`Eq`·`Copy`) (the same rule as `identity::Ids::trait_path`). For the type, a name the target unit declares is written as a full path (the same rule as `qualify` of `fmt::type_hashes`). Type parameters are the names as written. So impls that differ only in parameter names get different addresses, both remain, and the checker rejects them as overlapping (E0311).
- The checker enforces the placement rules of items. `impl T` only in T's unit, one per type (E0308). A trait impl only in the unit of the trait or the type (E0312), one per pair (E0311). To move a trait impl of another unit, `remove` and `put` in the same transaction.

### 2. Merge rule of `put`

- The items of `code` are applied one by one in source order. If the same address appears twice, the later one remains (the same as the current function rule: the same meaning as writing two `put`s in a row).
- Functions, types, traits and trait impls **replace the item at the same address as a whole**. The reason trait impls are not merged per function: an impl is one item that must have every method of the trait (E0315), and in identity too it goes into the text of the trait and the type together (the header "Nominal types and traits" of `identity.rs`).
- An inherent `impl` is not an item but a namespace (ADR-0026 §3: the path is `unit::T::f`). So `impl T { fn f .. }` is merged **per function**. If T's block has `f` it is replaced, otherwise added. The other functions of the block stay. If there is no block it is created. The block head (type parameters and bounds) becomes the head of the `put`. If another function fails the check under the changed head, it is rejected with that function's diagnostic (the same way as a method breaking when the type declaration is changed).
- A same name of a different kind (`struct foo` in a unit that has the function `foo`) is added, not replaced. The checker rejects it with E0302. An item of a different kind is not silently deleted.
- The commit rule is unchanged (ADR-0009). If the program after application has even one structure or type error, the whole is rejected and nothing is written. Proof is not a requirement. Storage is the normal form (ADR-0026 §6: the `impl` block after its type, the functions inside an `impl` in name order), so the order inside `code` does not remain in the result.

### 3. What `remove` accepts

- The five address forms of the table in 1. Removing address P takes the item at P and the items whose path starts with P (for `unit::T`, `unit::T::*`). A trait impl `<unit::T as ..>` does not start with `unit::T`, so it remains. If a remaining impl refers to a type or trait that no longer exists, the checker rejects it (E0305). To remove it, remove that address too in the same transaction.
- Not accepted: the trait method `unit::Trait::m` and the trait impl function `<..>::f` (part of a trait or impl. `put` the whole fixed item. The same as `rename` not accepting trait methods), and unit paths (`remove_unit`). They are rejected with a problem string that says what to use instead.
- The `remove` array of `write` accepts the same addresses.

### 4. What stays rejected

- **`use`.** It is outside the language (E0214). `put` has no separate rejection; it is put into the unit together with the items so that the checker rejects it with the same E0214 as in a file. The same rule and the same diagnostic as the edit surfaces (`plan_files`). Otherwise the T0-20 rejection of `non_fn_items` goes away.
- **Sub-units (`mod`).** Units are made by the `unit` operation. Rejected as now ("create units with a `unit` op").
- An empty `impl T { }` (an inherent block with no functions) has nothing to write, so it is rejected in the same form as "`code` contains no definition".

### 5. Commit line and invariant changes

- `changed`·`removed` compare the rows of `fmt::qualified_hashes`. The rows now are definitions (`check::defs_of`: functions, `impl` functions, trait impl functions, trait default bodies) and type declarations (`type_hashes`, with attributes: `type_def_as` prints the attribute lines first). To these are added the rows of the trait declaration `unit::Trait` and the trait impl head `<unit::T as unit::Trait>`. Only then does every item `put` writes appear in the commit line. The tasks, seeds and solutions of the frozen sets have no traits or trait impls (0 hits of grep for `trait`·`impl .. for` in `.bmb`·`.json`·`.py` under `bench/`, 2026-10-31). So the new rows are seen only when a session writes a trait on its own.
- **Invariant changes.** Adding or removing a type's `#[invariant(p)]`, or changing it to another predicate, changes the text of the type declaration, and `unit::T` appears in `changed`. Changing only the body of the predicate `p` shows only `p` in `changed`, but the `id` of the type changes (ADR-0060 §1: the attribute writes the predicate by `id`). This shows in `expect unit::T` (rejected with the old `id`) and in the `id` of map L1. The transitive effect is answered by `impact`, as now. Changing a trait impl also changes the `id` of that trait and type (the identity text contains the impl). "Invariant change = the type `id` differs from the seed" of the H-ENCAP verdict (`bench/brb-encap/README.md`) is the same as this definition.

### 6. Protecting the frozen sets: the behaviour for everyone, the new descriptions behind a flag

- **Behaviour.** The `put`·`remove` above are the same on every server and the CLI (`bmb apply`). There is no `put` whose meaning splits by flag. The responses to inputs that succeed now are unchanged (a `put` containing only functions, a `remove` of a function address). The response changes only for inputs rejected today: a `put` containing items other than functions (the T0-20 rejection → commit) and a `remove` of a new address form ("no definition" → deletion). In the sweep of T0-20, the reference, weak and gaming solutions of the frozen sets sent no such `put` (1,136 `code`s, 59 BRB modules, 0 hits). At implementation the same sweep is done for the new `remove` addresses.
- **Descriptions.** The bytes of `tools/list` are the same as now without the flag. Only with the new flag `--item-docs` do the descriptions of `tx_put`·`tx_remove`·`write` (both forms of `--tool-docs`) state the five items and addresses. A frozen edition starts the server with the `mcp_flags` of its own `set.json` (no flags if absent), so the description bytes stay. A new edition writes `--item-docs` in `mcp_flags`. The `instructions` of `initialize` do not mention functions, so they are not changed. Draft wording: `tx_put` "In a transaction: add or replace items in UNIT. A function, type (with its attributes), trait or trait impl replaces the one at the same path; the functions of an `impl T { .. }` block are added to or replace those of T's `impl` block.", `tx_remove` "In a transaction: remove the item at PATH: `unit::f`, `unit::T` (with its `impl` block), `unit::T::f`, `unit::Trait` or `<unit::T as unit::Trait>`." It is finalized at implementation and pinned by a test.
- **Protection by test.** For each flag combination the frozen editions use (none, `--write-tool`, `--write-tool --tool-docs`, `--file-tools`, `--ast-tools`), a test is added that pins the SHA-256 of the `tools/list` result, measured at the commit before the implementation. Now the `write`·`--tool-docs` tests look only at tool names and part of the wording (`tests/mcp.rs`).
- **Prompts of the frozen editions.** The prompts of m1·m1b·BVB·BRB and the write editions say only that `tx_put`·`write` accept "definitions", so they do not become false. Only `bench/brb-encap/prompt-bmb.md` says "it cannot write types or `impl` blocks". So T0-21 runs on the compiler tree before this implementation (ADR-0070 decision 1 (a). With `--same-as` if it goes into `run_models.py`).
- **Switching the default** (the new descriptions without a flag) is outside this ADR. When the plan no longer uses the editions frozen with the old descriptions, it is submitted as an approval item.

### 7. Tests

- `tests/workspace.rs`: `put` of `impl` functions (add, replace, other functions of the block preserved, block creation, head replacement and the diagnostic of the function it breaks), `put` of types (field change and the diagnostic of methods, adding or replacing `#[invariant(p)]` → the type in `changed`, replacing the predicate body → type `id` change and rejection of an `expect` of the old `id`), `put` of traits and trait impls (replacement per pair, missing method E0315, moving to another unit together with `remove`, impls differing only in parameter names are E0311), a `put` mixing the five kinds in one `code` (all committed, `changed` lists them all), the five addresses of `remove` and the cascade (`unit::T` → `unit::T::*`), rejection of a remaining trait impl (E0305), the wording for addresses not accepted (`unit::Trait::m`, `<..>::f`, units), E0214 for `use`, rejection of sub-units. The current `put_rejects_items_it_cannot_write` is replaced by these.
- Round trip: for each program of the corpus, the result of writing into an empty workspace with `unit` and a `put` per item is the same bytes as the normal-form files of `bmb import` (the test that a unit with data types can be built with MCP alone). That the syntactic computation of the trait impl address equals the front part of the checker's `fn_path` is also checked with this corpus.
- `tests/mcp.rs`: the byte-pinning test of 6, the new descriptions of `--item-docs`, writing and proving a type and methods with `tx_put`·`write`. `tests/mcp_fuzz.rs`: add type, `impl`, trait and trait impl items and the new `remove` addresses to the code generator, and keep the model as it is (only a commit changes the workspace, and after a commit the check passes and the form is normal).

### 8. Lifting the T0-09 workaround: a new edition of `brb-encap`

- After acceptance and implementation, `bench/brb-encap-b` is made and frozen before the first run (ADR-0021 §1). The new operation of the BMB arm is an `impl` method of the type, like the Rust arm (`Set::replace(&mut s, ..)`). The sentence "cannot write types or `impl` blocks" is removed from the prompt, and `--item-docs` goes into `mcp_flags`. The hidden judging unit calls the method. The reference, weak and gaming solutions are also rewritten as methods. The four gate jobs (`oracle`·`weak`·`adequacy`·`tests`) run by the same criteria. The refutation condition is that of `brb-encap`, registered again before the run.
- The frozen edition `brb-encap` stays and T0-21 measures it. The results of the two editions are not mixed (ADR-0021 §1).

## Rationale

- **Cause and layer (JUDGMENT §3):** the tool surface blocks writes that can be done deterministically. The layer is the tool. The language and compiler already check and prove these items, and only the write surface stayed at the M1 subset.
- **Canonical way (S1):** definition-level editing (ADR-0009) writes and removes every item of a unit by address. In Rust a module is a sequence of items (`fn`·`struct`·`enum`·`impl`·`trait`·`use`) (Rust Reference "Items"). Structural editing tools (item-level edits of rust-analyzer) also treat the item as the unit. Calling a trait impl `<T as Trait>` is Rust's qualified path notation.
- **Candidates (the §10 recommendation of T0-23):** (A) `put`·`remove` accept every item. (B) A new operation per item kind (`put_type`, `put_impl`, ..). Two ways for one thing and more tools (S3·S4). (C) Status quo; types and `impl`s are written with the edit surfaces (ADR-0073). Those surfaces are measurement variants and off by default. It absorbs a defect of the transaction surface in another surface (§2.1). All three pass C1~C4. A is chosen. The decisive criteria are S3 (`put`·`remove` use the addresses that `rename`·`expect`·identity of the same transaction use) and S2 (all item kinds under one rule).
- **Inherent `impl` per function, trait impl as a whole:** the former is a namespace, so each function is its own definition (path `unit::T::f`, `Def` of identity). The latter is one item that implements one trait (E0315, the impl text of identity). These are two cases of the one rule that only what has an address is replaced (S3).
- **Alternatives for frozen-set protection:** (i) The behaviour for everyone, the new descriptions behind a flag and in new editions (this decision). (ii) The flag splits the behaviour too. When a frozen edition runs on the new tree the responses to all inputs are the same, but the same operation gets two meanings (S3) and the defect remains on the default server (§2.1). The frozen editions also gain nothing. Their tasks write only functions. A comparison within a tree (original edition vs variant edition) is fair because both sides see the same behaviour (ADR-0070: when the compiler tree changes it is a new condition anyway). (iii) Freeze every edition again with the new descriptions. It changes the condition of tasks that do not write types (the description bytes that go into every request. That is the fixed context T0-17 measures) and breaks the baselines of comparisons in progress and waiting (the original editions of T0-10·T0-11, original vs variant of T0-13·T0-15·T0-17·T1-41). Nothing is gained (C3). The decisive criteria are C3 (the frozen condition is the bytes the model sees) and S3. Choosing the description form by flag is the same existing mechanism as `--write-tool`·`--tool-docs`·`--file-tools`·`--ast-tools` (S3).
- **Why `use` is left to the checker:** a rejection wording of `put` alone would make the same rule appear in two places with two wordings. It is kept as the one E0214, the same as the file and edit surfaces (S3).

## Consequences

- Places that change (information): `Op::Put`·`Op::Remove` of `workspace.rs` (`non_fn_items` deleted), `fmt::qualified_hashes` (trait and trait impl rows), `FLAGS` and `tools` of `mcp.rs` (`--item-docs`), the `apply` and MCP lines of `compiler/README.md`, the tests of 6·7. DESIGN.md does not change (only the items accepted by the operations of §6 "writing is a transaction" widen).
- Measurement: the description bytes of the frozen editions and the responses to inputs that succeed now are unchanged. Only inputs rejected today are committed. T0-21 runs on the tree before the implementation (6).
- Open: `rename`·`expect` over MCP (T1-20) are separate. If opened in the same new edition, the description bytes change once. `rename` of trait methods is not widened here either.
- To do after acceptance: implementation of T0-23 (1~7), building and freezing `brb-encap-b` (8, a new task).
- Revert: `Op::Put` rejects items other than functions again, `Op::Remove` looks only at `m.fns`, and `--item-docs` is removed. The descriptions without the flag are the same bytes regardless of this decision.

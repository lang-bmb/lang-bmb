# ADR-0157: Byte round trips in the proof encoder

- Status: Accepted (autonomous)
- Date: 2026-11-26
- Related: ADR-0048 (integer types and bit operations), ADR-0090 (spec values outside their type), ADR-0017 §3 (facts are theorems of the definitions), DESIGN.md §6

## Context

- `x.to_be_bytes()` and `x.to_le_bytes()` are encoded as an array of byte terms, byte `k` being `(mod (div x 2^s) 256)`, and `T::from_be_bytes(b)` and `T::from_le_bytes(b)` as the sum of the images `(mod b[k] 256)` at their places, read as a value of `T` (`verify::byte_term`, `verify::from_bytes_term`). Both are exact, for operands outside the type too.
- The solver does not connect the two. `u64::from_le_bytes(x.to_le_bytes()) == x` was undecided at the resource limit (E0811, rlimit 5,000,000), and so was every form of it: through a local, a field, an element-wise copy, a `Vec`. Z3 introduces a quotient and a remainder for each `div` and `mod` and does not find that the remainders of the successive quotients add up to `x`. For a `u32`, `from_be_bytes(x.to_be_bytes())` proved at 8,634, `i16::from_le_bytes(b).to_le_bytes()` at 105,827.
- Reading a byte string as words is what a hash, a cipher or a serializer does. A package porting SipHash absorbs 8 message bytes as one little-endian word; with the gap it could state the word only as a sum of products and had to fall back to absorbing byte by byte.

## Decision

1. **A byte is its own image without `mod`.** `from_bytes_term` writes the image of each element `b` in `u8` as `(ite (and (<= 0 b) (<= b 255)) b (mod b 256))` (`verify::byte_image`): the same value for every integer, and for an element the solver knows to be a byte no `mod` is reasoned about. A word that a specification reads from a byte slice (`u64::from_le_bytes([m[i], .., m[i + 7]])`) is then as cheap as the sum of the products.
2. **A direct composition is rewritten (specifications and code).** `from_*_bytes` of an array that is literally `y.to_*_bytes()` in the same order and width is the image of `y` in the target type (`wrap_int`), and, in a specification, `to_*_bytes` of a value that is literally `from_bytes_term` of the elements of an array `e` in the same order and width is the array of the images of `e[k]` (`verify::bytes_val`, `verify::from_bytes_val`). The match is on text: the candidate operand is found from the length of the text and checked by writing it again (`verify::unapply`), so a match is exactly the composition. Locals, fields and `let`s of a specification are substituted values, so these forms are direct compositions.
3. **Code assumes two facts.** With `x.to_*_bytes()`: for `x` in its type's range, the bytes read back in the same order are `x` (`verify::bytes_fact`). With `T::from_*_bytes(b)`, unless `b` is the bytes of a value (2): when the elements of `b` are values of `u8`, the result equals their sum at their places (less `2^w` from `2^(w-1)` on for a signed type), and its bytes in the same order are `b` (`verify::from_bytes_fact`). The value is written without `mod` and `ite` (`verify::bytes_value`): with the images, bytes stored into a slice at a variable offset and read back stayed undecided for a 64-bit value.
4. The port does the same (`selfhost/encode_terms.bmb`, `encode_exec.bmb`, `encode_spec.bmb`), byte-identical.

## Rationale

- Each fact is true in every model, guarded by the ranges it needs, so the queries stay sound in the sense of ADR-0017 §3, the pattern of the facts of bit operations. The rewrites of (1) and (2) replace a term by one that has the same value for every integer operand, out of range too (ADR-0090). `byte_round_trips_are_rusts` in `tests/lemmas.rs` evaluates the facts and the rewritten terms at every 8-bit value and at the edge and pseudo-random values of the wider types against Rust's methods, for both orders, every integer type, operands outside the type, bytes outside `u8` and a target type of the other sign; `byte_terms_are_rusts_bytes` checks `from_bytes_term` with a byte outside `u8`.
- Code only gets facts, because a specification term may sit under a quantifier or in a definition, where an assumption would capture a bound variable; for a specification, the rewrites cover the direct forms, and an element-wise copy of a specification array of bytes is not covered.
- Cost, measured with `bmb verify` before and after: the fact of `to_*_bytes` is a few hundred units where a value's bytes are taken and not read back (`first_byte` of the failure corpus 705 → 1,108, `big_end` 784 → 1,146); `bytes_back` 8,634 → 1,230, `from_little` 105,827 → 4,947. The standard library and the port use no byte method, so their queries are the same bytes. In `tests/verify/pass/byte_round_trips.bmb` and a matrix of every integer type in both orders, the round trips prove at most at 2,893 directly or through a local or field, 4,355 for the bytes back in a specification, 61,110 for the bytes back in code and 67,400 through a slice at a variable offset, with the same verdict under five solver seeds.
- Alternative: only facts, no rewrite. Rejected: specifications would keep the gap. Alternative: only the rewrite. Rejected: an array copied or stored element by element is no longer the same text, and that is how real code moves bytes.
- Not decided: a word read in one function from bytes another function wrote, when the bytes are stated only in a specification (`m[i + k] == x.to_le_bytes()[k]` in a postcondition); the caller has no `to_*_bytes` in code to carry the fact.

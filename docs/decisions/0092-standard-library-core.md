# ADR-0092: Standard library core

- Status: Accepted (2026-11-06, 4B-01 completed by approval of the maintainer. The draft is 4B-03). As in review R12, it is written on top of generics (ADR-0046), owned types (ADR-0047) and strings (ADR-0050): the premise of monomorphic maps from the time of 4A-01 is withdrawn
- Date: 2026-11-05
- Related: ADR-0031 (`Vec`), ADR-0046, ADR-0047, ADR-0050, ADR-0091 (system interface), `dev-docs/measurements/selfhost-gap.md` §5.1, backlog 2U-07, ROADMAP "full sequence of the language" ④

## Confirmed during implementation (2026-11-08, 4B-02 (a))
- **Shipping:** one unit `mod NAME` per `lib/std/NAME.bmb`. `compiler/build.rs` builds the file list and puts the files into the compiler with `include_str!`, and adds the same files to the compiler identity (the incremental cache key `BMB_SOURCE_DIGEST`). There is no install location or path argument.
- **Adding (`compiler/src/stdlib.rs`):** the units the program refers to by a path `std::NAME::..` (calls, types, patterns, bounds, `#[uses]`, `refs::walk`) and the units those units refer to are added under the top-level unit `std`, after the program's units. The file name is `std/NAME.bmb` and in the source map it comes after the program files, so the positions of the program files keep the numbers of the caller's file list. Units that are not referred to are not added (the first edition of open question 1: they are neither checked nor proved). Added units are checked, proved and compiled like any other definition.
- **Name:** a top-level unit `std` in a program is E0309 (builtin name).
- **Moving `lib/` (4B-02 (d), the third item of the Consequences section):** the five files were moved to `lib/std/` (contents unchanged, unit names too). The callers (`tests/lib_run`, the two of `bench/game`, the two of `bench/lib`) are changed from `bytes::f` to `std::bytes::f` and do not pass the files. The output is the same. One name was made different from the table of §2: SHA-256 is `std::sha256`, not `std::hash`. Rust's `std::hash` is the `Hash`·`Hasher` traits (for hash tables), so the same name would have a different meaning, which goes against the principle of §2 (Rust's names and meanings). `base64`·`crc32`, which were not in the table, were kept under those names as `std::base64`·`std::crc32`.
- **`std::str` (4B-02 (b)):** `starts_with`·`ends_with`·`find`·`strip_prefix`·`strip_suffix`·`trim_ascii_start`·`trim_ascii_end`·`decode_utf8`. A slice cannot be returned (ADR-0015), so where Rust returns a slice a position is returned (`strip_prefix` gives the `i` of `&s[i..]`). The contracts are exactly the byte specification: `find` is `std::bytes::found` (the first position, and if none then nowhere; the earlier `std::bytes::find` said only that `Some` is a real position and said nothing about being the first or about the meaning of `None`, so it was made exact this time), `decode_utf8` is `std::utf8::seq_len` of Table 3-7 and the scalar value (the linear expression `is_code`), the others are byte predicates. The side that slices at a returned position has no run-time check (the bound facts and contracts of 2U-06). `trim` is kept under Rust's `trim_ascii_*` names, which do ASCII whitespace only, not Rust's Unicode whitespace (Unicode `trim` when the demand appears). `split_once` is not provided, because returning a position makes it the same as `find`. The result of `decode_utf8` is the struct `std::str::Decoded { ch, next }` (BMB has no tuples). Method syntax: if the name on a text receiver is not a builtin method and is a function of `std::str`, it is that function (`s.starts_with(p)` → `std::str::starts_with(s, p)`, a `String` is passed as `s.as_str()`: the adjustment `Adjust::AsStr`), also for a string literal receiver (`"a=b".find("=")`). The method name alone also adds `std::str` (`stdlib::METHOD_UNITS`). The hint for an unknown text method (E0404) lists the functions of `std::str` and says how to move Rust's `trim`·`contains`·`split_once` to the functions above. Tests: the run program `tests/run/std_str` (same output as the Rust translation `std_str_ref.rs`, valgrind), the differential test `std_str_agrees_with_rust_str` in `tests/stdlib.rs` (3,000 lines of random text, the fully proved BMB program `tests/data/std_str_diff.bmb`, extended with `BMB_SOUND_ITERS`). Proof cost: the most expensive definition `decode_utf8` has rlimit 460,423 (largest obligation 37,521, within 1/5 of the default limit 5,000,000).
- **`std::num` (4B-02 (c)):** the readers `parse_u64`·`parse_i64`·`parse_u64_hex` (`&str`, byte versions `*_bytes`) are exactly Rust's `from_str`·`from_str_radix(s, 16)`: one leading `+` (also `-` for the signed one), one or more digits, `None` on overflow, and `None` is exactly the remaining inputs (overflow is proved with `dec_grows`, "the value does not decrease as digits are added"). The writers `push_u64`·`push_i64`·`push_u64_hex` (lowercase) append to a `String` the same text as Rust's `Display`·`{:x}`. The contract is the normal form predicate `is_dec(t, a, n, x)`: the length is `width(x)` (19 constant thresholds, linear) and `t[k]` is the digit of `x` at place `n-1-k` from the end (`dig`, linear because it uses only constant division). The recursion is on the digit number, not on the bytes, so the fact that the earlier bytes are unchanged after an append is not needed separately (a recursive predicate over bytes had no name for the bytes before the append, so a frame lemma could not be used). The round trip is the lemmas `u64_round_trip`·`u64_hex_round_trip` (reading the written text gives `Some(x)`). While writing this unit, a `String` length defect of the verifier (backlog 1B-55) was found and fixed. Tests: the run program `tests/run/std_num` (same output as the Rust translation), the differential test `std_num_agrees_with_rust` in `tests/stdlib.rs` (3,000 lines of boundary values, signs, leading zeros and mixed bytes; the value read is written again so the round trip is compared too).
- **`std::slice` (4B-02 (e)):** `sort_by_key` of the table of §2 takes a closure that extracts the key, and BMB has no closures (ADR-0053 awaits approval). So `sort_indices<T: Ord>(keys: &[T]) -> Vec<usize>` was provided, which returns the stable sort order of the keys as a sequence of positions: `v[r[0]], v[r[1]], ..` is the result of Rust's `v.sort_by_key(..)` (equal keys in the order they came in). It does not move values, so it also works for a `Vec` of a move type. The contract `sorted_order` is the length, the range, and the stable order of every pair (`before`: the smaller key, and if equal the smaller position), and a stable order cannot contain the same position twice, so it is a permutation (the lemma `sorted_is_perm`). This form was chosen over multisets so the proof uses only linear facts and pair quantification (insertion sort; the loop invariant is "stable order except for the position being moved"). When closures arrive, `sort_by_key` is put on top of it. `binary_search<T: Copy + Ord>` has Rust's meaning (`Ok(i)` is any position of an equal value, `Err(i)` is the unique insertion point), and the premise is ascending order of every pair (`ascending`). `T: Ord` is only integers and `bool` for now (ADR-0046 open question 4). Tests: the run program `tests/run/std_slice` (order of equal keys, found and insertion point, same as the Rust translation), the differential test `std_slice_agrees_with_rust` in `tests/stdlib.rs` (1,500 lines of random keys with many repeats, compared with Rust's stable `sort_by_key` and `binary_search`). Proof cost: `sort_indices` 438,638 (largest obligation 41,437).
- **`std::collections` (4B-02 (f)):** as in the table of §2, `BTreeSet<K: Copy + Ord>` and `BTreeMap<K: Copy + Ord, V: Copy>` over a sorted `Vec` (a `Vec` of values alongside). The type invariant is that the keys are ascending in every pair (hence unique) and that the two `Vec`s have the same length. The position is the binary search `locate` (the key's place: smaller before, not smaller after). The contracts of insertion and removal have two layers: how the array changes (`inserted_at`·`removed_at`·`replaced`: inserted, removed or replaced at place `p`) and the meaning of the map (`maps`·`has_key`·`holds`: for `get`, `Some(v)` means the key corresponds to `v` and `None` means the key is absent), plus the size facts the caller uses cheaply (`len`, `map_grew` and so on). This is the "sequence of sorted pairs and a lookup predicate over it" of the table of §2 (the mathematical map of open question 2 not yet). The shifting is done in a `Vec` outside the set (taken out with `std::mem::replace`, shifted and put back): the type invariant must hold at every loop head, and in the middle of a shift a key is duplicated. Values are copied (`V: Copy`) because `get` cannot return a reference (ADR-0015), and keys being `Ord` is only integers and `bool` for now (`String` keys together with ADR-0046 open question 4). To write this unit, `Vec<T>` of a type parameter (backlog 2T-10) was opened. Tests: the run program `tests/run/std_collections` (counting occurrences, distinct values, same as the Rust translation, valgrind), the differential test `std_collections_agree_with_rust` in `tests/stdlib.rs` (2,000 random inserts, replacements, removals and lookups over a small key range, and the final contents, compared with Rust's `BTreeMap`·`BTreeSet`). Proof cost: the unit 2,366,602, largest obligation 73,787 (`BTreeMap::insert`).
- **Text keys (4B-04, 2026-11-08):** as in `K: Ord` of the table of §2, the key may be a move value: `BTreeSet<K: Ord>`·`BTreeMap<K: Ord, V: Copy>`, key `String` (the builtin `Ord` of the implementation confirmation of ADR-0046). Lookup takes a borrowed key as in Rust (`get(&k)`·`contains(&k)`·`contains_key(&k)`·`remove(&k)`). Keys that move cannot be shifted with `v[j] = v[j - 1]`, so the recursive functions `shift_in` (Rust's `Vec::insert`) and `shift_out` (`Vec::remove`, the removed one in `Some`) move them one at a time with `std::mem::replace`. It is recursion rather than a loop because a key already moved cannot be mentioned in a loop invariant (move checking treats a mention in a specification as a use too). `ensures` speaks of the values as they came in, so the contract of the recursion takes that place. The sorting lemmas are passed the element at that place (`&v[p]`) instead of the key. Taking out in order is the consuming `into_keys` (map, set) and `into_values` (map): `key_at`·`at`, which return the key at a place, only make sense when the key is `Copy`, but a second `impl` block with different bounds is forbidden by ADR-0026 (E0308) and there is no `where` clause (E0240). So `key_at`·`at` were removed. Values stay `Copy` (`get` returns a copy of the value). Values that move are kept in a `Vec` of their own and the map has positions as values (Rust's arena idiom). The two frictions (`impl` blocks with different bounds, speaking of moved values in specifications) are left as decisions for the maintainer (backlog 2T-11·2T-12). The proof cost went down: the unit 2,366,602 → 1,354,174, largest obligation 73,787 → 58,395 (`BTreeMap::insert`). Tests: the run program `tests/run/std_text_keys` (word count, `"B" < "a" < "ab" < "b" < "é"`, same as the Rust translation, valgrind), the differential test `std_collections_text_keys_agree_with_rust` (random operations on 20 keys with prefixes, case, 2 to 4 byte characters and empty text, compared with Rust). The code generation of `s.contains(&7)`, which passes a borrowed literal (stored in a temporary), was also fixed at this time.
- **`std::intern` (4B-02 (g), 2026-11-08):** the intern table of the table of §2. Like rustc's `Symbol` table it is a map from text to numbers (`BTreeMap<String, usize>`) and the names in number order (`Vec<String>`), and the type invariant is that for every pair of the map the name of that number is that key (`consistent`). `intern(&mut self, s: &str) -> usize` (the next number if new; the contract is that the number refers to `s`), `get` (if absent, no key is `s`), `name_is`, `push_name(i, &mut out)` because a name cannot be lent out (ADR-0015) (rustc's `as_str`), `len`, `into_names`. Preservation of the invariant is the one generic lemma `insert_keeps<K: Ord>`: over a sort, key equality is SMT's `=`, so it is proved at 33,270, and it is called at the `String` instance (equality of text is a quantified formula over the bytes within the length, so using it on `String` directly left the array theory undecided). While writing this unit, an encoder defect was fixed in which the parameter facts of a `proof fn` (E0819) used the outer length as an array of inner lengths for a `Vec<String>` field (E0812, a query with a wrong sort). Tests: the run program `tests/run/std_intern` (same as the Rust translation, valgrind), the differential test `std_intern_agrees_with_rust`. Proof cost: the unit about 440 thousand, largest obligation 67,419 (`intern`).
- **`std::json` (4B-02 (h), merged with T4-05, 2026-11-08):** JSON reading and writing of the table of §2. Instead of a tree of values it is an array of nodes (simdjson's tape): `Node { kind, start, end, next }` (7 kinds, the byte range in the text, the node after this node and everything it contains), and the elements of an array and the keys and values of an object (a key is a string node before its value) follow in order. A reference cannot be returned (ADR-0015), so `Doc` does not hold the text and the reading functions take the text (premise `of_text`: the same length). The type invariant `nodes_in` (every node is within the text, `next` goes forward) proves all the bounds on the reading side. `parse` is one state machine and open arrays and objects are a stack (`Vec<usize>`), so the nesting depth is not the machine's stack (the 100 thousand deep array of JSONTestSuite). Strings follow RFC 8259 §7 (no byte below 32, the eight escapes and the four digits of `\\u`, the rest is UTF-8 by `std::utf8::width`), numbers follow §6. Reading: `count`·`kind`·`start`·`end`·`next`·`element`·`member` (the key is compared as the bytes between the quotes, as they are, `raw_is`)·`i64_value` (`std::num::parse_i64_bytes`)·`string_value` (escape decoding; an unpaired surrogate is rejected as in `serde_json`). The writer `push_string` follows the rules of `serde_json` (`"`·`\\`·`\\b`·`\\f`·`\\n`·`\\r`·`\\t`, other control bytes as lowercase `\\u00xx`) and its contract is the range of the length. Number writing is `push_u64`·`push_i64` of `std::num`. The correctness of the verdict is the job of tests, not of proof (the "fully proved" of §3 is all obligations: bounds, overflow, termination): of JSONTestSuite (pinned commit `1ef36fa`, `scripts/json_suite.py`, downloaded and not put in the repository), the 95 `y_` have the same tokens as Python `json`, the 188 `n_` are all rejected, and of the 35 `i_`, 21 are accepted and 14 rejected (`dev-docs/measurements/json-suite/`). The differential test `std_json_agrees_with_rust`: random values made by Rust are written with random escapes and whitespace and the tokens are compared (200 by default, 2,000 also agree). The state of `parse` (the nodes are within the front part of the text, the open ones are nodes) is the single predicate `tape`, and `parse` does not unfold it: adding a node, opening, closing and weakening are done by helper functions with contracts (`add`·`open_at`·`close`·`later`), so `parse`, which failed at seed 1 in the first edition, stands at 269,607 ~ 270,107 (the 4B closing audit). Proof cost: the unit 3,530,126, largest obligation 485,775 (`push_string`).
- **Tools:** the normal form (`bmb fmt`·`import`), the workspace files and the `changed` of a commit contain only program units. A transaction operation on a `std` path is rejected (`std` is the standard library). `fix`·`uses`·lints·`mutate` look only at program files and definitions. Map L0·L1 rows have `"library":"std"` (a key present only when it applies, ADR-0020 §1). Tests `compiler/tests/stdlib.rs`, the run program `tests/run/std_str`, the check corpus `tests/check/err/std_unit`.

## Context

- The existing library is the five in `lib/` (`bytes`·`utf8`·`sha256`·`base64`·`crc32`), and the program that uses them passes them along as files. All are fully proved and pass the official vectors (T4-01~04).
- The library needed for porting the compiler (4D) is in §5.1 of the gap analysis: byte buffers, integer formatting and parsing (decimal, hexadecimal), sorted maps and sets with byte string keys (147 places of `BTreeMap` and 82 of `BTreeSet` in stage0), stable sorting by key (26 places of `sort*`), SHA-256, JSON writing and reading, UTF-8, an intern table. The run programs of 2U-05 had no string operations (`starts_with`·`find`·`split`·`trim`·`parse`, character iteration) and were written with bytes and `while` (2U-07).

## Decision

1. **A source library written and proved in BMB.** The standard library is not functions built into the compiler but BMB source (`lib/std/`). The proof gate checks it exactly like other code, and there are 0 escape hatches (the system builtins of ADR-0091 are not the library). The compiler adds it to the program automatically (`std::` paths resolve to these units). The current way of passing files goes away.
2. **Scope (first edition).** Starting with what self-hosting needs, with Rust's names and meanings:

   | Unit | Contents | Contract style |
   | --- | --- | --- |
   | `std::str` | `starts_with`·`ends_with`·`find`·`split_once`·`trim`·`strip_prefix`, character iteration `decode_utf8(s, i) -> Option<(char, usize)>` (ADR-0050 open question 2) | the result is exactly the byte specification (the `eq_result`·`found` form of `lib/bytes.bmb`) |
   | `std::num` | decimal and hexadecimal `parse` and formatting of `u64`·`i64` (a generalization of `push_u64` and so on) | round trip (`parse(format(x)) == Some(x)`) and normal form |
   | `std::collections` | `BTreeMap<K: Ord, V>`·`BTreeSet<K: Ord>`: `insert`·`get`·`remove`·`contains`·taking out in order | the specification is a sequence of sorted pairs (keys unique, ascending) and a `lookup` predicate over it. The implementation is a sorted `Vec` (first edition, binary search), and a balanced tree if measurement requires it |
   | `std::slice` | stable sort `sort_by_key` (insertion → merge), binary search | the result is a permutation of the input and sorted, the order of equal keys is preserved |
   | `std::json` | a value type, writing (escapes), reading (JSONTestSuite `y_`·`n_`, the same work as T4-05) | what is written conforms to the grammar and round trips |
   | `std::hash` | `lib/sha256.bmb` moved | the FIPS 180-4 specification (as now) |
   | `std::intern` | a name → handle table | the same name has the same handle, different names have different handles |

3. **Proof cost budget.** For every library definition the `rlimit` of the most expensive obligation is at most 1/5 of the default limit (the same margin as V5), and the whole unit has 0 unstable under `stability --seeds 8`. A definition that exceeds this is split with lemmas (`proof fn`) or its implementation is changed, without weakening the contract. The cost on the using side reads only the contracts (the contract firewall), so it is not tied to the library bodies.
4. **Freezing and changing.** The public contracts of the library change by the same rule as the corpus: when one is weakened, the alignment of `bmb weaken` proves the users again (2D-19). A frozen measurement edition (ADR-0021) freezes the library of that time with it.

## Rationale (alternatives considered)

| Option | Verdict |
| --- | --- |
| **BMB source + proof (adopted)** | The demonstration of the mission (proved code replaces tests) starts in the library. The self-hosting compiler uses the same library |
| Built into the compiler (like the current `Vec` methods) | Fast, but the unproved TCB grows, and a library implementation is attached to the one compiler |
| The current way, in which the user passes the `lib/` files | There is no namespace and no edition (version), and the tools (map, query) cannot tell the program from the library |
| Hash maps | The iteration order is not deterministic (stage0 does not use them either, gap analysis §3.1) |

## Consequences

- The 4B-02 implementation goes in the order `std::str`·`std::num` → `std::slice` → `std::collections` → `std::json` (2U-07, merged with T4-05). For each unit: official vectors or a Rust differential test, a run program, a fuzzer target.
- The map and queries show `std::` units apart from program units (the write tools do not edit `std::`).
- The five of `lib/` move to `std::` and the tests (`tests/lib_run`) change only in the names.

## Open questions

1. The cost of adding automatically: to avoid proving unused units, a per-unit proof cache is shipped with the compiler (together with the 5C distribution).
2. The specification view of `BTreeMap`: whether to put a mathematical map (`Map<K, V>`, Verus's view) into the specification language instead of a sequence of pairs. The specification language now has only sequences (slices).
3. Before method syntax (2M), calls are only in the form `std::str::starts_with(s, p)`.
